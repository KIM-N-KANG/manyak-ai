# [서비스 구현 명세서] — 6레이어 채팅 시스템의 구체화

> 본 문서는 **[1-PROMPT-LAYER.md]**(누가 무엇을 담는가), **[2-LAYER-PLACEMENT.md]**(어디에·언제·얼마나 자주 배치되는가), **[3-CONTEXT-ARCHITECTURE.md]**(왜 그렇게 조립해야 하는가의 설계 철학)의 추상 명세를, **마냑(Manyak) 채팅 서비스에서 실제로 어떻게 바인딩·구현하는가**로 구체화하는 구현 명세서다.
>
> 즉 1~3이 "보편 원리"라면, 본 문서는 **이 서비스 한정의 구현 결정과 데이터 흐름**을 확정한다. 콘텐츠 소유권·배치의 **정본(SSOT)은 여전히 [1-PROMPT-LAYER.md]·[2-LAYER-PLACEMENT.md]**이며, 본 문서는 그 위에서 구현 선택만 고정한다. 어긋날 경우 1·2가 우선한다.

---

## 0. 이 문서가 메우는 공백

1~3 문서는 6레이어가 **무엇을 담고**, **어디에 놓이고**, **왜 그렇게 조립되는지**를 보편적으로 정의한다. 그러나 다음 질문에는 답하지 않는다.

- 마냑은 **희소한 입력**(태그 + 선택 스토리라인 + 추가정보)만 받는데, 이걸로 STORY/CHARACTER/USER 레이어를 **언제·어떻게 채우는가?**
- "실시간 조립"은 **어느 시점에, 어떤 코드 경계에서** 일어나는가?
- 동적 상태(MEMORY)는 **무엇에·어떻게 저장**되고 매 턴 주입되는가?
- 모델·저장소를 **어떤 추상 경계**로 두는가?

본 문서는 그 공백을 메운다.

## 1. 핵심 원칙 — 세 시점을 분리한다

이 서비스의 모든 혼란은 **서로 다른 시점을 뭉뚱그릴 때** 발생한다. 특히 정적 준비 단계는 다시 **스토리 컴파일(A-1)**과 **세션 초기화(A-2)**로 갈린다. 반드시 셋을 분리한다.

### 시점 A-1 — 스토리 컴파일 (작가 시점), **스토리당 1회**
희소 입력(태그·스토리라인·추가정보)을 **풍성한 스토리 명세 JSON**으로 확장해 DB(`story_settings` 등)에 저장하는 시점. **컴파일 LLM은 여기서만 1회 돈다.** 이후 어떤 세션도 재컴파일하지 않으며, 같은 스토리를 여러 플레이어가 이 저장본으로 공유한다.

### 시점 A-2 — 세션 초기화 (플레이어 시점), **세션당 1회**
저장된 스토리 명세 JSON을 로드해 STORY/CHARACTER/USER 슬롯을 **결정적 치환으로** 채우고(LLM 호출 없음), MEMORY를 빈 상태로 초기화하며, 작가가 쓴 **오프닝 장면(`prologue`+`start_situation`)을 런타임 History의 첫 항목으로 시드**하는 시점. 이후 세션 내내 정적 레이어는 **고정 재사용**한다.

### 시점 B — 런타임 (조립), **매 턴**
이미 채워진 정적 레이어(고정) + History + MEMORY(동적) + PHI를 **사용자가 메시지를 보낼 때마다** 조립해 채팅 LLM에 던지는 시점.

```text
┌──────────── 시점 A-1: 스토리 컴파일 (작가, 스토리당 1회) ────────────┐
│  희소 입력                                                            │
│   · 선택 스토리라인 (3편 중 1편)                                      │
│   · 사용자 추가정보                                                   │
│   · (원래 태그 carry-over)                                            │
│        │                                                             │
│        ▼  하이브리드 = 컴파일 LLM 확장 + 결정적 치환                  │
│   스토리 명세 JSON (story_settings 등) → DB 저장                      │
└──────────────────────────────────────────────────────────────────────┘
                   │ (스토리당 1회 컴파일 — 이후 세션이 공유)
                   ▼
┌──────────── 시점 A-2: 세션 초기화 (플레이어, 세션당 1회) ────────────┐
│  저장된 스토리 명세 JSON 로드                                         │
│        │                                                             │
│        ▼  결정적 치환만 (컴파일 LLM 호출 없음)                       │
│   STORY-PROMPT / CHARACTER-PROMPT / USER-PROMPT  (채워진 정적 문서)   │
│   + MEMORY 빈 상태로 초기화                                           │
│   + 오프닝 장면(prologue·start_situation) History 시드               │
└──────────────────────────────────────────────────────────────────────┘
                              │ (정적 레이어 보관)
                              ▼
┌───────────────────── 시점 B: 런타임 (매 턴) ────────────────────────┐
│  사용자 입력 도착                                                     │
│        │                                                             │
│        ▼  조립기(assembler)                                          │
│   [시스템 앞] SAFETY→CORE→STORY-core→CHARACTER→USER                  │
│   [History]  누적 대화                                                │
│   [Depth]    MEMORY 현재 상태 (끝에서 1~2번째)                        │
│   [PHI]      CHARACTER→STORY→CORE→SAFETY 핵심만                      │
│        │                                                             │
│        ▼                                                             │
│   채팅 LLM 호출 → 응답                                                │
│        │                                                             │
│        ▼  (턴 후) 요약/추출 LLM → MEMORY 상태 갱신 → 저장             │
└──────────────────────────────────────────────────────────────────────┘
```

> **컴파일(시점 A-1, 스토리당 1회)·세션 초기화(시점 A-2, 세션당 1회)·런타임 조립(시점 B, 매 턴)을 섞지 않는다.** 컴파일 LLM은 A-1에서만 돌고, A-2는 저장본을 읽어 슬롯을 치환할 뿐이며, 조립은 B에서 매 턴 일어난다.

## 2. 확정된 설계 결정 (Phase 0)

### 2.1 역할 매핑 — USER = 주인공, AI = 주변인물 + 스토리 진행

스토리 생성 단계의 산출물을 채팅 레이어에 다음과 같이 귀속한다.

| 스토리 생성 산출물 | 채팅 레이어 | 연기 주체 |
|---|---|---|
| **주인공** (storyline의 "주인공은…") | **USER** | 사람이 1인칭으로 플레이 |
| **주변 인물** (예: 레이, 칸, 세린) | **CHARACTER** | AI가 연기하는 NPC |
| 장르·세계관·전개 | **STORY** | AI가 무대·진행 운용 |

- 사람은 **주인공을 1인칭(First-person)으로 플레이**한다. ([1-PROMPT-LAYER.md:127]의 "철저히 일인칭 관점의 플레이어 프로필" 원칙과 정합.)
- **AI는 주변 인물(들)을 연기하고, 동시에 스토리 진행(무대·연출)을 운용**한다.
- 따라서 CHARACTER-PROMPT의 "사용자에 대한 내적 태도"는 **NPC가 주인공(=사용자)을 어떻게 인식하는가**를 의미한다.

### 2.2 레이어 채우기 — 하이브리드 (컴파일 + 치환)

STORY/CHARACTER/USER를 채울 때 **두 방식을 결합**한다.

- **결정적 치환**: 이름·태그처럼 그대로 꽂으면 되는 값은 `{{슬롯}}` 치환. (현 `prompt.py` 패턴)
- **컴파일 LLM 확장**: 말투·동기·세계관 디테일처럼 **풍부함이 필요한 부분**은 세션 1회 LLM 호출로 생성.

근거: 순수 치환만으로는 캐릭터 카드가 얇아져 긴 세션 몰입이 약해지고, 풀 컴파일은 비용·지연·검증 난도가 크다. 하이브리드가 **풍부함과 결정성**을 동시에 확보한다.

### 2.3 모델 추상화 — 인터페이스 1개 + OpenAI 호환 구현 1개

- **얇은 `ChatProvider` 인터페이스**(예: `async def complete(messages, **opts) -> str`) 하나만 정의한다.
- 1차 구현은 **OpenAI 호환 chat completions** 클라이언트 하나(현 `gemini.py`처럼 `AsyncOpenAI` + `base_url` 교체). DeepSeek·Upstage·OpenAI 대부분이 그대로 붙는다.
- 모델·`base_url`·키는 `config.py`에서 주입한다.
- **과잉 추상화 금지**: provider별 클래스를 처음부터 만들지 않는다. messages 구조가 다른 provider(예: Anthropic)가 실제 필요해질 때 **어댑터를 추가**한다.

### 2.4 세션 상태 저장소 — in-memory dict (인터페이스 뒤)

- 런타임 MEMORY 상태는 **`session_id` 키의 파이썬 dict**로 시작한다.
- 단, 호출부는 **`SessionStore` 인터페이스**(`get/set/delete`)에만 의존하고, 내부만 dict로 구현한다. 추후 Redis/DB 교체 시 호출부 불변.

**장단점**

| 장점 | 단점 / 위험 |
|---|---|
| 외부 인프라 0, 즉시 구현 | 프로세스 재시작 시 **전부 소실(휘발성)** |
| MVP·단일 프로세스에 충분 | **다중 워커/수평 확장 불가** (워커별 dict 분리) |
| Phase 3~4 빠른 검증 | TTL/eviction 없으면 **메모리 누수** |

**완화책**: ① `SessionStore` 인터페이스로 추상화(교체 대비), ② 오래된 세션 정리용 TTL 훅 자리 예약, ③ 수평 확장 시점에 Redis 구현으로 교체.

### 2.5 입출력 표기·구조 규약 (CORE 소유)

- **표기 규약**: 사용자 입력과 AI 출력은 **동일한 표기**를 공유한다. `*...*` = 행동·상황 묘사(지문), 따옴표 없는 일반 텍스트 = 대사. 이 규약의 소유는 **CORE**다([1-PROMPT-LAYER.md]의 "대사·지문·내면 묘사의 표기 규약"). 입력·출력이 같은 형식이라야 History가 일관된 문체 본보기가 된다([3-CONTEXT-ARCHITECTURE.md] 3부).
  - **화자 라벨**: AI가 연기하는 주변 인물의 대사는 `인물명: 대사` 형식으로 화자를 매 줄 명시한다(예: `레이: 늦었군.`). 따옴표·볼드·괄호 화자 표기 등 다른 장식은 쓰지 않으며, 화자를 지문 서술로만 암시하지 않는다. 주인공(사용자)은 화자가 하나뿐이므로 라벨을 **생략**한다(`*...*`는 연출, 그 외 텍스트는 주인공 대사). 라벨 형식의 세부는 **CORE 소유**이며 그 구현은 `CORE-PROMPT.md`에 둔다.
    - **와이어 포맷 ↔ UI 표시 분리**: 이 라벨은 **모델이 출력하는 와이어 포맷**이다. 프론트엔드는 이를 **파싱해 화자를 식별한 뒤 이름 헤더·말풍선 등으로 변환·표시**(단일 화자 시 숨김 가능)하고, **History에는 라벨 원문을 그대로 보존**해 다음 턴 모델에 되먹인다. 즉 라벨은 payload(모델 출력·History)에 항상 존재하되, 최종 화면에 글자 그대로 `인물명:`을 노출할지는 표현 계층의 자유다.
- **AI 출력 3종**: 매 응답은 ① 상황 묘사 ② 인물 대사 ③ 다음 행동 선택지 3개를 담는다. **선택지 슬롯의 존재·개수(3개)·형식은 CORE(출력 봉투) 소유, 선택지의 내용은 STORY가 채운다.** CORE는 "선택지를 항상 3개, 정해진 모양으로"만 규정하고, STORY는 "어떤 선택지인가"를 결정한다(스타일 직교).

### 2.6 사용자 입력 유형과 갓모딩 굴절

- 런타임 사용자 입력은 세 가지이며, **모두 변환 없이 History의 user 턴으로** 들어간다.
  - ① 주인공 1인칭 대사 → 그대로
  - ② `*지문*` 연출(행동·상황 묘사) → 그대로
  - ③ AI 추천 선택지 선택 → 선택지 문구 그대로
- 입력창의 `*` 도우미 버튼은 `**`를 자동 삽입하는 **UI 편의**일 뿐, 백엔드·모델에는 `*...*` 텍스트 한 줄로 보인다. 별도 처리 없음.
- **갓모딩 굴절(STORY 소유)**: 사용자의 `*...*` 연출은 존중하되, ① 다른 인물의 대사·내면을 확정하거나 ② 결정적 사건(주요 인물 즉사, 즉시 승리 등)을 일방 선언하면, AI는 그대로 따르지 않고 개연성 있게 굴절시킨다. 입력을 받아들이는 정도(서사 권한)는 STORY가 통제한다.

### 2.7 MVP 범위 — 키워드북·스탯 제외

첫 구현(MVP)에서는 다음을 **구현하지 않는다**. 명세서·슬롯·런타임 어디에도 반영하지 않으며, ERD에 컬럼이 존재하더라도 채우지 않는다.

| 제외 항목 | 관련 ERD | 제외 이유 |
|---|---|---|
| **키워드북(조건부 삽입)** | `story_keyword_notes`, `story_keyword_triggers` | 트리거 기반 동적 주입은 STORY 조건부 메커니즘으로, MVP 이후로 미룬다. |
| **스탯 시스템** | `story_stats`, `play_session_stats` | 5.1과 일관 — 현 단계 MEMORY는 스탯 없이 "대화 맥락"만 기억한다. 호감도·관계 수치 등은 도입하지 않는다. |
| **해시태그(검색용 태그)** | (ERD 저장처 미정) | 발행 스토리에는 태그 중 장르만 `stories.genre`로 남기고, 검색용 해시태그는 MVP 이후로 미룬다. |

> 따라서 MVP의 동적 상태(MEMORY)는 `summary` 한 칸뿐이며(5.1), 정적 레이어를 채우는 입력은 키워드·스탯을 포함하지 않는다.

## 3. 스토리 컴파일 파이프라인 — 시점 A-1 상세

### 3.1 입력 스키마 (백엔드 → AI 서버)
- `selected_storyline`: 사용자가 선택한 스토리라인 1편 (4문장 본문)
- `extra_info`: 사용자가 입력한 추가정보 (자유 텍스트)
- `tags` (carry-over): 원래 장르·주인공·주변인물 태그

> **컴파일 산출물 = "스토리 명세 JSON" (영속 대상).** 위 희소 입력을 컴파일한 결과는 **스토리당 1번** 만들어져 백엔드 DB에 저장되고, 이후 채팅 세션은 이 저장본을 읽어 슬롯을 채운다(템플릿 6개는 모든 스토리가 공유, 스토리별로 다른 것은 이 JSON뿐). 마냑 ERD에서의 영속 위치는 다음과 같다.
>
> | 명세서 영역 | ERD 테이블 | 용도 |
> |---|---|---|
> | 프롬프트 재료 (STORY/CHARACTER/USER) | `story_settings` | 정적 레이어 슬롯의 소스 — 3.3 바인딩 |
> | 노출 메타 | `stories` (`title`, `one_line_intro`, `description`, `genre`) | 목록·상세 노출 전용(`genre`만 `{{장르}}` 슬롯에도 치환). **프롬프트 레이어 아님** |
> | 세션 시작 화면 | `story_start_settings` (`name`, `prologue`, `start_situation`) | `name`=시작 설정 이름(UI 표시), `prologue`=프롤로그·`start_situation`=시작 상황(첫 화면 도입 **+ 첫 턴 History 시드** — 3.4·1절 A-2) |
> | 첫 입력 추천 | `story_suggested_inputs` (`input_text`, 최대 3) | UI 추천 문구. 레이어 아님 |
>
> **SSOT 주의**: `stories.description`(노출 상세 소개)과 `story_settings.world_setting`(STORY 재료)은 내용이 겹치기 쉽다. 프롬프트에는 `world_setting`만 쓰고 `description`은 노출 전용으로 분리한다(0절 원칙).

### 3.2 레이어별 채우기 (하이브리드)

| 레이어 | 채우는 방식 | 소스 |
|---|---|---|
| **STORY** | 컴파일 LLM이 선택 스토리라인 + 장르 태그 → 세계관·전개 규칙·서사 문체로 확장 | 스토리라인, 장르 태그 |
| **CHARACTER** | 스토리라인에 등장하는 주변인물명 + 주변인물 태그 → 인물별 카드(성격·말투·동기) 생성 | 스토리라인, 주변인물 태그 |
| **USER** | 주인공 태그 + 추가정보 → 1인칭 플레이어 프로필로 치환·정리 | 주인공 태그, 추가정보 |
| **SAFETY / CORE** | 채우지 않음 — **완전 정적**(콘텐츠 비의존) | 고정 템플릿 |
| **MEMORY** | 빈 상태로 초기화 — 대화가 쌓이면서 요약·압축됨 | — |

> **인물 수 상한**: 컴파일 LLM에 "스토리라인에 실제 등장하는 **주요 인물 최대 3명만** CHARACTER 카드로 만들고, 나머지는 STORY 배경 인물로 흡수"를 지시한다. 시스템 프롬프트 비대화·토큰 폭증을 막기 위함이다. (주인공은 카드가 아니라 **USER**가 소유한다.)

### 3.3 레이어별 슬롯 스키마

> 슬롯은 **사용자 입력을 꽂는 곳이 아니라, 세션 초기화(시점 A-2)에서 `story_settings`로부터 채워지는 출력 칸**이다. 아래 표의 **소스 열은 모두 `story_settings` 필드(또는 그 하위 키)**이며(`{{장르}}`만 `stories.genre` 예외), 세션 슬롯 채움은 전부 결정적 치환이다. 방식 열의 **컴파일**은 그 필드가 시점 A-1에서 컴파일 LLM으로 생성됐다는 뜻이고, **치환**은 원본 값이 가공 없이 그대로 들어간다는 뜻이다.

> **마냑 DB 바인딩 (`story_settings` → 레이어).** 슬롯의 재료는 한 흐름을 거쳐 형태가 두 번 바뀐다: **태그·스토리라인 → 컴파일(AI 부풀림, 시점 A-1) → `story_settings` 저장 → 슬롯 채움(시점 A-2).** 따라서 3.2(레이어별 채우기)가 "태그·스토리라인"을 소스로 적은 것(흐름의 앞 토막 = 컴파일 입력)과, 3.3 슬롯표가 `story_settings`를 소스로 적은 것(흐름의 뒤 토막 = 세션 슬롯 채움)은 같은 흐름의 다른 지점일 뿐 충돌이 아니다.
>
> 컴파일 산출물이 영속되는 `story_settings`의 7필드는 **STORY·CHARACTER·USER 세 정적 레이어에만** 귀속한다. 마냑 ERD 기준 귀속을 다음과 같이 **확정**한다.
>
> | `story_settings` 필드 | 소유 레이어 | 대응 슬롯 | 비고 |
> |---|---|---|---|
> | `world_setting` | STORY | `{{세계관_설정}}` | |
> | `plot_setting` | STORY | `{{핵심_전제}}`, `{{주요_갈등_가능성}}` | **객체** `{ premise, conflict }` — 2슬롯이라 구조화 저장(3.4). |
> | `rule_setting` | **STORY** | `{{전개_규칙}}` | 작가가 쓴 스토리별 콘텐츠이므로 **CORE 아님**(CORE는 콘텐츠 비의존 고정, 2.5·3.2). 출력 형식의 고정 봉투만 CORE가 소유한다. `tone_setting`과 **별도 슬롯으로 분리**(아래 확정). |
> | `tone_setting` | **STORY** | `{{문체_톤}}` | 서술 톤은 무대 연출 = STORY. 개별 NPC 말투만 CHARACTER `{{말투}}`가 가져간다. `rule_setting`·`length_ratio`와 **별도 슬롯으로 분리**(아래 확정). |
> | `length_ratio` | **STORY** | `{{분량_배분}}` | 묘사 대 대사 비중(예: "묘사 4 : 대사 6"). 1번 명세서 직교 원칙상 서술 톤과 별개의 STORY 하위 책임이므로 `tone_setting`에 합치지 않고 **전용 필드로 분리**(아래 확정). |
> | `character_setting` | CHARACTER | `{{인물명}}`/`{{성격}}`/`{{말투}}`/`{{동기}}`/`{{주인공에_대한_태도}}` | **객체 배열**(인물 1명 = 1원소·최대 3, 3.4). **주변인물만** — 텍스트에 주인공이 섞이면 컴파일 시 분리해 주인공 정보는 USER로 보낸다(2.1). |
> | `user_role_setting` | USER | `{{주인공_호칭}}`/`{{역할_신분}}`/`{{배경_설정}}`/`{{성격_특징}}`/`{{입력_선호}}` | 주인공(1인칭 플레이어). **객체** — 5슬롯이 각 하위 키에 대응(3.4). |
>
> **슬롯 소스의 SSOT (확정).** 비-장르 슬롯은 원본 태그·추가정보를 **직접 참조하지 않는다.** 원본 입력은 컴파일(A-1) 때 `story_settings` 필드로 녹아들어 JSON에 원본이 남지 않으므로, 세션 슬롯 채움(A-2)은 **전부 `story_settings`의 컴파일 결과에서** 이뤄진다. 이때 **여러 슬롯으로 갈리는 필드는 줄글이 아니라 구조화 JSON 객체로 저장**한다 — `user_role_setting`(객체)·`character_setting`(객체 배열, 인물 1명 = 1원소·최대 3)·`plot_setting`(객체)의 하위 키가 각 슬롯에 **결정적으로** 치환된다(파싱 외 LLM·재분석 불필요). 그래야 "A-2 = LLM 없는 치환"이라는 원칙이 성립한다. 슬롯과 1:1인 `world_setting`·`rule_setting`·`tone_setting`·`length_ratio`는 문자열로 둔다. `{{장르}}`만 `stories.genre`에서 직접 치환하는 예외 경로다.
>
> **장르는 예외.** `{{장르}}` 슬롯은 위 컴파일 흐름을 따르지 않고 `stories.genre`에서 **그대로 치환**된다(`story_settings`를 거치지 않으며 AI 부풀림도 없음). 주인공·등장인물 태그와 달리 장르만 최종 스토리에 원본으로 남기 때문이다(태그 중 장르만 `stories`에 저장). 나머지 태그는 `story_settings`에 녹아든 형태로만 존재하므로 별도 슬롯 소스가 아니다.
>
> **슬롯 분리 (확정).** `rule_setting`(전개 규칙·연출)·`tone_setting`(서술 톤)·`length_ratio`(분량 배분)는 한 슬롯에 합치지 않고 각각 전용 슬롯 `{{전개_규칙}}`·`{{문체_톤}}`·`{{분량_배분}}`으로 **분리한다.** 1번 명세서의 스타일 직교 분리(원칙 0 — 전개 규칙·서술 톤·출력 구성 비율(분량 배분)은 STORY 안에서도 서로 다른 하위 책임)에 따른 결정이며, Phase 1에서 STORY 템플릿을 이 세 슬롯으로 작성한다(8절).
>
> SAFETY·CORE에는 대응하는 `story_settings` 필드가 없다(콘텐츠 비의존). MEMORY는 명세서가 아니라 런타임 대화로 채워진다(5절).

#### STORY-PROMPT.md (정적 무대·연출)
| 슬롯 | 채우는 방식 | 소스 |
|---|---|---|
| `{{장르}}` | 치환 | `stories.genre` (예외 경로 — 유일하게 원본에서 직접 치환) |
| `{{세계관_설정}}` | 컴파일 | `world_setting` |
| `{{핵심_전제}}` | 컴파일 | `plot_setting.premise` (도입 상황) |
| `{{전개_규칙}}` | 컴파일 | `rule_setting` (작가 전개 규칙·연출 + 장르 속도·긴장 곡선이 컴파일 시 반영됨) — **PHI로 재주입되는 정적 규칙** |
| `{{문체_톤}}` | 컴파일 | `tone_setting` (서술 톤 + 장르 톤이 컴파일 시 반영됨) — **PHI로 재주입** |
| `{{분량_배분}}` | 컴파일 | `length_ratio` (묘사 대 대사 비중, 예: "묘사 4 : 대사 6"; 장르 속도감이 컴파일 시 반영됨) — **PHI로 재주입** |
| `{{주요_갈등_가능성}}` | 컴파일 | `plot_setting.conflict` (일어날 수 있는 사건·분기 — Actuality 아님) |

#### CHARACTER-PROMPT.md (주변인물, **인물 1명당 1블록 반복 — 주요 인물 최대 3명**)
| 슬롯 | 채우는 방식 | 소스 |
|---|---|---|
| `{{인물명}}` | 컴파일 | `character_setting[].name` |
| `{{성격}}` | 컴파일 | `character_setting[].personality` |
| `{{말투}}` | 컴파일 | `character_setting[].tone` |
| `{{동기}}` | 컴파일 | `character_setting[].motivation` (이 인물이 원하는 것) |
| `{{주인공에_대한_태도}}` | 컴파일 | `character_setting[].attitude_to_user` (NPC가 주인공=사용자를 대하는 **초기 고정 태도**. 이후 변화는 MEMORY가 기록) |

#### USER-PROMPT.md (주인공, 1인칭)
| 슬롯 | 채우는 방식 | 소스 |
|---|---|---|
| `{{주인공_호칭}}` | 컴파일 | `user_role_setting.name` (호칭 — 추가정보 반영, 없으면 기본값) |
| `{{역할_신분}}` | 컴파일 | `user_role_setting.role` |
| `{{배경_설정}}` | 컴파일 | `user_role_setting.background` |
| `{{성격_특징}}` | 컴파일 | `user_role_setting.personality` |
| `{{입력_선호}}` | 컴파일 | `user_role_setting.preference` (선택 — 비어 있을 수 있음) |

#### SAFETY / CORE
- **슬롯 없음.** 콘텐츠 비의존 정적 템플릿이므로 채우지 않는다.

### 3.4 스토리 명세 JSON 스키마 (MVP 확정본)

시점 A-1(스토리 컴파일)의 영속 산출물이 **"스토리 명세 JSON"**이다. 스토리당 1개 만들어져 DB에 저장되고, 채팅 세션은 이를 읽어 슬롯을 채운다. MVP 확정 필드는 다음과 같다.

> **요지**: 이 JSON 중 `prompt_settings` 7필드 + `meta.genre`만 STORY·CHARACTER·USER 3개 프롬프트의 빈칸을 채운다. 나머지(노출 메타·시작 화면·추천)는 프롬프트 바깥(노출·UI)에서 쓰인다.

| 영역 | 필드(컬럼) | 한글명 | 누가 채우나 | 프롬프트 유입 | 레이어 |
|---|---|---|---|---|---|
| 노출 메타 (`stories`) | `title` | 스토리 제목 | AI 초안 + 사용자 확정 | ❌ 노출 | — |
| | `one_line_intro` | 한 줄 소개 | AI 초안 + 사용자 확정 | ❌ 노출 | — |
| | `description` | 스토리 소개 | AI 초안 + 사용자 확정 | ❌ 노출 (`world_setting`과 SSOT 분리) | — |
| | `genre` | 장르 | 사용자 선택(태그) | ✅ `{{장르}}` 치환(예외 경로) | STORY |
| 프롬프트 재료 (`story_settings`) | `world_setting` | 세계관 설정 | AI 컴파일 | ✅ | STORY |
| | `plot_setting` | 사건 설정(객체 `{premise, conflict}`) | AI 컴파일 | ✅ | STORY |
| | `rule_setting` | 규칙 설정 | AI 컴파일 | ✅ | STORY |
| | `tone_setting` | 문체 설정(서술 톤) | AI 컴파일 | ✅ | STORY |
| | `length_ratio` | 분량 배분(묘사 대 대사 비중) | AI 컴파일 | ✅ | STORY |
| | `character_setting` | 인물 설정(객체 배열, **주변인물만**) | AI 컴파일 | ✅ | CHARACTER |
| | `user_role_setting` | 역할 설정(객체, 주인공) | AI 컴파일 | ✅ | USER |
| 시작 화면 (`story_start_settings`) | `name` | 시작 설정 이름 | AI 초안 + 사용자 확정 | ❌ UI 표시 | — |
| | `prologue` | 프롤로그 | AI 초안 + 사용자 확정 | △ 첫 화면 도입 + **첫 턴 History 시드** | — (정적 레이어 아님) |
| | `start_situation` | 시작 상황 | AI 초안 + 사용자 확정 | △ 첫 화면 도입 + **첫 턴 History 시드** | — (정적 레이어 아님) |
| 추천 입력 (`story_suggested_inputs`) | `input_text` | 추천 입력(최대 3) | AI | ❌ 추천 버튼 | — |

## 4. 런타임 조립 (매 턴) — 시점 B 상세

### 4.1 조립 위치(물리적 좌표)
[2-LAYER-PLACEMENT.md] 2절 다이어그램을 그대로 따른다.

1. **[시스템 앞]** SAFETY → CORE → STORY-core → CHARACTER → USER (정적, 세션 1회 고정)
2. **[History]** 누적 대화 (러닝 트랜스크립트)
3. **[Depth]** MEMORY 현재 상태 — 내역 **끝에서 1~2번째**에 매 턴 갱신 삽입
4. **[PHI]** 정적 가드레일/필터 핵심만, 내부 순서 **CHARACTER → STORY → CORE → SAFETY** (SAFETY가 생성에 가장 근접)

> USER는 PHI·Depth 어디에도 재주입하지 않는다(갓모딩 방지). MEMORY는 PHI가 아니라 Depth가 전담한다.

### 4.2 한 턴의 처리 흐름
```text
1. 사용자 입력 도착 (session_id 포함)
2. (직전 턴 확정) 직전 AI 응답이 있으면 그 턴을 확정으로 보고,
   요약/추출 LLM이 최근 History → 상태 JSON 갱신 → SessionStore.set
   · 재생성으로 폐기된 응답은 다음 입력이 오기 전이라 여기 포함되지 않음(오염 차단)
3. SessionStore.get(session_id) → MEMORY 상태 JSON 로드
4. 입력 정규화: *지문* / 대사 / 선택지를 변환 없이 History user 턴에 추가 (2.5·2.6)
5. MEMORY-PROMPT.md 양식에 상태 JSON 렌더 → "[현재 상태]" 블록
6. 조립기: 시스템(앞) + History + Depth(현재 상태) + PHI 구성
7. ChatProvider.complete(messages) → 응답 (상황 묘사 + 대사 + 선택지 3개, 2.5)
8. 응답을 History에 추가하고 사용자에게 반환 (요약은 다음 입력 때 2단계에서 수행)
```

> **첫 턴 주의**: 세션 첫 입력이 도착하는 시점에 History는 비어 있지 않다. A-2에서 시드한 **오프닝 장면(`prologue`+`start_situation`)이 History 첫 항목**으로 이미 들어 있으므로, 4번에서 사용자 첫 입력이 그 뒤에 붙고 6번 조립 시 모델이 오프닝 장면을 본다. (2단계 요약은 직전 AI 응답이 없는 첫 턴에는 건너뛴다.)

### 4.3 명세 재검증 메모
[2-LAYER-PLACEMENT.md]는 "임의 깊이 삽입"을 전제하나, 실제 OpenAI 호환 API에서 **mid-array system 메시지의 동작**은 모델마다 다르다. 따라서 Depth 블록을 `system` 역할로 끝 근처에 둘지, `user` 역할 메타 메시지로 둘지는 **Phase 5에서 검증 후 확정**한다(7절).

## 5. MEMORY의 3분리 — 가장 흔한 혼동 지점

"채팅 맥락을 기억하는 MEMORY.md"라는 표현은 **세 가지를 뭉뚱그린 것**이다. 반드시 분리한다.

| 구분 | 정체 | 어디에 사는가 | 정적/동적 |
|---|---|---|---|
| **① MEMORY-PROMPT.md** | 상태를 **어떤 포맷으로 적고**, **무엇만 기록하며**(Actuality+State), LLM이 주입된 상태를 **어떻게 읽을지**의 규칙·스키마·렌더 양식 | 리포 `prompt/chat/` | **정적** (커밋됨) |
| **② 런타임 상태 데이터** | 대화 맥락 요약·배경 정보 압축본 | **세션 저장소(JSON)** | **동적** (세션별) |
| **③ History** | 원본 대화 트랜스크립트 | **백엔드 DB**(런타임엔 messages 배열로 로드) | 누적 |

핵심 규칙:
- **① MEMORY-PROMPT.md는 채팅 맥락을 저장하지 않는다.** "어떻게 저장·관리할지를 정의"하는 **정적 계약서**다.
- **② 실제 상태는 .md 파일로 커밋하지 않는다.** 세션별 데이터이므로 `session_id` 키의 JSON으로 저장소에 둔다.
- **MEMORY는 History의 파생 요약**이다. ([1-PROMPT-LAYER.md:204]) 직전 턴이 확정된 시점(= 다음 사용자 입력 도착)에 요약/추출 LLM이 History → 상태 JSON으로 압축·갱신한다(4.2).
- **③ History 원본의 영속 저장은 백엔드 DB가 소유**한다. AI 서버의 `SessionStore`는 History 전체가 아니라 그 **파생 요약(state)만** 보관한다. 둘은 별개 저장소다(채팅 이어가기는 백엔드 DB의 History 복원으로 이뤄진다).
- 이름 충돌 주의: 런타임 저장소를 `MEMORY.md`로 부르지 않고 **"세션 상태(session state)"**로 부른다.

### 5.1 MEMORY 상태 스키마

> 현 단계는 **스탯(호감도·관계 수치 등)이 없으며, "대화 맥락"만 기억**한다. 따라서 상태 스키마는 요약 한 칸으로 시작한다. (향후 스탯이 생기면 필드를 추가한다.)

**상태 데이터 (세션 저장소의 JSON):**
```json
{ "summary": "지금까지의 대화 맥락 요약 텍스트" }
```

**Depth 주입 렌더 양식 (`MEMORY-PROMPT.md`가 정의):**
```text
[현재 상태]
{{summary}}
```

**기록 규칙:**
- `summary`에는 **확정된 사실·진행 상황(Actuality)**만 압축해 적는다. 아직 일어나지 않은 가능성(STORY 소관)이나 인물의 고정 성격(CHARACTER 소관)은 적지 않는다.
- **직전 턴이 확정된 시점(= 다음 사용자 입력이 도착한 때)**에 요약/추출 LLM이 최근 History를 읽어 `summary`를 갱신한다. 재생성으로 폐기된 응답은 다음 입력이 오기 전이라 요약에 반영되지 않는다(재생성 기억 오염 차단, 4.2).
- 이 블록은 **Depth로 내역 끝 가까이** 매 턴 주입된다. (system 역할 기준; Claude 어댑터 추가 시 조립기가 user 역할로 분기.)

## 7. Depth / PHI 검증 (Phase 5 예고)

- **Depth·PHI·World Info는 모델 기능이 아니라 클라이언트 측 messages 조립 기법**이다. DeepSeek·OpenAI·Anthropic 어디서나 동일하게 구현 가능하며, 별도 모델 지원이 필요 없다.
- 검증 대상은 "모델 능력"이 아니라 **"늦게 주입한 지시를 모델이 실제로 더 잘 따르는가"**다.
- **A/B 하네스**: 동일 History에서 ⓐ MEMORY를 맨 앞 시스템에만 / ⓑ 끝에서 1~2번째(Depth)에 주입 → 동일 질문에 대한 상태 준수도 비교. 배포 모델(DeepSeek)로 그대로 실행.
- 부수 검증: mid-array `system` vs `user` 메타 메시지의 효과 차이(4.3).

## 9. 수용 기준 (자기 검증)

- 시점 A-1(스토리 컴파일·스토리당 1회)·A-2(세션 초기화·세션당 1회)·시점 B(조립·매 턴)가 분리되고, 컴파일 LLM은 A-1에서만 도는 것이 명시됨 (1절)
- Phase 0의 4가지 결정이 모두 명시됨 (2절)
- 역할 매핑이 스토리 생성 산출물과 1:1로 귀속됨 (2.1)
- MEMORY가 ①템플릿/②상태/③History로 분리되고, 런타임 상태가 .md 커밋이 아님이 명시됨 (5절)
- 콘텐츠 소유권·배치의 SSOT가 [1·2]임을 재확인하고 본 문서는 구현 결정만 다룸 (0절, 머리말)
- 모델·저장소가 추상 경계 뒤에 있고 과잉 추상화를 피함 (2.3, 2.4, 6절)
- Depth/PHI가 모델 기능이 아니라 조립 기법임과 검증 방식이 명시됨 (7절)
- 입출력 표기 규약과 선택지 3슬롯의 소유(CORE)·내용(STORY)이 분리 명시됨 (2.5)
- 사용자 입력 3종 처리와 갓모딩 굴절(STORY) 규칙이 명시됨 (2.6)
- CHARACTER 카드가 주요 인물 최대 3명으로 제한됨 (3.2~3.3)
- 요약 갱신이 턴 확정 시점에 일어나 재생성 오염을 막음 (4.2, 5.1)
- History 영속은 백엔드 DB, SessionStore는 파생 요약만 보관임이 명시됨 (5절)
- 작가 오프닝 장면(`prologue`·`start_situation`)이 첫 화면 표시 + 첫 턴 History 시드로 모델에 전달되어 첫 턴 연속성이 보장됨 (1절 A-2, 3.4, 4.2)
