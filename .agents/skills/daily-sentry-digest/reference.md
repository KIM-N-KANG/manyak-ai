## 조회

| 항목 | 값 |
| --- | --- |
| org | `manyak` |
| 프로젝트 | `python-fastapi`(ai) · `java-spring-boot`(server) · `typescript-nextjs`(web) |
| 창 | 지난 24시간 |
| 이어지는 오류 | `is:unresolved environment:[prod, production]` |
| 새 오류 | 위 쿼리 + `firstSeen:>{24시간 전 UTC를 ISO로}` (별도 조회) |
| 대조군 | 위 쿼리 + `firstSeen:>{7일 전 UTC를 ISO로}` (아래 "0건 판정" 참조) |

`firstSeen`에는 **절대 시각만 쓴다.** `-24h`·`age:-1d` 같은 상대 기간은 쓰지 않는다(함정 4).
값은 실행 시각에 계산한다. 예: `date -u -v-24H '+%Y-%m-%dT%H:%M:%S'`.

### 0건 판정: 대조군 없이는 "오류 없음"이라고 쓰지 않는다

새 오류 조회가 0건으로 나오면, **곧바로 "신규 없음"이라고 적지 않는다.**
7일 대조군을 한 번 더 던져 결과가 0보다 큰지 본다.

- 대조군 > 0 → 조회는 살아 있다. "신규 없음"은 사실이다.
- 대조군 = 0 → 조회 계층이 조용히 깨졌다는 뜻이다. **메시지에 "신규 판정 실패"로 적는다.**
  0건과 고장을 구분하지 못한 채 "오류 없음"을 보내면 장애가 난 날을 조용한 날로 보고하게 된다.

## 실측으로 확인한 함정 5개 (2026-07-31)

규칙이 이렇게 생긴 이유다. 규칙을 고칠 때 이 다섯을 다시 깨지 않는지 본다.

**1. 응답의 `First seen` 표시값으로 "새 오류"를 판단하면 안 된다.**
조회 창 안에서의 첫 등장이라 창에 따라 값이 달라진다. 같은 이슈(`TYPESCRIPT-NEXTJS-14`)가
7일 창에서는 "3일 전", 24시간 창에서는 "16시간 전"으로 나왔다. 표시값을 쓰면 매일 모든
오류가 새 오류가 된다. 반드시 **쿼리 조건**으로 걸어 따로 조회한다.

**2. 환경 이름이 서비스마다 다르다.**

| 프로젝트 | 환경값 |
| --- | --- |
| typescript-nextjs | `production` |
| python-fastapi | `prod` |
| java-spring-boot | `prod` |

`environment:production` 하나만 걸면 AI·서버 오류가 통째로 사라진다.
`environment:[prod, production]`으로 둘 다 넣는다(대괄호 문법 동작 확인함).

**3. 백엔드는 사용자 수가 항상 0이다.**
AI·서버는 사용자 컨텍스트를 붙이지 않아 `Users: 0`으로 찍힌다. 사용자 수로 정렬하거나
임계값을 걸면 백엔드 오류가 매일 바닥에 깔려 보이지 않는다. 그래서 아래 분류는
심각도가 아니라 **서비스별**로 나눈다.

**4. 상대 기간 문법(`-24h`·`age:-1d`)이 불안정하다. 실패도 조용하다.**
Sentry MCP는 쿼리를 내부 에이전트로 고쳐 쓴 뒤 던지는데, 그 결과가 매번 같지 않다.
같은 자리에서 실측한 것:

| 넣은 값 | 결과 |
| --- | --- |
| `firstSeen:-24h` | 1차 "결과 없음", 2차 HTTP 400 (`>=-24h` 파싱 실패) |
| `age:-1d` | "결과 없음" |
| `age:-3d` | HTTP 400 (`>-3d` 파싱 실패) |
| `age:-7d` | 정상 (13건) |

400은 그나마 낫다. **더 나쁜 것은 "결과 없음"이다.** 조회가 깨진 것과 진짜 0건이
똑같이 보인다. 그대로 두면 매일 "신규 없음"을 보내면서 새 오류를 통째로 놓친다.

절대 시각(ISO)은 일관되게 동작했다. 같은 자리에서 확인한 단조성:

| 조건 | 건수 |
| --- | --- |
| `firstSeen:>2026-07-20T00:00:00` | 17 |
| `firstSeen:>2026-07-27T00:00:00` | 6 |
| `firstSeen:>2026-07-30T06:16:00` | 0 |

그래서 절대 시각만 쓰고, 0건일 때는 위 "0건 판정"의 대조군으로 한 번 더 확인한다.

**5. 슬랙에 보낼 때 마크다운 표는 조용히 사라진다.**
`slack_send_message`의 도구 설명은 표를 지원한다고 적고 있지만, 실제로 보내 보니
4줄짜리 표가 통째로 없어지고 빈 줄만 남았다(2026-07-31 실측, 첫 전송에서 발생).
전송은 성공으로 끝나기 때문에 **보내는 쪽에서는 실패를 알 수 없다.**

- **표를 쓰지 않는다.** 여러 항목은 `-` 목록으로 적는다(목록은 정상 전달을 확인함).
- 첫 전송 뒤에는 `slack_read_thread`로 읽어 내용이 다 들어갔는지 확인한다.

## 분류

| 묶음 | 대상 | 표시 |
| --- | --- | --- |
| 🔴 새 오류 | 신규 조회(위 "조회" 표)에 걸린 것 전부 | 개별, 맨 위 |
| 🟠 백엔드 | `python-fastapi` · `java-spring-boot` | **전부 개별** |
| 🟡 웹 (그 외) | 끊김류가 아닌 웹 오류 | 개별 |
| ⚪ 웹 (끊김류) | `Failed to fetch` · `Load failed` | **한 줄로 접고 스레드에 상세** |

- **백엔드를 전부 개별로 두는 이유**: 볼륨이 원래 적고(하루 3건 수준) 사용자 수가 0이라,
  어떤 임계값을 걸어도 통째로 접힌다. 함정 3의 결과다.
- **웹 끊김류를 접는 이유**: 24시간 7건 중 4건, 7일 20건 중 11건이 이것이다. 사용자가 탭을
  닫거나 네트워크가 끊겨도 찍혀서 개별로는 고칠 게 없다.
- **접기 예외를 두지 않는다.** "사용자 N명 이상이면 펼친다" 같은 임계값은 근거 없이
  찍는 값이고, 틀리면 조용히 놓친다. 대신 **접은 줄에 이슈 종수·이벤트 수·사용자 수를
  반드시 적는다** — 임계값을 나중에 정할 때 필요한 숫자가 매일 메시지에 남는다.

### 묶기

같은 시각대에 AI → 서버 → 웹으로 이어진 것으로 보이면 한 사건으로 묶는다.
단 **요청 단위로 대조하지 않았으면 인과로 단정하지 않고** 스레드에 "미확인"으로 남긴다.
매일 요청 단위 대조까지 하면 실행 시간과 비용이 커져서, 지금은 하지 않는다.

### 빼기

- 이미 `resolved` · `ignored` 상태

## 메시지 형식

정본은 `knk-harness/docs/templates/slack-report.md`의 🐛 템플릿이다. 다만 **클라우드 루틴에는
그 레포가 체크아웃되지 않으므로**, 이 절만 보고도 쓸 수 있게 필요한 내용을 여기 옮겨 둔다.
정본이 바뀌면 이 절도 함께 손본다.

### 지켜야 할 것

- 슬랙은 GitHub 마크다운이 아니다. 굵게는 `*텍스트*`, 링크는 `<URL|표시 텍스트>`,
  목록은 `•`. 제목 수준(`#`)은 동작하지 않는다.
- 첫 줄은 `🐛 [영역] 한 줄 요약`. 영역은 `[ai]` `[server]` `[web]` `[infra]`를 쓰고,
  요약에 여러 서비스가 걸리면 이어 붙인다(`[ai][server][web]`).
- `*요청*` 줄을 비우지 않는다. 받는 쪽이 무엇을 할지 알려주는 줄이다.
- 시각에는 타임존(KST)을 반드시 붙인다.
- **표를 쓰지 않는다**(함정 5). 여러 항목은 목록으로 적는다.
- 본문은 짧게, 상세는 스레드로 나눈다.
- 사용자 입력 원문·채팅 원문·secret을 넣지 않는다.

### `*요청*` 값

이 파이프라인은 **새 오류가 하나라도 있으면 `조사`, 없으면 `공유만`**을 쓴다(사용자 결정).
어느 항목이 새 것인지는 🔴로 구분한다.

`수정`을 기본값으로 쓰지 않는다. 자동 발송이 매일 `수정`을 달면 받는 AI가 매일 고치기
시작한다. 자동 발송의 가장 비싼 오작동이다.

### 본문 골격

```
🐛 [ai][server][web] 지난 24시간 오류 N건 — 새로 생긴 것 M건

*요청*: 공유만
*무슨 일*: 1~2문장. 무엇이 가장 잦은지까지
*영향*: 사용자 N명 (이슈별 합산이라 중복 가능 — 고유 인원이 아니다)
*긴급도*: 🔴 지금 / 🟡 이번 스프린트 / 🟢 여유 있을 때
*집계 창*: YYYY-MM-DD HH:MM ~ MM-DD HH:MM KST

*백엔드 N건*
• [ai] 한 줄 설명 — N건, 마지막 YYYY-MM-DD HH:MM KST
  <이슈 URL|이슈 ID>

*웹 네트워크 끊김류 N종 N건 / 사용자 N명 (접음)*
```

### 스레드 골격

```
집계 규칙: environment:[prod, production] · is:unresolved · 지난 24시간
새 오류 판정: firstSeen:>{24시간 전 UTC ISO} 별도 조회 → N건
0건 대조군: firstSeen:>{7일 전 UTC ISO} → N건

웹 접힌 N종:
• 이슈ID  제목  경로  N건/N명
  ...

미확인: (확인하지 못한 인과관계가 있으면 여기에)
```

### 오류 0건인 날

```
🐛 [ai][server][web] 지난 24시간 오류 없음

*요청*: 공유만
*집계 창*: YYYY-MM-DD HH:MM ~ MM-DD HH:MM KST
```

침묵하지 않는 이유: 안 보내면 파이프라인이 죽은 날과 조용한 날이 구분되지 않는다.
매일 뭔가 오게 두면 끊겼을 때 사람이 알아챈다 — 그래서 죽음 감시를 따로 만들지 않았다.

## 실행 환경 (클라우드 루틴)

- 매일 오전 10시 KST = cron `0 1 * * *` (UTC)
- 클라우드 루틴은 **로컬 파일·환경변수·형제 레포를 볼 수 없다.**
  `.env`도 `../knk-harness`도 없다. 그래서 이 문서가 자립적이어야 한다.
- Sentry·Slack은 claude.ai 커넥터로 붙인다. 시크릿을 파일이나 프롬프트에 적지 않는다.
