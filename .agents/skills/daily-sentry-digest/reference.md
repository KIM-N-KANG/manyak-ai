## 조회

| 항목 | 값 |
| --- | --- |
| org | `manyak` |
| 프로젝트 | `python-fastapi`(ai) · `java-spring-boot`(server) · `typescript-nextjs`(web) |
| 창 | 지난 24시간 |
| 이어지는 오류 | `is:unresolved environment:[prod, production]` |
| 새 오류 | 위 쿼리 + `firstSeen:>{24시간 전 UTC를 ISO로}` (별도 조회) |
| 대조군 | 위 쿼리 + `firstSeen:>{7일 전 UTC를 ISO로}` (아래 "0건 판정" 참조) |
| 어제 대조 | 같은 쿼리를 **창 48시간**으로 (본문 `어제와 비교` 줄에 쓴다) |

`어제 대조`는 이슈별 건수를 24시간 결과와 짝지어 뺀다. 이슈 하나의 어제 건수는
`48시간 건수 - 24시간 건수`다. 48시간 결과에만 있고 24시간 결과에 없는 이슈는
어제만 나고 오늘은 안 난 것이므로 본문에 올리지 않는다.

`firstSeen`에는 **절대 시각만 쓴다.** `-24h`·`age:-1d` 같은 상대 기간은 쓰지 않는다(함정 4).
값은 실행 시각에 계산한다. 예: `date -u -v-24H '+%Y-%m-%dT%H:%M:%S'`.

### 0건 판정: 대조군 없이는 "오류 없음"이라고 쓰지 않는다

새 오류 조회가 0건으로 나오면, **곧바로 "신규 없음"이라고 적지 않는다.**
7일 대조군을 한 번 더 던져 결과가 0보다 큰지 본다.

- 대조군 > 0 → 조회는 살아 있다. "신규 없음"은 사실이다.
- 대조군 = 0 → 조회 계층이 조용히 깨졌다는 뜻이다. **메시지에 "신규 판정 실패"로 적는다.**
  0건과 고장을 구분하지 못한 채 "오류 없음"을 보내면 장애가 난 날을 조용한 날로 보고하게 된다.

## 실측으로 확인한 함정 5개 (2026-07-31)

규칙이 이렇게 생긴 이유다. 규칙을 고칠 때 이 다섯을 다시 깨지 않는지 본다.

**1. 응답의 `First seen` 표시값으로 "새 오류"를 판단하면 안 된다.**
조회 창 안에서의 첫 등장이라 창에 따라 값이 달라진다. 같은 이슈(`TYPESCRIPT-NEXTJS-14`)가
7일 창에서는 "3일 전", 24시간 창에서는 "16시간 전"으로 나왔다. 표시값을 쓰면 매일 모든
오류가 새 오류가 된다. 반드시 **쿼리 조건**으로 걸어 따로 조회한다.

**2. 환경 이름이 서비스마다 다르다.**

| 프로젝트 | 환경값 |
| --- | --- |
| typescript-nextjs | `production` |
| python-fastapi | `prod` |
| java-spring-boot | `prod` |

`environment:production` 하나만 걸면 AI·서버 오류가 통째로 사라진다.
`environment:[prod, production]`으로 둘 다 넣는다(대괄호 문법 동작 확인함).

**3. 백엔드는 사용자 수가 항상 0이다.**
AI·서버는 사용자 컨텍스트를 붙이지 않아 `Users: 0`으로 찍힌다. 사용자 수로 정렬하거나
임계값을 걸면 백엔드 오류가 매일 바닥에 깔려 보이지 않는다. 그래서 아래 분류는
심각도가 아니라 **서비스별**로 나눈다.

**4. 상대 기간 문법(`-24h`·`age:-1d`)이 불안정하다. 실패도 조용하다.**
Sentry MCP는 쿼리를 내부 에이전트로 고쳐 쓴 뒤 던지는데, 그 결과가 매번 같지 않다.
같은 자리에서 실측한 것:

| 넣은 값 | 결과 |
| --- | --- |
| `firstSeen:-24h` | 1차 "결과 없음", 2차 HTTP 400 (`>=-24h` 파싱 실패) |
| `age:-1d` | "결과 없음" |
| `age:-3d` | HTTP 400 (`>-3d` 파싱 실패) |
| `age:-7d` | 정상 (13건) |

400은 그나마 낫다. **더 나쁜 것은 "결과 없음"이다.** 조회가 깨진 것과 진짜 0건이
똑같이 보인다. 그대로 두면 매일 "신규 없음"을 보내면서 새 오류를 통째로 놓친다.

절대 시각(ISO)은 일관되게 동작했다. 같은 자리에서 확인한 단조성:

| 조건 | 건수 |
| --- | --- |
| `firstSeen:>2026-07-20T00:00:00` | 17 |
| `firstSeen:>2026-07-27T00:00:00` | 6 |
| `firstSeen:>2026-07-30T06:16:00` | 0 |

그래서 절대 시각만 쓰고, 0건일 때는 위 "0건 판정"의 대조군으로 한 번 더 확인한다.

**5. 슬랙에 보낼 때 마크다운 표는 조용히 사라진다.**
`slack_send_message`의 도구 설명은 표를 지원한다고 적고 있지만, 실제로 보내 보니
4줄짜리 표가 통째로 없어지고 빈 줄만 남았다(2026-07-31 실측, 첫 전송에서 발생).
전송은 성공으로 끝나기 때문에 **보내는 쪽에서는 실패를 알 수 없다.**

- **표를 쓰지 않는다.** 여러 항목은 `-` 목록으로 적는다(목록은 정상 전달을 확인함).
- 첫 전송 뒤에는 `slack_read_thread`로 읽어 내용이 다 들어갔는지 확인한다.

## 분류

| 묶음 | 대상 | 표시 |
| --- | --- | --- |
| 🔴 새 오류 | 신규 조회(위 "조회" 표)에 걸린 것 전부 | 제목 앞에 🔴, 자기 서비스 줄 맨 위 |
| `[ai]` | `python-fastapi` | **전부 개별** |
| `[server]` | `java-spring-boot` | **전부 개별** |
| `[web]` (그 외) | 끊김류가 아닌 웹 오류 | 개별 |
| `[web]` (끊김류) | `Failed to fetch` · `Load failed` | **한 줄로 접고 스레드에 상세** |

- **백엔드를 전부 개별로 두는 이유**: 볼륨이 원래 적고(하루 3건 수준) 사용자 수가 0이라,
  어떤 임계값을 걸어도 통째로 접힌다. 함정 3의 결과다.
- **웹 끊김류를 접는 이유**: 24시간 7건 중 4건, 7일 20건 중 11건이 이것이다. 사용자가 탭을
  닫거나 네트워크가 끊겨도 찍혀서 개별로는 고칠 게 없다.
- **접기 예외를 두지 않는다.** "사용자 N명 이상이면 펼친다" 같은 임계값은 근거 없이
  찍는 값이고, 틀리면 조용히 놓친다. 대신 **`[web]` 스레드에 이슈 종수·이벤트 수·사용자 수를
  반드시 적는다.** 임계값을 나중에 정할 때 필요한 숫자가 매일 메시지에 남는다.

### 묶기

같은 시각대에 AI → 서버 → 웹으로 이어진 것으로 보이면 한 사건으로 묶는다.
단 **요청 단위로 대조하지 않았으면 인과로 단정하지 않고** 해당 서비스 회신 끝에
"확인하지 못한 것"으로 남긴다.
매일 요청 단위 대조까지 하면 실행 시간과 비용이 커져서, 지금은 하지 않는다.

### 빼기

- `prod` / `production`이 아닌 환경
- 이미 `resolved` · `ignored` 상태

"어제 이미 올렸다"를 기억하는 장치를 두지 않는다. 하루 3건 수준이라 감당되고,
고치지 않고 두면 매일 보이는 것이 오히려 압박이 된다.

## 메시지 형식

정본은 `knk-harness/docs/templates/slack-report.md`의 🐛 템플릿이다. 다만 **클라우드 루틴에는
그 레포가 체크아웃되지 않으므로**, 이 절만 보고도 쓸 수 있게 필요한 내용을 여기 옮겨 둔다.
정본이 바뀌면 이 절도 함께 손본다.

### 정본 템플릿과 다른 점 (의도한 것이다. 되돌리지 말 것)

정본 🐛 템플릿에는 `앵커`·`재현 절차`·`요청`·`긴급도` 네 절이 있는데
**이 요약에는 넣지 않는다.**

- `앵커`는 받는 사람이 조사를 시작할 출발점(Sentry 링크, 세션 리플레이, `chat_id`,
  `레포명 + 파일:라인`, Jira 키)을 모아 두는 절이다.
- `재현 절차`는 어떤 상황에서 무엇을 하면 그 오류가 나오는지 단계로 적는 절이다.

**뺀 이유**: 정본 템플릿은 오류 하나짜리 제보용이다. 요약은 하루치 여러 건을 담으므로
앵커가 건마다 한 벌씩, 재현 절차도 건마다 한 벌씩 필요해져 본문이 읽을 수 없게 된다.
대신 **항목 제목에 Sentry 링크를 걸어 앵커 역할을 대신한다.** 링크 하나면 받는 쪽이
스택트레이스와 이벤트를 직접 조회할 수 있다.

재현 절차는 아예 만들지 않는다. 요약은 이미 난 오류를 모아 알리는 것이지 재현을 부탁하는
것이 아니고, 재현 단계를 우리가 확인하지 않은 채 적으면 지어낸 것이 된다.

`요청` 줄도 넣지 않는다(사용자 결정, 2026-07-31). 이 요약은 매일 같은 값이 찍히는
정기 보고라 그 줄이 아무것도 알려주지 않는다. 조사가 필요한 건이 있으면 그것은
따로 제보한다.

`긴급도` 줄도 넣지 않는다(사용자 결정, 2026-07-31). **Sentry 데이터로는 급한지 아닌지를
정할 수 없기 때문이다.** 정말 급한 것은 오류 때문에 사용자가 떠나는 상황인데, Sentry는
"몇 번 났고 몇 명이 겪었다"까지만 안다. 그 사람들이 떠났는지는 Amplitude에 있고 이 요약은
거기까지 보지 않는다. 기준 없이 신호등을 고르면 같은 데이터에도 매일 다른 색이 나온다
(실제로 같은 날 🟢과 🟡이 번갈아 나왔다).

대신 **사람이 급한지 판단할 재료를 준다.** `막힌 길목`과 `어제와 비교` 두 줄이 그것이다.
이탈에 가장 가까운 신호는 어느 길목이 막혔는지(`/login`이 막히면 아무도 못 들어온다)와
어제보다 갑자기 늘었는지다. 판정은 읽는 사람이 한다.

**한 건을 따로 제보할 때는 정본 템플릿을 그대로 쓴다.** 그때는 `send-slack-report` 스킬이다.

### 지켜야 할 것

- **`slack_send_message`에는 표준 마크다운으로 넣는다.** 굵게는 `**텍스트**`,
  링크는 `[표시 텍스트](URL)`, 목록은 `-`. 도구가 슬랙 문법으로 바꿔 준다
  (실측 확인: `**A**`→`*A*`, `[T](U)`→`<U|T>`, `-`→`•`, 이모지→`:bug:`).
  `slack-report.md`는 슬랙 원문 문법(`*텍스트*`·`<URL|텍스트>`)을 적고 있는데,
  그것은 슬랙 API에 직접 넣을 때의 이야기다. 이 파이프라인은 도구를 거치므로 도구 쪽을 따른다.
- **표를 쓰지 않는다**(함정 5). 여러 항목은 목록으로 적는다.
- **긴 붙임표(em dash)를 쓰지 않는다.** 쌍점이나 괄호로 나눈다.
- 메시지 끝에 `다음을 사용하여 보냄 Claude` 꼬리표가 자동으로 붙는다. 직접 적지 않는다.
- 첫 줄은 `🐛 [영역] 한 줄 요약`. 영역은 `[ai]` `[server]` `[web]` `[infra]`를 쓰고,
  요약에 여러 서비스가 걸리면 이어 붙인다(`[ai][server][web]`).
- 우리가 계산한 시각에는 타임존(KST)을 반드시 붙인다.
- 본문은 제목만, 숫자와 링크는 스레드로 나눈다(아래 "본문과 스레드를 나누는 기준").
- 사용자 입력 원문·채팅 원문·secret을 넣지 않는다.

### 서비스 표기

**`[ai]` · `[server]` · `[web]` 세 가지만 쓴다.** 세 줄은 오류가 없어도 순서를 지켜
그대로 둔다(없으면 그 아래에 `- 없음`).

- 한글로 "웹", "백엔드"라고 적지 않는다. 표기를 섞으면 같은 것을 두 이름으로 부르게 된다.
- **`백엔드 N건` 같은 중간 제목을 넣지 않는다.** ai와 server를 묶는 층이 하나 더 생겨
  읽는 사람이 세 서비스를 나란히 훑지 못한다.

### 숫자 단위

**종**은 이슈 종류 수, **건**은 발생 횟수다. 두 단위를 한 메시지에서 섞어 쓰지 않는다.
2026-07-31 시운전에서 제목의 "8건"은 이슈 종수인데 본문의 "13건"은 발생 횟수여서,
합계가 맞지 않아 보였다. 본문 제목은 **종**으로 세고, 발생 횟수는 스레드에만 적는다.

### 본문과 스레드를 나누는 기준

본문은 **무엇이 났는지 제목만** 훑게 한다. 링크·건수·마지막 시각·경로는 전부 스레드다.
본문에 숫자를 늘어놓으면 매일 같은 항목이 반복돼 아무도 안 읽는다(사용자 결정, 2026-07-31).

스레드는 **`[ai]`·`[server]`·`[web]` 세 개다.** 한 회신에 셋을 다 담으면 길어져서
자기 서비스 부분을 찾지 못한다.

**조회 방법을 적는 회신은 넣지 않는다**(사용자 결정, 2026-07-31). 받는 사람이 알아야
할 것은 무슨 오류가 났는지이지 우리가 어떻게 세었는지가 아니다. 던진 조회식과 0건
대조군 결과는 **루틴 실행 답변에만** 남긴다(슬랙에는 안 적어도 세션 기록에는 남는다).

### 본문과 회신은 오류 이름을 다르게 적는다 (의도한 것이다)

- **본문**: 무슨 일인지 알 수 있는 **쉬운 한 줄 설명**. 예: `스토리라인 응답이 스키마와 맞지 않음`
- **회신**: Sentry에 찍힌 **실제 오류 이름 그대로**.
  예: `_InvalidAiResponse: stories[0]가 응답 스키마와 맞지 않습니다.`

본문은 훑는 자리라 쉬운 말이어야 하고, 회신은 조사를 시작하는 자리라 정확한 이름이어야 한다.
회신까지 쉬운 말로 바꾸면 받는 사람이 Sentry에서 그 오류를 찾지 못한다(사용자 결정, 2026-07-31).

### 문체

**존댓말로 쓴다.** `무슨 일` 줄만 "잦았다", "있었다"처럼 반말로 나가는 일이 있었다.
한 메시지 안에서 문체가 섞이면 손으로 쓴 것과 자동으로 나간 것이 뒤섞여 보인다.

### 줄 쓰는 법

읽는 사람이 서비스별로 훑을 수 있게 **서비스 표시를 줄 하나로 세우고, 그 아래에 항목을 단다.**
한 줄에 이어 붙이면 어디가 서비스이고 어디가 내용인지 눈으로 안 갈린다.

- **긴 붙임표(em dash)를 쓰지 않는다.** 필요하면 쌍점이나 괄호로 나눈다.
- 스레드에서 제목에 링크를 건다. 링크를 줄 끝에 따로 붙이지 않는다.
- 건수 앞은 쌍점(`:`), 부가 정보는 괄호로 묶는다.
- **시각은 발생 당일 절대 시각으로 적는다**(`07-31 01:51 KST`).
  목록 조회가 주는 "13시간 전" 같은 값을 환산해서 쓰지 않는다. 그 값은 시간 단위로
  반올림돼 있어 환산하면 틀린다(실측: 환산값 02:16, 실제 01:51, 25분 차이).
  절대 시각은 **이슈 상세 조회**의 `Last Seen`에 UTC로 들어 있다. KST로 바꿔 적는다.

### 본문 골격

```
**🐛 [ai][server][web] 지난 24시간 오류 N종, 새로 생긴 것 M종**

**무슨 일**: 1~2문장. 무엇이 가장 잦은지까지
**영향**: 사용자 N명 (이슈별 합산이라 중복 가능. 고유 인원이 아니다)
**막힌 길목**: `/login` N건, `/stories/new` N건
**어제와 비교**: 총 N건에서 N건 (늘어난 것: 오류 이름 N건에서 N건)
**본 기간**: MM-DD HH:MM부터 MM-DD HH:MM까지 (KST)

`[ai]`
- 한 줄 설명
- 한 줄 설명

`[server]`
- 한 줄 설명

`[web]`
- 네트워크 끊김류 N종 (Failed to fetch, Load failed)
```

새 오류에는 제목 앞에 🔴를 붙인다. 그것 말고 본문에 숫자나 링크를 넣지 않는다.

#### `막힌 길목`

웹 오류가 난 **경로**를 건수와 함께 적는다. 경로는 이슈의 `culprit`에 들어 있다.

- 어느 길목이 막혔는지가 이탈에 가장 가까운 신호다. `/login`이 막히면 아무도 못 들어오고,
  `/stories/new`가 막히면 첫 스토리를 못 만든다.
- 웹 오류가 하나도 없으면 **이 줄을 통째로 뺀다.** `없음`이라고 적지 않는다.
- 백엔드 오류에는 이 줄을 쓰지 않는다. 경로 대신 함수 이름이 들어 있어 길목이 아니다.

#### `어제와 비교`

**어제 같은 시간대와 견준 발생 횟수**를 적는다.

- 48시간 창으로 한 번 더 조회해 얻는다(아래 "조회" 표의 `어제 대조`).
  어제 건수 = 48시간 건수에서 24시간 건수를 뺀 값이다.
- 총합이 늘었으면 **어느 오류가 늘었는지**를 괄호에 적는다. 총합만으로는 무엇이
  터졌는지 알 수 없다.
- 줄어들었거나 비슷하면 총합만 적는다.
- 48시간 조회가 실패하면 이 줄에 `어제 값을 가져오지 못했습니다`라고 적는다.
  조용히 빼면 읽는 사람이 "변화 없음"으로 읽는다.

### 스레드 골격 (회신 3개)

**회신 1 `[ai]`**, **회신 2 `[server]`**, **회신 3 `[web]`**. 앞의 둘은 같은 모양으로 쓴다.

```
**`[ai]` 상세**

- [Sentry에 찍힌 실제 오류 이름](이슈 URL): N건 (마지막 MM-DD HH:MM KST)
  어디서 무엇이 실패했는지 한두 문장. 확인한 것만 적는다.
```

웹 끊김류는 개별로 고칠 게 없으므로 한 줄씩 짧게 적고 경로를 붙인다.

```
**`[web]` 상세**

**네트워크 끊김류 N종 N건 / 사용자 N명**
- [이슈ID](URL): 제목, `경로`, N건 / 사용자 N명
```

확인하지 못한 인과관계가 있으면 해당 서비스 회신 끝에 `**확인하지 못한 것**:` 한 줄로 남긴다.

표가 아니라 목록이다(함정 5).

**던진 조회식은 루틴 실행 답변에 실제 문자열 그대로 적는다.** 어림해서 적지 않는다.
2026-07-31 첫 전송에서 실행하지 않은 시각을 적어 숫자와 짝이 어긋난 사고가 났다.
슬랙 메시지에는 조회식을 넣지 않지만, 답변에서 빠지면 그 사고를 다시 잡을 수 없다.

### 오류 0건인 날

```
**🐛 [ai][server][web] 지난 24시간 오류 없음**

**본 기간**: MM-DD HH:MM부터 MM-DD HH:MM까지 (KST)
```

회신은 달지 않는다.

침묵하지 않는 이유: 안 보내면 파이프라인이 죽은 날과 조용한 날이 구분되지 않는다.
매일 뭔가 오게 두면 끊겼을 때 사람이 알아챈다. 그래서 죽음 감시를 따로 만들지 않았다.

## 실행 환경 (클라우드 루틴)

이 스킬을 매일 돌리는 루틴의 설정값이다. 루틴 자체는 claude.ai에 있고 git에 남지 않으므로,
값이 여기 없으면 어디에도 없다. 루틴을 고치면 이 절도 함께 고친다.

| 이름 | 센트리 오류 일일 요약 (KNK-711) |

루틴 프롬프트는 **이 스킬을 읽고 그대로 수행하라**는 지시와 실패 처리만 담는다.
조회 규칙이나 메시지 형식을 프롬프트에 옮겨 적지 않는다. 두 곳에 있으면 갈라진다.

### 실행 환경에 대해 확인한 것 (KNK-732, 실제로 돌려 봄)

- **레포는 기본 브랜치(`dev`)로 받아진다.** 그래서 이 스킬이 `dev`에 머지되기 전에는
  루틴이 스킬을 찾지 못한다. 브랜치를 시험하려면 프롬프트에 `git fetch` + `git checkout`을
  넣는다. 소스 설정의 `branch` 필드는 서버가 무시했다.
- **두 레포는 형제로 받아진다.** `/home/user/manyak-ai`, `/home/user/knk-harness`.
  로컬과 같은 배치라 `.agents/skills/` 안의 하네스 심링크가 그대로 열린다
  (`create-branch/SKILL.md` 내용까지 읽힘). 하네스 제품 스펙도 접근 가능하다.
- **MCP 커넥터는 루틴을 만들 때 계정의 것이 자동으로 붙는다.** Sentry·Slack 둘 다 포함된다.
  따로 지정할 필요가 없다.
- **루틴은 API로 지울 수 없다.** 지우려면 위 설정 화면에서 한다.

### 그래도 이 문서는 자립적이어야 한다

하네스를 소스에 넣어 두긴 했지만, 루틴 설정이 바뀌면 언제든 없어질 수 있다.
`.env`나 로컬 스크립트는 애초에 없다. 그래서 조회·분류·형식 규칙은 전부 이 문서 안에 둔다.

Sentry·Slack은 claude.ai 커넥터로 붙는다. 시크릿을 파일이나 프롬프트에 적지 않는다.

### 머지 후에 할 일

1. 루틴 프롬프트에서 `git fetch origin feat/KNK-711-...`와 `git checkout ...` 두 줄을 뺀다.
   빼지 않으면 계속 그 브랜치를 읽어 `dev`의 변경이 반영되지 않는다.
2. 루틴을 켠다(`enabled: true`). 지금은 꺼져 있어 수동 실행만 된다.
3. 다음 날 오전 10시에 사람 없이 실행된 메시지가 오는지 확인한다.
