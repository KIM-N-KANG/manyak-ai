# create-jira-subtasks 참고

`SKILL.md`가 가리키는 절의 상세다. 필요한 절만 펼쳐 본다.

## §1 본인 소유 게이트 (모든 쓰기의 첫 관문)

팀이 함께 쓰는 Jira다. 설명 수정·상태 전환 등 **쓰기 전에** 대상 티켓의 `reporter`/`assignee`를
읽어, 본인이 만들었거나(reporter) 본인에게 할당된(assignee) 티켓만 건드린다.

- "본인"은 실행 계정(`/myself`)으로 해석한다 — 스킬을 돌리는 사람 자신의 티켓만 대상이다.
- 다른 팀원 소유 티켓은 자동으로 바꾸지 않고 **건너뛰며 보고**한다.
- 정말 바꿔야 하면 명시 확인을 받은 뒤에만 예외로 한다.

## §2 구조 관리

### §2-1 생성 — 작업 리스트를 Jira에 처음 반영

1. 부모의 현재 description과 기존 서브태스크를 **먼저 읽는다.** Jira가 현재 상태의 정본이라,
   "무조건 생성"이 아니라 현재 상태와의 차이만 반영한다.
2. 식별은 항목 `id`↔서브태스크 키 매핑으로 한다. **제목으로 동일성을 판단하지 않는다**
   (제목은 바뀐다). 로컬 `id`는 키를 받기 전까지만 쓰는 임시 라벨이다.
   키를 아직 받지 않은 항목만 만든다(중복 방지).
3. 매핑이 없는데(예: 새 세션) 부모에 이미 서브태스크가 있으면, 무엇이 새 항목인지 추측하지
   말고 기존 목록을 보여주고 확인받는다.
4. 신규 항목을 부모 밑 서브태스크로 만든다 — 요약은 `title`, **담당자는 부모 티켓의 담당자를 그대로**,
   초기 상태 `해야 할 일`. 만든 키를 항목 `id`와 매핑해 보고한다.
   담당자는 실행 계정을 따라가지 않는다 — 부모에서 읽어 그대로 쓴다(부모에 담당자가 없으면 물어본다).
5. **최초 추정치**를 함께 설정한다. 사용자가 값을 주면 그대로, 위임받았으면 작업 규모로
   판단한다. worklog가 아니라 timetracking 필드로 직접 설정한다.

**생성 시점에는 description을 채우지 않는다.** 작업 전에 쓴 설명은 실제 작업과 어긋나기
쉽다. 계획은 대화(planning 산출물)가 들고 있고, description은 완료 시점에 결과로 채운다(§4).
사용자가 계획을 미리 적어 달라고 명시한 경우만 예외다.

### §2-2 추가

작업 중 새로 생긴 항목 하나를 부모 밑 서브태스크로 만들고, 그 `id`↔키 매핑을 더한다.
나머지는 §2-1과 같다.

### §2-3 폐기

접는 항목은 **삭제하지 않고** `폐기` 상태로 보낸다(이력 보존).

- `해야 할 일`이면 바로 `폐기`로 전환한다.
- `진행 중`이면 직접 가는 전환이 없다 — `진행 중 → 해야 할 일 → 폐기` 2단계임을 알리고
  확인받은 뒤 실행한다.

## §3 상태 관리

전환은 상태마다 다르고 ID도 다르다. **매번 그 티켓의 현재 전환을 조회해** 목표 상태 이름으로
매칭한 전환을 실행한다. ID를 하드코딩하거나 추측하지 않는다. 목표 상태로 가는 전환이 없으면
억지로 옮기지 말고 보고한다.

워크플로 상태 이름은 메모리 `knk-jira-workflow-statuses`를 참고하되, 실제 전환은 런타임
조회로 확정한다.

### §3-1 사용자 지시로 옮기기

"KNK-000을 〈상태〉로" 요청을 처리한다. §1 게이트를 통과한 티켓만, 위 방식으로 전환한다.

**"부모 M 완료"는 일괄 전환이다** — 부모와 모든 서브태스크 중 본인 소유인 것을 `완료`로
보낸다. §5 안전장치를 적용하고, 각 티켓은 §4 결과 기록을 먼저 채운다.

### §3-2 PR 일괄 전환

`create-pr`로 부모 PR을 올린 뒤 실행한다.

1. 부모 브랜치에 PR이 실제로 있는지 확인한다.
2. 부모와 모든 서브태스크 중 본인 소유인 것을 `PR 리뷰 및 검증`으로 보낸다.
   전역 전환이라 어느 상태에서든 간다.
3. §5 안전장치를 적용한다.

## §4 완료 기록

`완료`로 전환하기 **전에** description을 작업 결과로 채운다.

### §4-1 무엇을 적나

- **서브태스크** — "결과" 섹션(날짜 포함)을 만든다. 서두는 의사 결정이 보이는 3단 서술로
  연다: **어떤 기능에 대해, 무슨 문제·요구가 있어서, 어떻게 구현했다.** 이어서 검증
  결과(실행한 명령·결과)와 산출물 링크(PR·커밋)를 사실 기반으로 적는다. 계획과 달라진 점,
  남은 후속이 있으면 반드시 명시한다.
- **부모** — 목표·배경·완료기준 개요와 결과 요약. 서브태스크 목록은 적지 않는다
  (Jira 기본 패널이 보여주므로, 적으면 드리프트만 생긴다).
- 기존 description에 내용이 있으면 지우지 않고 아래에 결과 섹션을 덧붙인다.

### §4-2 시간 기록

description을 적을 때 **할애한 시간의 합**을 worklog로 함께 남긴다. 사용자가 값을 주면
그대로, 위임받았으면 실제 진행 규모로 판단한다.

- 최초 추정치는 생성 때 설정한다(§2-1).
- 추정치 자체를 만질 때는 worklog가 아니라 timetracking 필드로 직접 설정한다.
- 완료 티켓의 남은 추정치는 0으로 정리한다.

## §5 안전장치 (팀 공용 Jira)

- 모든 쓰기는 §1 소유 게이트를 먼저 통과한다.
- 상태를 바꾸는 모든 작업은 대상과 `현재→목표`를 먼저 보여주고 확인받는다.
- 일괄 전환(부모 완료·PR)은 부모와 서브태스크 전부를 표로 보여주고 확인 후 실행한다.
  남의 소유 티켓은 "스킵(타인 소유)"로 표시한다.
- 목표 상태로 갈 전환이 없는 티켓은 강행하지 않고 보고한다.

## §6 금지 사항

- 본인이 만들지 않고 할당받지도 않은 티켓을 명시 확인 없이 수정·전환하지 않는다.
- 전환 ID를 추측하거나 하드코딩하지 않는다(런타임 조회).
- 서브태스크 동일성을 제목으로 판단하지 않는다(식별은 Jira 키).
- 목표 상태로 갈 전환이 없는데 강행하지 않는다.
- 일괄 전환을 확인 없이 실행하지 않는다.
- 티켓을 삭제(DELETE)하지 않는다 — 폐기는 상태 전환으로만 한다.
- `create-commit`·`create-pr` 등 공용 스킬을 수정하지 않는다. 키·상태만 연계하고,
  특정 도구 이름 대신 역할로 적는다.
- 부모의 기존 서브태스크를 읽지 않고 생성해 중복을 만들지 않는다.
- 부모 description에 서브태스크 목록을 적지 않는다(드리프트 방지).
- 작업 전에 description을 계획으로 미리 채우지 않는다(사용자가 명시로 요청한 경우 예외).
- 결과 기록 없이 티켓을 `완료`로 전환하지 않는다.
- Jira를 고쳐 planning 결과를 재구성하지 않는다(동기화는 `planning → Jira` 단방향).
