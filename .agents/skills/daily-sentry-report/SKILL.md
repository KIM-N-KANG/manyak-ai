# 센트리 일일 요약 (daily-sentry-report)

## 목적

지난 24시간 Sentry 오류를 세 서비스 통틀어 읽을 수 있는 한 통으로 만들어 슬랙에 올린다.
핵심은 전부 옮기는 것이 아니라 **덜 옮기는 것**이다. 그냥 나열하면 웹의 반복 오류가
백엔드 오류를 덮어 아무도 안 읽는다.

KNK-711. 규칙의 근거·결정 이력·함정은 `reference.md`에 있다.

## 같이 쓰는 파일

- `.agents/skills/daily-sentry-report/reference.md`: 조회·분류·메시지 규칙의 정본.
  **작성 전에 반드시 읽는다.** 임계값과 문구를 여기서 가져오고, 기억으로 대신하지 않는다.

## 필요한 것

- Sentry MCP (org `manyak`, 프로젝트 `python-fastapi`·`java-spring-boot`·`typescript-nextjs`)
- Slack MCP (전송 대상 채널은 `reference.md`의 "전송 대상" 절)

둘 중 하나라도 없으면 **작성하지 말고 멈춘다.** 조회를 못 한 채 "오류 없음"을 보내면
장애가 난 날에도 조용한 날로 보고하게 된다. 이 파이프라인의 가장 나쁜 실패다.

## 작업 흐름

1. `reference.md`를 읽는다. 전송 대상 채널이 미정이면 여기서 멈추고 사용자에게 묻는다.
2. **숫자를 집계 조회로 받는다.** `search_events`, dataset `errors`,
   query `environment:[prod, production]`, fields `issue`·`count()`·`count_unique(user)`·
   `max(timestamp)`, period `24h`. 발생 횟수·영향 인원·마지막 시각이 한 번에 나온다.
   - **이슈 상세를 열지 않는다.** 상세에는 프롬프트 원문·지역변수·식별자가 들어 있고,
     슬랙에 안 옮겨도 루틴 실행 기록에 남는다(`reference.md` "숫자는 집계 조회로만 받는다").
3. **제목과 링크를 목록 조회로 받는다.** `search_issues`,
   query `is:unresolved environment:[prod, production]`, 창 24시간, 3개 프로젝트.
   여기서 `culprit`(경로)도 받는다.
4. **새 오류**를 따로 조회한다. 3번 쿼리에 `firstSeen:>{24시간 전 UTC ISO}`를 더한다.
   - 응답의 `First seen` 표시값으로 판단하지 않는다(조회 창에 따라 값이 달라진다. 함정 1).
   - `-24h` 같은 상대 기간을 쓰지 않는다. 조용히 0건을 내거나 400으로 죽는다(함정 4).
   - **0건이면 그대로 0건이다.** 조회 실패인지 아닌지는 도구 호출의 성패로만 가른다.
     호출이 죽었으면 "조회 실패"를 보내고, 성공했는데 비었으면 "새로 생긴 것 없음"이다
     (`reference.md` "0건 판정"). 확인용 대조군 조회를 따로 던지지 않는다.
5. `reference.md`의 분류 규칙으로 묶는다. 백엔드는 전부 개별, 웹 끊김류는 한 줄로 접는다.
6. 본문과 스레드를 나눠 작성한다. 형식은 `reference.md`의 "메시지 형식".
   - **본문에는 제목만 적는다.** `[ai]`·`[server]`·`[web]` 세 줄을 세우고 그 아래에
     한 줄 설명만 단다. 링크·건수·마지막 시각은 전부 스레드다.
   - **`오류 난 화면` 줄은 웹 오류가 있을 때만 넣는다.** 웹 오류가 없으면 줄을 통째로 뺀다.
     백엔드는 경로 대신 함수 이름이라 화면이 아니다.
   - 급한지 아닌지는 읽는 사람이 판단한다. 신호등(긴급도)을 대신 골라 주지 않는다.
   - **스레드는 회신 3개다.** `[ai]` 상세, `[server]` 상세, `[web]` 상세.
     한 회신에 몰아 담지 않는다. 조회 방법을 적는 회신은 넣지 않는다.
   - 링크는 **조회 결과에서 복사한 URL만** 쓴다. 패턴을 조합해 만들지 않는다.
   - 확인하지 못한 인과관계는 단정하지 않고 "확인하지 못한 것"으로 남긴다.
7. 보낸다. 본문 전송 후, 응답의 `ts`를 `thread_ts`로 써서 회신을 잇는다.
   - **세 서비스 다 오류가 0건인 날에는 본문 한 문장만 보내고 회신을 달지 않는다.**
   - **하나라도 오류가 있으면 회신 3개를 다 단다.** 오류가 없는 서비스도 회신을 달고
     "오류 없음"이라고 적는다. 회신 수가 매일 같아야 받는 쪽이 같은 자리에서 찾는다.
   - **사람이 대화 중에 부른 경우**: 전송 전에 메시지 전문을 보여 주고 확인을 받는다.
   - **클라우드 루틴이 부른 경우**: 확인 없이 보낸다. 물어볼 사람이 없다.
8. **보낸 것을 다시 읽어 확인한다.** `slack_read_thread`로 본문과 **자기가 보낸 회신**을 읽고,
   빠진 내용이 없는지 본다. 개수는 7번에서 실제로 보낸 수와 맞으면 된다. 오류 0건인 날에
   회신이 없는 것은 정상이므로 다시 보내지 않는다. 전송은 성공으로 끝나도 내용 일부가
   조용히 삭제될 수 있다(표가 그렇다. `reference.md` 함정 5). 빠졌으면 그 부분만 다시 보낸다.
9. 보낸 채널과 메시지 링크를 보고한다.

## 오류가 0건인 날

침묵하지 않는다. "지난 24시간 오류 없음" 한 줄을 보낸다.
보내지 않으면 파이프라인이 죽은 날과 조용한 날을 구분할 수 없다(사용자 결정).

## 금지 사항

- **조회에 실패하면 요약을 보내지 않는다.** 2번(집계)·3번(목록)·4번(새 오류) 셋 다 필수다.
  하나라도 실패하면 오늘 무슨 오류가 났는지 온전히 알 수 없으므로, 요약 대신 조회가
  실패했다는 사실을 보낸다. 실패한 조회가 무엇인지 함께 적는다.
- **이슈 상세를 열지 않는다.** 상세에는 프롬프트 원문·지역변수·`device_id_hash`가 들어 있고,
  슬랙에 옮기지 않아도 루틴 실행 기록에 남는다. 필요한 숫자는 집계 조회로 다 나온다.
- 확인하지 못한 원인·연결을 사실처럼 적지 않는다.
- 이슈 URL을 패턴 조합으로 만들지 않는다.
- 사용자 입력 원문·채팅 원문·secret을 싣지 않는다. 식별자로 대신한다.
- 이슈 상태를 바꾸지 않는다(resolve·ignore·assign). 이 스킬은 읽고 보내기만 한다.
- `reference.md`의 임계값을 그 자리에서 바꾸지 않는다. 바꿀 일이 보이면 보고만 한다.

## 완료 보고

  여기서 빠지면 숫자가 맞는지 나중에 확인할 방법이 없다.
- 몇 건을 몇 줄로 줄였는지.
- 접거나 뺀 것이 있으면 무엇을 뺐는지. 조용히 줄이지 않는다.
- 조회하지 못한 프로젝트가 있으면 명시한다.
