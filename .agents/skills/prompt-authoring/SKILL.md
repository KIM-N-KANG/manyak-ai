# 프롬프트 제작·보완

## 목적

프롬프트를 새로 만들거나(제작) 고칠 때(보완), 모델에 상관없이 통하는 설계 원칙을 일관되게 적용해 품질을 안정시킨다. 판단 기준은 아래 **설계 원칙** 한 곳에 모여 있고, 제작·보완 두 흐름이 그것을 공유한다.

**트레이드오프:** 품질을 위해 약간의 신중함을 택한다. 사소한 한 줄 수정에는 판단껏 가볍게 간다.

## 시작: 무엇을 할지 정한다

먼저 짧게 파악한다 — **작업 목표, 대상 모델, 기대 출력**.

**제작이냐 보완이냐 (라우터):**

- 기존 프롬프트가 주어지면 → **보완 흐름**으로 간다(①부터).
- 새로 만드는 거면 → **제작 흐름**.
- "이 프롬프트 좋게 만들어줘"처럼 모호하면 보완으로 보되, '좋게/개선'이 무엇을 뜻하는지
  추측하지 말고 **먼저 물어본다**(= 보완 ①). 모호함을 푸는 자리가 바로 거기다.

## 제작 흐름

1. **요구 명세화** — 이 프롬프트가 무슨 일을 해야 하는지, 무엇이 성공인지 적는다.
2. **역할·맥락·출력 형식 결정** — 모델에게 줄 역할과 배경, 받고 싶은 출력 형식을 먼저 정한다.
3. **구조 잡기** — 지시 / 맥락 / 예시 / 출력 형식의 자리를 나눈다.
4. **초안 작성** — 아래 **설계 원칙**을 적용해 쓴다.
5. **자기 점검** — 아래 **자기 점검** 체크리스트로 마무리한다.

## 보완 흐름

1. **보완 이유 파악** — 무슨 문제를 푸는 수정인지 분류한다(버그 / 품질 / 명확성 / 출력 형식 등).
   이유가 모호하면 고치기 전에 먼저 확인한다.
2. **원 프롬프트의 의도 파악** — 원래 무엇을 하던 프롬프트인지 먼저 이해한다.
   - *왜 먼저?* "출력이 너무 길다"는 피드백이라도 원 의도가 "교육용 상세 설명"이면, 의도를
     모른 채 무작정 줄이는 건 오히려 새 버그가 된다.
3. **진단** — 모순·모호·죽은 무게(불필요한 지시)를 찾는다.
4. **원칙 위반 지점 특정** — 어느 설계 원칙을 어긴 결과인지 짚는다.
5. **최소 범위 수정** — 원 의도·동작은 유지하고, **확인된 문제만** 고친다. 무관한 개선을 끼워넣지 않는다.
6. **예시 대조** — 수정본을 예시 / 기대 출력과 다시 맞춰본다.
7. **자기 점검** — 아래 **자기 점검** 체크리스트로 마무리한다.

## 설계 원칙

모델에 상관없이 통하는 기준이다. 제작·보완 모두 이 한 곳을 참조한다(흐름에서 재서술하지 않는다).
각 원칙에는 *왜*가 붙는다 — 근거를 알면 적히지 않은 경우에도 의도대로 일반화하기 때문이다.

1. **정의와 예시를 일치시킨다.** 규칙을 말하고 든 예시가 그 규칙을 어기면, 모델은 둘 중 하나(보통
   더 구체적인 예시)를 따르고 규칙은 무력화된다.
   - Before — 규칙 "한 문장으로 간결히" + 예시 답 "안녕하세요! 무엇을 도와드릴까요? 오늘 기분은…"(3문장)
   - After — 예시 답을 "환불은 7일 이내 가능합니다." 한 문장으로. 규칙과 예시가 같은 것을 가리킨다.
2. **단일 진실 공급원.** 같은 규칙을 여러 곳에 흩뿌리지 않는다. 한 곳에서 정의하고 나머지는
   참조한다 — 흩뿌리면 한쪽만 고쳐져 모순이 생긴다.
3. **명확·구체.** "적절히", "잘" 같은 모호어를 버리고 검증 가능한 기준을 준다("3문장 이내", "JSON만").
4. **'왜'를 함께 준다.** 근거가 있으면 모델이 규칙을 외운 게 아니라 이해해, 경계 밖 상황에도 의도대로 행동한다.
5. **금지보다 대체 행동을 준다.** "하지 마라"만 있으면 무엇을 해야 할지 모른다.
   - Before — "사과하지 마라."
   - After — "사과 대신 곧바로 해결책을 제시하라."
6. **출력 형식을 명시한다.** 원하는 구조를 그대로 보여준다 — 형식이 없으면 출력이 매번 달라진다.
   - Before — "결과를 정리해줘."
   - After — "다음 형식으로만 답하라:  `제목: <한 줄>` / `요약: <세 줄>` / `다음 행동: <불릿 3개>`"
7. **예시는 원하는 출력과 똑같이 생기게 한다.** few-shot 예시의 형식·톤·길이가 곧 모델이 따라할
   본보기다. (1과 구분: 1은 규칙↔예시의 모순, 7은 예시↔목표 출력의 형태 일치)
8. **과잉 제약을 피한다.** 모든 줄에 MUST/ALWAYS를 붙이면 정작 중요한 게 묻힌다. 정말 중요한 것만 강조한다.
9. **용어를 일관되게 쓴다.** 같은 개념을 "유저/사용자/플레이어"로 번갈아 부르면 모델이 다른
   것으로 오해할 수 있다.
10. **간결하게.** 군더더기·죽은 지시는 토큰을 쓰고 주의를 흩는다. 안 쓰이는 지시는 지운다.
11. **구조와 배치.** 구분자·섹션으로 나누고, 가장 중요한 지시는 눈에 띄는 위치(맨 앞 또는 맨 끝)에 둔다.
12. **역할·맥락과 실패 처리.** 모델에게 역할·목적·대상 독자를 주고, 빈 입력·모호·범위 밖 같은
    엣지 케이스에서 어떻게 행동할지 정해 둔다.

## 자기 점검 (완료 전)

위 **설계 원칙**에서 뽑은 빠른 통과용 요약이다(기준의 출처는 설계 원칙이며, 여기는 게이트일 뿐).
모두 YES여야 통과한다.

- [ ] 정의와 예시가 일치하는가?
- [ ] 같은 개념에 같은 용어를 일관되게 썼는가?
- [ ] 모호어 없이 기대 동작이 구체적인가?
- [ ] 불필요한 MUST/ALWAYS 없이 핵심만 강조했는가?
- [ ] 기대 출력 형식이 명시돼 있는가?
- [ ] (보완) 원 의도·동작을 유지하고 확인된 문제만 최소 범위로 고쳤는가?
- [ ] (보완) 이 수정이 보완 이유를 실제로 해결하는가?

## 이 레포(manyak)에서 쓸 때

manyak `prompt/` 작업의 고유 규칙(레이어 책임 분리·frontmatter·LF 줄바꿈·버전 저장 등)은
`CLAUDE.md`와 `spec/`를 따른다. 수정한 프롬프트의 동작은 유닛 테스트로 검증되지 않는다 —
실측 검증(로컬 `scripts/` 스크립트·`experiment/` 러너, 과금이라 승인 선행)은 `CLAUDE.md`의
"실측·실험" 절을 따르고, 실측하지 않았으면 보고에 "실측 미실시"를 명시한다.
