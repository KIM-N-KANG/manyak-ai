# sync-ai-spec 참고

`SKILL.md`가 가리키는 절의 상세다. 필요한 절만 펼쳐 본다.

## §1 층 판단 — 이 스킬의 핵심

문서는 코드 설명서가 아니다. 모든 주요 단위가 **무엇(What) → 왜(Why) → 어떻게(How) →
왜 그 방법(Why this way)** 순서로 서술되고, 핵심 설계 결정은 §5-2 카탈로그(D1~Dn)에서
**한 번만** 서술된다. 그래서 동기화는 "코드가 바뀌었으니 구현 표를 고친다"가 아니라
**이 변경이 어느 층을 건드리는지**에서 시작한다. 방법을 갈아탄 변경을 값 표 수정으로
처리하면 문서의 근거 서술이 거짓이 된다.

판단 입력은 diff만이 아니다 — **커밋 메시지·PR 본문·manyak-ai `spec/` 파일의 동반 변경**('왜'가 적힌 곳)을
함께 읽는다. 변경 단위마다 네 질문을 순서대로 묻는다.

1. **무엇이 바뀌었나?** 다루는 문제 자체가 달라졌다(기능 추가·제거, MVP 범위 변경, 서비스 역할 변화).
   → 무엇 층부터 다시 쓰고 그 아래 셋을 연쇄 재검토한다.
   문서 전반에 파급되는 규모면 단독으로 갱신하지 말고 사용자에게 상위 판단(문서 구조 개편 여부)을 묻는다.
2. **왜가 바뀌었나?** 문제는 그대로인데 그것이 문제인 이유나 심각도가 달라졌다(실측으로 원인이
   다른 것으로 밝혀짐, 빈도·영향 범위 재산정). → 왜 층을 고치고, 그 근거에 기대던 아래 둘을 재검토한다.
   원인을 잘못 짚고 있었다면 방법도 함께 흔들린다.
3. **어떻게가 바뀌었나?** 문제도 이유도 그대로고 계약 필드·파라미터 값·내부 구조만 바뀌었다.
   → 해당 §의 어떻게 층(표·스키마·서술)만 최소 수정한다.
4. **왜 그 방법이 바뀌었나?** 같은 문제를 **다른 방법으로 갈아탔다**(모델·공급자 교체, stateless 포기,
   선택지 정책 변경 등). manyak-ai `spec/` 파일이 함께 바뀌었다면 강한 신호다.
   → §5-2 카탈로그를 §2 규칙대로 갱신하고, **버린 안과 버린 이유를 남긴다.** 그 결정을 참조하는
   섹션들의 어떻게 층을 연쇄 갱신한다.

| 변경 | 층 | 처리 |
| --- | --- | --- |
| temperature 0.75 → 0.8 (실측 근거 커밋) | 어떻게 | §5-4-3 값 표만 갱신 (D9는 그대로) |
| 선택지를 본문 스트림에 재통합 | 왜 그 방법 | D6 `폐기` 전환 + 대체 사유, §5-3-4·§5-3-5 연쇄 갱신 |
| 요약(summary) 생성 기능 AI 이관 | 무엇 + 왜 그 방법 | §5-3-4 무엇 층·Phase 라벨부터 재검토, 필요 시 새 D 등록 검토 |
| 응답 meta에 필드 1개 추가 | 어떻게 | §5-6 meta 표 갱신 (D10은 그대로) |
| 502 원인이 출력 잘림이 아니라 JSON 이스케이프 누락으로 밝혀짐 | 왜 | 원인 서술을 고치고, 그 원인에 맞춰 잡았던 방법이 아직 맞는지 재검토 |

**애매할 때 '어떻게'로 단정하는 것이 가장 흔한 오류다.** 근거가 부족하면 사용자에게 묻는다.

**없던 '왜 그 방법'을 지어내지 않는다.** 4층은 대안 비교를 요구하지만, 당시 실제로 견준 안이
없었다면 없었다고 적는다. 있지도 않았던 비교를 채워 넣는 것은 이 층이 막으려는 바로 그 일이다.

## §2 D 카탈로그 관리 규칙

규칙의 정본은 문서 §5-2다. 요지는 셋이다.

- 새 결정은 **등록 기준(장기적·구조적·다수 파급)을 통과할 때만** D(n+1)로 추가한다. **번호 재사용 금지.**
- 기준 미달이면 D로 올리지 않고 해당 섹션 '어떻게' 층 갱신으로 격하한다.
- 뒤집힌 결정은 **삭제하지 않고** `폐기` 상태로 전환하고 대체 사유를 남긴다.

## §3 결정·섹션 매핑과 갱신 제안

층 판단 결과를 문서 좌표로 옮긴다 — 영향받는 결정 ID(D1~Dn)와 섹션(§5-2~§5-7)의 **교차점만** 대상으로
잡는다. §5-7 어긋난 곳 표(A*)에 영향이 있으면(어긋남 해소·새 항목) 함께 넣는다.

수정 전에 이 형식으로 확인받는다.

> "다음 갱신을 제안합니다:
> - [커밋/PR] → 층: {무엇/왜/어떻게/왜 그 방법} → 대상: {D번호, §번호}
> - 요지: {한 줄}
>
> 진행할까요?"

문서를 고칠 때는 4층 서술 순서(계약 표는 '어떻게' 층에만), §5-2 단일 서술(타 섹션은 ID 참조),
0-glossary 용어, 기존 문체(존댓말)를 유지한다. 파일은 LF로 저장한다(knk-harness 문서 규약).

### 압축된 말 금지

**일상에서 안 쓰는 짧은 한자말로 뜻을 뭉뚱그리지 않는다.** 쓰는 사람은 한 단어로 줄여 편하지만,
읽는 사람은 그 단어가 정확히 무엇을 가리키는지 매번 되짚어야 한다. 짧아진 만큼 읽는 쪽이
비용을 치르는 거래이고, 스펙 문서에서는 그 거래가 손해다.

| 쓰지 않는다 | 대신 쓴다 |
| --- | --- |
| 축 | 기준, 방향, 갈래 (무엇을 가르는 기준인지 밝혀 쓴다) |
| 배선 | 연결, 이어 붙임, 호출 연결 |
| 동률 | 같은 값, 나란함, 개수가 같음 |
| 게이트 | 확인 단계, 통과 조건, 승인 |
| 길목 | 거쳐 가는 자리, 통로 |
| 간극 | 어긋남, 차이, 벌어진 곳 |
| 변이 | 달라진 것, 바뀐 형태 |

**목록은 예시이지 전부가 아니다.** 판단 기준은 하나다 — **더 흔한 말이 있는데 굳이 짧은 말을
골랐다면 쓰지 않는다.** 새로 걸리는 말을 발견하면 이 표에 더한다.

이 규칙은 문서 본문, 표 항목, 커밋 메시지, PR 본문, 사용자 보고에 모두 적용된다.
비유로 풀어쓰는 것도 답이 아니다 — 원래 개념 위에 설명을 한 겹 더 씌워 오히려 어려워진다.
그 일이 실제로 어떻게 벌어지는지를 짧은 문장으로 적는다.

마지막에 메타 표를 갱신한다 — 기준 코드 SHA(스크립트가 출력한 12자리), 작성일, 버전(내용 변경 시 +0.1).

## §4 감지 스크립트 종료코드와 대응

| 코드 | 뜻 | 대응 |
|---|---|---|
| 0 | 변경 없음 | "기준 SHA 이후 스펙 영향 경로의 변경이 없습니다. 스펙은 최신입니다."로 보고하고 종료 |
| 10 | 감시 경로 안에 변경 있음 | 커밋(또는 머지 PR) 단위로 묶어 §1 층 판단으로 |
| 11 | 감시 경로 밖 변경만 있음 | 끝내지 말고 그 커밋 메시지를 읽는다. 설계 변경을 시사하면 §1로, 아니면 "스펙 최신"으로 보고 |
| 1 | 조회 자체가 실패 | 스펙 파일 없음(→ "knk-harness 경로를 확인해주세요", 형제 레포가 함께 체크아웃돼야 한다) / git 레포 밖에서 실행 / `origin/dev` 조회 실패 / `git log` 실패. **어느 쪽이든 "변경 없음"이 아니다** |
| 3 | 앵커 SHA 없음 | 앵커가 없으면 감지가 불가능하다. 사용자에게 기준 시점을 물어 SHA를 확정하고, 갱신할 때 메타 표에 앵커 행을 복구한다 |
| 4 | 기준 SHA가 로컬에 없음 | force push 등으로 사라진 경우다. 사용자에게 보고한다 |
| 5 | git fetch 실패 | 낡은 `origin/dev`로 비교하면 드리프트를 놓치므로 중단한다. 네트워크·권한을 확인하고 다시 실행 |
| 2 | 사용법 오류 | 이 스크립트는 인자를 받지 않는다 |

**0이 아닌 코드를 "스펙 최신"으로 바꿔 보고하지 않는다.** 이 스킬이 막으려는 사고가 정확히 그것이다.

스크립트가 두 목록을 낸다. **감시 경로 안**이 층 판단 대상이고, **감시 경로를 전혀 건드리지 않은**
목록은 참고다 — 원칙은 스펙 무영향이지만 커밋 메시지가 설계 변경을 시사하면 예외로 포함한다.
안팎을 함께 건드린 커밋은 첫 목록에서 이미 다루므로 둘째 목록에서 빠진다.

감시 경로 목록은 스크립트 안에 있다. 늘리거나 줄일 일이 생기면 문서가 아니라 스크립트를 고친다.

## §5 커밋·PR 절차

knk-harness는 별도 레포다. 문서 갱신 커밋·PR은 팀 공용 스킬로 진행하고, 각 단계는 사용자 확인을
거친다. 공용 스킬(`create-branch`·`create-commit`·`create-pr`)은 **호출만 하고 수정하지 않는다.**

1. knk-harness에서 `dev` 최신화(pull)를 **먼저** 하고 `docs/KNK-xxx-...` 브랜치를 분기한다
   (묵은 dev에서 갈라지지 않게 분기 전 pull이 필수다).
2. `create-commit`으로 커밋한다 — 커밋 키는 이 동기화 작업의 Jira **서브태스크** 키를 쓴다.
   브랜치·PR 제목은 부모 키를 따른다(`pr-title-follows-branch` 컨벤션).
3. `create-pr`로 Draft PR을 올린다(브랜치 push는 이 스킬이 함께 한다).
   PR 본문에 동기화 요약(변경 단위 → 층 → 수정 섹션)을 넣는다.

## §6 금지 사항

- `5-ai-server.md` 외의 어떤 파일도 수정하지 않는다(knk-harness의 타 문서 포함).
  0-glossary·3-frontend·4-backend·6-analytics·7-deployment는 각자 소유자가 있다.
  불일치를 발견하면 고치지 말고 보고만 한다.
- 사용자 확인 없이 문서를 수정하거나 커밋·PR을 만들지 않는다.
- D 번호를 재사용하거나 폐기된 D를 삭제하지 않는다.
- 층 판단을 건너뛰고 구현 표부터 고치지 않는다.
- 변경과 무관한 섹션을 재작성하지 않는다. 문체 통일·개선 욕심으로 무관한 문장을 고치지 않는다.
- 어긋난 곳 표(A*)의 항목을 근거 없이 지우지 않는다 — 해소된 항목은 해소 근거(커밋·PR)와 함께 정리한다.
- 커밋·PR을 직접 만들지 않는다 — 공용 스킬로 진행하고, 그 스킬을 수정하지 않는다.
