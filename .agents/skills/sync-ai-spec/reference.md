# sync-ai-spec 참고

`SKILL.md`가 가리키는 절의 상세다. 필요한 절만 펼쳐 본다.

## §1 변경 분류 — Spec·Design·ADR의 책임

문서가 세 역할로 나뉘므로 동기화는 "코드가 바뀌었으니 스펙 표를 고친다"가 아니라 **이 변경이 결정을
건드리는지**에서 시작한다. 판단 입력은 diff만이 아니다 — **커밋 메시지·PR 본문·manyak-ai
`spec/` 파일의 동반 변경**('왜'가 적힌 곳)을 함께 읽는다. 변경 단위마다 아래 순서로 묻는다.

1. **값·계약만 바뀌었나?** 문제도 이유도 방법도 그대로고 계약 필드·파라미터 값·내부 구조·실패 처리
   세부만 바뀌었다. → 승인된 외부 계약은 **Spec**, 현재 내부 구조·설정은 **Design**을 고친다. 코드 차이만으로 계약을 승인하지 않는다. ADR은 손대지 않는다.
2. **다른 방법으로 갈아탔나?** 같은 문제를 다른 방법으로 풀기 시작했다(모델·공급자 교체, stateless 포기,
   선택지 정책 변경 등). manyak-ai `spec/` 파일이 함께 바뀌었다면 강한 신호다.
   → **ADR부터** 쓴다. 확정된 기존 본문을 보존하고 새 결정을 4층으로 적는다. 새 기록에 대체하는 ID·범위·이유를
   남긴다(§2). 그다음 Spec·Design의 해당 절에 각 역할의 결과를 반영한다.
3. **왜가 바뀌었나?** 방법은 그대로인데 그것이 문제인 이유나 심각도가 달라졌다(실측으로 원인이
   다른 것으로 밝혀짐, 빈도·영향 범위 재산정). → **ADR**에 바뀐 근거를 새 기록으로 남기고, 그 근거에 기대던 방법이
   아직 맞는지 재검토한다. 스펙은 결과가 바뀔 때만 고친다.
4. **다루는 문제 자체가 바뀌었나?** 기능 추가·제거, MVP 범위 변경, 서비스 역할 변화.
   → **ADR**에 새 결정(또는 기능별 결정 기록)을 4층으로 적고, 스펙에 새 절·표를 더한다.
   문서 전반에 파급되는 규모면 단독으로 갱신하지 말고 사용자에게 상위 판단(문서 구조 개편 여부)을 묻는다.

| 변경 | 분류 | 처리 |
| --- | --- | --- |
| temperature 0.75 → 0.8 (실측 근거 커밋) | 값 | Design §3-2 표만 갱신. ADR D9는 그대로 |
| 응답 meta에 필드 1개 추가 | 계약 | 스펙 §5-6·§5-9 갱신. ADR D10은 그대로 |
| 선택지를 본문 스트림에 재통합 | 방법 교체 | ADR D6 본문 보존 + 새 결정에 대체 ID·사유 4층. 스펙 §5-3-4·§5-3-5·§5-9 덮어쓰기 |
| 502 원인이 출력 잘림이 아니라 JSON 이스케이프 누락으로 밝혀짐 | 왜 | ADR에 정정 근거를 새 기록으로 남기고 방법 재검토. 스펙은 처리 결과가 바뀔 때만 |
| 요약(summary) 생성 기능 AI 이관 | 문제 변경 | ADR에 새 결정 4층. 스펙 §5-3-4·§5-9에 새 계약 |

**애매할 때 "값만 바뀜"으로 단정하는 것이 가장 흔한 오류다.** 근거가 부족하면 사용자에게 묻는다.

**없던 '왜 그 방법'을 지어내지 않는다.** 4층은 대안 비교를 요구하지만, 당시 실제로 견준 안이
없었다면 없었다고 적는다. 있지도 않았던 비교를 채워 넣는 것은 이 층이 막으려는 바로 그 일이다.

## §2 ADR 쓰는 법 — 4층 서술과 D 카탈로그

ADR의 모든 항목은 **무엇(What) → 왜(Why) → 어떻게(How) → 왜 그 방법(Why this way)** 순서로 쓴다.
무엇이 문제였는지, 그것이 왜 문제였는지, 어떻게 바꿨는지, 다른 방법도 있었는데 왜 이 방법인지.
구현 상세는 결정의 결과로만 등장하고, 현재 계약은 Spec, 내부 설정 값은 Design으로 연결한다(ADR에 값 표를 복제하지 않는다).

ADR은 세 부류로 나뉜다. 어디에 쓸지는 ADR 문서의 "카탈로그 관리 규칙"이 정본이고, 요지는 다음과 같다.

- **설계 결정 카탈로그(D1~Dn)** — 장기적·구조적이고 여러 기능·레포에 파급되는 결정. 새 결정은
  등록 기준을 통과할 때만 D(n+1)로 추가한다. **번호 재사용 금지.** 뒤집힌 결정은 **삭제하지 않고**
  확정 본문을 보존하고 새 결정에서 대체 ID·범위·이유를 연결한다.
- **기능별 결정 기록** — D 기준에는 못 미치지만 근거를 남길 가치가 있는 기능 단위 선택. 문제·선택과
  이유·대안과 대가 순서의 bullet로 쓴다.
- **기존 제약과 후속 판단 이력(A1~A22)** — 분리 전 문서의 추적 기록. 새 제약은 여기가 아니라 스펙
  §5-7 "현재 제약" 문단에 요약하고, 해소되면 스펙에서 지우고 ADR의 해당 A 행에 해소 근거(커밋·PR)를 적는다.

## §3 갱신 제안과 문체

변경 분류 결과를 문서 좌표로 옮긴다 — Spec은 절 번호(§5-1~§5-9), Design은 절 번호(§3-1~§3-4), ADR은 D 번호·기능별 결정 기록의
절 제목·A 번호로 가리킨다. 수정 전에 이 형식으로 확인받는다.

> "다음 갱신을 제안합니다:
> - [커밋/PR] → 분류: {값·계약 / 방법 교체 / 왜 / 문제 변경}
>   → Spec: {§번호 또는 없음} / Design: {§번호 또는 없음} / ADR: {D번호·절 제목·A번호 또는 없음}
> - 요지: {한 줄}
>
> 진행할까요?"

**Spec을 고칠 때**: 승인된 계약만 남긴다. "이전에는", "…에서 …로 바꿨다", "…계획"처럼 시간이 들어간
문장은 쓰지 않고, 이미 있으면 지운다. 표·그림·요청/응답 예시(§5-9)가 바뀐 계약과 맞는지 함께 본다.
근거가 궁금할 자리에는 ADR 항목 링크 한 줄만 둔다.

**Design을 고칠 때**: 검증된 현재 구조·설정과 실패·복구를 적는다. 계약과 결정 이유는 각 정본으로 연결한다.

**ADR을 고칠 때**: 4층 순서를 지키고 확정 본문은 보존한다. 변경 결정에 대체 ID·범위를 남기고 현재 계약·구조는 Spec·Design 링크로 가리킨다.

공통: 0-glossary 용어, 기존 문체(존댓말), LF 저장(knk-harness 문서 규약)을 유지한다.

### 압축된 말 금지

**일상에서 안 쓰는 짧은 한자말로 뜻을 뭉뚱그리지 않는다.** 쓰는 사람은 한 단어로 줄여 편하지만,
읽는 사람은 그 단어가 정확히 무엇을 가리키는지 매번 되짚어야 한다. 짧아진 만큼 읽는 쪽이
비용을 치르는 거래이고, 스펙 문서에서는 그 거래가 손해다.

| 쓰지 않는다 | 대신 쓴다 |
| --- | --- |
| 축 | 기준, 방향, 갈래 (무엇을 가르는 기준인지 밝혀 쓴다) |
| 배선 | 연결, 이어 붙임, 호출 연결 |
| 동률 | 같은 값, 나란함, 개수가 같음 |
| 게이트 | 확인 단계, 통과 조건, 승인 |
| 길목 | 거쳐 가는 자리, 통로 |
| 간극 | 어긋남, 차이, 벌어진 곳 |
| 변이 | 달라진 것, 바뀐 형태 |

**목록은 예시이지 전부가 아니다.** 판단 기준은 하나다 — **더 흔한 말이 있는데 굳이 짧은 말을
골랐다면 쓰지 않는다.** 새로 걸리는 말을 발견하면 이 표에 더한다.

이 규칙은 문서 본문, 표 항목, 커밋 메시지, PR 본문, 사용자 보고에 모두 적용된다.
비유로 풀어쓰는 것도 답이 아니다 — 원래 개념 위에 설명을 한 겹 더 씌워 오히려 어려워진다.
그 일이 실제로 어떻게 벌어지는지를 짧은 문장으로 적는다.

### 메타 갱신

- Spec의 문서 정보 표 `기준 코드` 행에 스크립트가 출력한 12자리 SHA를 쓴다. "브랜치 `SHA`" 형식은 감지 스크립트가 읽으므로 유지한다.
- 수정한 문서의 문서 정보 표 `버전`(내용 변경 시 +0.01)과 `수정일`(오늘)을 갱신한다. Design은 Spec의 기준 코드를 참조한다.
- H1은 파일명과 맞추고, 문서 정보 → 읽는 순서 → 실제 본문과 일치하는 목차 순서를 유지한다.
  문서 정보 표의 첫 행은 버전·작성일·수정일·대상·작성 목적 순서다. YAML frontmatter를 추가하지 않는다.
- ADR의 문서 작성일·수정일은 개별 결정일과 구분하며 기존 결정 ID·본문을 보존한다.

## §4 감지 스크립트 종료코드와 대응

| 코드 | 뜻 | 대응 |
|---|---|---|
| 0 | 변경 없음 | "기준 SHA 이후 변경이 없습니다. 문서 본문과 코드의 일치 여부는 별도 검토가 필요합니다."로 보고하고 종료 |
| 10 | 감시 경로 안에 변경 있음 | 커밋(또는 머지 PR) 단위로 묶어 §1 변경 분류로 |
| 11 | 감시 경로 밖 변경만 있음 | 끝내지 말고 그 커밋 메시지를 읽는다. 설계 변경을 시사하면 §1로, 아니면 "문서 반영 대상 변경 없음"으로 보고 |
| 1 | 조회 자체가 실패 | Spec·Design·ADR 중 파일 없음(→ "knk-harness 경로를 확인해주세요", 형제 레포가 함께 체크아웃돼야 한다) / git 레포 밖에서 실행 / `origin/dev` 조회 실패 / `git log` 실패. **어느 쪽이든 "변경 없음"이 아니다** |
| 3 | 기준 코드 SHA 없음 | 메타 표에 `기준 코드` 행이 없거나 "브랜치 \`SHA\`" 꼴이 아니다. 사용자에게 기준 시점을 물어 SHA를 확정하고, 갱신할 때 그 꼴로 행을 복구한다 |
| 4 | 기준 SHA가 로컬에 없음 | force push 등으로 사라진 경우다. 사용자에게 보고한다 |
| 5 | git fetch 실패 | 낡은 `origin/dev`로 비교하면 드리프트를 놓치므로 중단한다. 네트워크·권한을 확인하고 다시 실행 |
| 2 | 사용법 오류 | 이 스크립트는 인자를 받지 않는다 |

**0이 아닌 코드를 "스펙 최신"으로 바꿔 보고하지 않는다.** 이 스킬이 막으려는 사고가 정확히 그것이다.

스크립트가 두 목록을 낸다. **감시 경로 안**이 분류 대상이고, **감시 경로를 전혀 건드리지 않은**
목록은 참고다 — 원칙은 스펙 무영향이지만 커밋 메시지가 설계 변경을 시사하면 예외로 포함한다.
안팎을 함께 건드린 커밋은 첫 목록에서 이미 다루므로 둘째 목록에서 빠진다.

감시 경로 목록은 스크립트 안에 있다. 늘리거나 줄일 일이 생기면 문서가 아니라 스크립트를 고친다.

## §5 티켓·커밋·PR 절차

**스펙 반영 티켓.** 작업 티켓과 별도로, Phase별 "스펙 문서 업데이트" 티켓 아래 자식 티켓으로 둔다.
작업 티켓을 만들 때 함께 만드는 것이 원칙이고(`AGENTS.md` 작업 워크플로), 이 스킬을 돌리는 시점에
없으면 여기서 만든다.

- 부모: 현재 Phase의 "스펙 문서 업데이트" 티켓(Jira에서 `summary ~ "스펙 문서 업데이트"`로 찾고,
  진행 중인 것을 고른다). 없거나 둘 이상이면 사용자에게 묻는다.
- 제목: `{작업 티켓 키} {작업 요지} Spec·Design·ADR 반영` 꼴. 담당자는 작업 티켓 담당자, 추정치는 규모대로.
- **만들기 전에 제목·부모·담당자·추정치를 보여주고 승인받는다.** 승인 없이 만들지 않는다.
  생성은 `create-jira-subtasks` 스킬 규칙을 따른다.

**커밋·PR.** knk-harness는 별도 레포다. 문서 갱신 커밋·PR은 팀 공용 스킬로 진행하고, 각 단계는
사용자 확인을 거친다. 공용 스킬(`create-branch`·`create-commit`·`create-pr`)은 **호출만 하고 수정하지 않는다.**

1. knk-harness에서 `dev` 최신화(pull)를 **먼저** 하고 `docs/{자식 티켓 키}-...` 브랜치를 분기한다
   (묵은 dev에서 갈라지지 않게 분기 전 pull이 필수다).
2. `create-commit`으로 커밋한다 — 브랜치·커밋·PR 제목 모두 **자식 티켓 키** 하나를 쓴다
   (선례: `[KNK-689] Docs: 마이 페이지 변경을 프론트엔드 스펙·QA 문서에 반영`).
3. `create-pr`로 Draft PR을 올린다(브랜치 push는 이 스킬이 함께 한다).
   PR 본문에 동기화 요약(변경 단위 → 분류 → 수정한 문서·항목)을 넣는다.

## §6 금지 사항

- `docs/spec/5-ai-server-spec.md`·`docs/design/3-ai-server-design.md`·`docs/adr/3-ai-server-adr.md` 외의 어떤 파일도 수정하지 않는다(knk-harness의 타 문서 포함).
  용어집·클라이언트·백엔드·분석·배포 문서는 각자 소유자가 있다.
  불일치를 발견하면 고치지 말고 보고만 한다.
- 사용자 확인 없이 문서를 수정하거나 티켓·커밋·PR을 만들지 않는다.
- 스펙에 과거 서술·변경 이력·계획을 남기지 않는다. 그런 내용은 ADR로 옮기거나 지운다.
- ADR에서 D 번호를 재사용하거나 폐기된 D를 삭제하지 않는다.
- 변경 분류를 건너뛰고 스펙 표부터 고치지 않는다.
- 변경과 무관한 곳을 재작성하지 않는다. 문체 통일·개선 욕심으로 무관한 문장을 고치지 않는다.
- A 표의 항목을 근거 없이 지우지 않는다 — 해소된 항목은 해소 근거(커밋·PR)와 함께 정리한다.
- 커밋·PR을 직접 만들지 않는다 — 공용 스킬로 진행하고, 그 스킬을 수정하지 않는다.
