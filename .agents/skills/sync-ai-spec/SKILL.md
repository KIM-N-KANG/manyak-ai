# AI 서버 스펙 동기화 (sync-ai-spec)

## 목적

`knk-harness/docs/product-specs/5-ai-server.md`는 AI 서버의 SSOT 스펙이다.
manyak-ai 구현이 바뀌면 이 문서도 따라 바뀌어야 하는데, 사람이 기억에 의존하면
스펙과 구현이 조용히 어긋난다(드리프트). 이 스킬은 그 간극을 git으로 감지하고,
문서의 서술 철학(3층 서술)에 맞게 갱신한다.

문서는 코드 설명서가 아니다 — 모든 주요 단위가 **배경(Context) → 문제와
결정(Problem & Decision) → 구현(Implementation)** 순서로 서술되어 있고, 핵심
설계 결정은 §5-2의 카탈로그(D1~Dn)에서 한 번만 서술된다. 따라서 동기화도
"코드가 바뀌었으니 구현 표를 고친다"가 아니라, **이 변경이 어느 층위를
건드리는지 판단하는 것에서 시작**한다.

## 핵심 원칙

- **층위 판단이 먼저다.** 구현 변경이 곧 Implementation 수정은 아니다. 결정이
  뒤집힌 변경을 값 표 수정으로 처리하면 문서의 근거 서술이 거짓이 된다.
  변경마다 "Context가 바뀌었나 → Problem & Decision이 바뀌었나 → Implementation만
  바뀌었나"를 순서대로 묻는다.
- **수정 대상은 5-ai-server.md 하나뿐이다.** knk-harness의 다른 문서
  (0-glossary, 3-frontend, 4-backend, 6-analytics, 7-deployment …)는 각자
  소유자가 있다 — 어떤 이유로도 건드리지 않는다. 타 문서와의 불일치를 발견하면
  수정하지 말고 보고만 한다.
- **D 카탈로그 관리 규칙을 따른다.** 규칙의 정본은 문서 §5-2다 — 새 결정은
  등록 기준(장기적·구조적·다수 파급)을 통과할 때만 D(n+1)로 추가(번호 재사용
  금지), 기준 미달이면 해당 섹션 Implementation 갱신으로 격하, 뒤집힌 결정은
  삭제하지 않고 `폐기` 상태 전환 + 대체 사유 기록.
- **변경과 무관한 섹션은 재작성하지 않는다.** diff가 가리키는 좌표(결정 ID ×
  섹션)만 수정한다. 문체 통일·개선 욕심으로 무관한 문장을 고치지 않는다.
- **모호하면 질문한다.** 층위 판단이 애매할 때 낮은 층위(Implementation)로
  단정하는 것이 가장 흔한 오류다. 판단 근거가 부족하면 사용자에게 묻는다.
- **확인 후 반영한다.** 갱신안(어느 층위·어느 결정·어느 섹션)을 먼저 보여주고
  확인받은 뒤 문서를 수정한다.

## 경로와 대상

| 항목 | 값 |
| --- | --- |
| 스펙 파일 | `../knk-harness/docs/product-specs/5-ai-server.md` (수정 허용 대상은 이 파일뿐) |
| 동기화 앵커 | 스펙 메타 표의 "기준 코드" 행 — `dev` 브랜치 SHA |
| 감시 경로 (manyak-ai) | `src/` `prompt/` `spec/` `Dockerfile` `pyproject.toml` `.github/workflows/` `.env.example` |

감시 경로 밖의 변경(tests/, scripts/, 문서 오탈자 등)은 스펙에 영향이 없는
것으로 보되, 커밋 메시지가 설계 변경을 시사하면 예외로 포함한다.

## 실행 순서

### 1단계: 드리프트 감지

스펙 메타 표에서 기준 코드 SHA를 읽고, 그 이후의 변경을 수집한다. 아래 `git`
명령은 모두 **manyak-ai 레포지토리 루트에서** 실행한다 — 이 스킬은 두 레포를 오가므로
(감지는 manyak-ai, 문서 수정은 knk-harness) 작업 디렉터리가 knk-harness에 있으면
잘못된 결과가 나온다.

```bash
# manyak-ai 레포지토리 루트에서 실행
git fetch origin
git log <기준SHA>..origin/dev --oneline -- src/ prompt/ spec/ Dockerfile pyproject.toml .github/workflows/ .env.example
```

**변경이 없으면** 사용자에게 알리고 종료한다:
> "기준 SHA 이후 스펙 영향 경로의 변경이 없습니다. 스펙은 최신입니다."

변경이 있으면 커밋(또는 머지 PR) 단위로 묶어 목록화한다.

### 2단계: 층위 판단 (변경 단위마다)

판단 입력은 diff만이 아니다 — **커밋 메시지·PR 본문·manyak-ai `spec/` 파일의
동반 변경 여부**('왜'가 적힌 곳)를 함께 읽는다. 세 질문을 순서대로 묻는다.

1. **Context가 바뀌었나?** — 기능의 존재 이유·제품 배경 자체가 달라졌다
   (기능 추가·제거, MVP 범위 변경, 서비스 역할 변화).
   → 해당 단위의 배경 서술부터 다시 쓰고, 그 아래 결정·구현을 연쇄 재검토한다.
   문서 전반에 파급되는 규모라면 단독으로 갱신하지 말고 사용자에게 상위
   판단(문서 구조 개편 여부)을 요청한다.
2. **Problem & Decision이 바뀌었나?** — 설계 결정의 변경·폐기·신설이다
   (모델·공급자 교체, stateless 포기, 선택지 정책 변경 등. manyak-ai `spec/`
   파일이 함께 바뀌었다면 강한 신호다).
   → §5-2 카탈로그를 D 관리 규칙대로 갱신하고, 그 결정을 참조하는 섹션들의
   구현 서술을 연쇄 갱신한다.
3. **Implementation만 바뀌었나?** — 결정은 그대로이고 계약 필드·파라미터 값·
   내부 구조만 바뀌었다.
   → 해당 §의 구현 층(표·스키마·서술)만 최소 수정한다.

판단 예시:

| 변경 | 층위 | 처리 |
| --- | --- | --- |
| temperature 0.75 → 0.8 (실측 근거 커밋) | Implementation | §5-4-3 값 표만 갱신 (D9는 그대로) |
| 선택지를 본문 스트림에 재통합 | Problem & Decision | D6 `폐기` 전환 + 대체 사유, §5-3-4·§5-3-5 연쇄 갱신 |
| 요약(summary) 생성 기능 AI 이관 | Context + Decision | §5-3-4 배경·Phase 라벨부터 재검토, 필요 시 새 D 등록 검토 |
| 응답 meta에 필드 1개 추가 | Implementation | §5-6 meta 표 갱신 (D10은 그대로) |

### 3단계: 결정·섹션 매핑

층위 판단 결과를 문서 좌표로 변환한다 — 영향받는 결정 ID(D1~Dn)와 섹션(§5-2~
§5-7)의 교차점만 수정 대상으로 잡는다. §5-7 간극 표(A*)에 영향이 있으면(간극
해소·신규 간극) 함께 대상에 넣는다.

### 4단계: 갱신 제안·확인

수정안을 요약해 사용자에게 확인받는다:

> "다음 갱신을 제안합니다:
> - [커밋/PR] → 층위: {Context/결정/구현} → 대상: {D번호, §번호}
> - 요지: {한 줄}
>
> 진행할까요?"

### 5단계: 문서 갱신 + 앵커 갱신

확인받은 수정을 반영한다. 3층 서술 순서(계약 표는 구현 층에만), §5-2 단일
서술(타 섹션은 ID 참조), 0-glossary 용어, 기존 문체(존댓말)를 유지한다.

마지막으로 메타 표를 갱신한다 — 기준 코드 SHA, 작성일, 버전(내용 변경 시 +0.1).
동기화한 `dev` SHA는 manyak-ai 레포지토리 루트에서 `git rev-parse --short=12 origin/dev`로
획득한다(메타 표는 12자리 short SHA 표기다 — `git log` 출력을 눈으로 옮기지 않는다).

### 6단계: PR 안내

knk-harness는 별도 레포다. 커밋·PR은 사용자 확인 게이트를 거친다:

1. knk-harness에서 `dev` 최신화(pull) 선행
2. `docs/KNK-xxx-...` 브랜치 분기(티켓 키는 해당 작업의 Jira 티켓)
3. 커밋 후 Draft PR — 본문에 동기화 요약(변경 단위 → 층위 → 수정 섹션) 포함

## 오류 처리

| 상황 | 대응 |
| --- | --- |
| 스펙 파일이 없음 | "knk-harness 경로를 확인해주세요. `../knk-harness/docs/product-specs/5-ai-server.md`를 찾을 수 없습니다." |
| 메타 표에 기준 코드 SHA 없음 | 앵커가 없으면 감지가 불가능하다 — 사용자에게 기준 시점을 물어 SHA를 확정하고, 갱신 시 메타 표에 앵커 행을 복구한다 |
| 기준 SHA가 로컬에 없음 | `git fetch origin` 후 재시도. 그래도 없으면(force push 등) 사용자에게 보고 |
| 층위 판단 근거 부족 | Implementation으로 단정하지 말고 해당 변경의 의도를 사용자에게 질문 |
| 타 문서와의 불일치 발견 | 수정하지 않는다. 발견 사실만 보고(타 문서는 소유자·별도 티켓 사안) |

## 금지 사항

- 5-ai-server.md 외의 어떤 파일도 수정하지 않는다(knk-harness의 타 문서 포함).
- 사용자 확인 없이 문서를 수정하거나 커밋·PR을 만들지 않는다.
- D 번호를 재사용하거나 폐기된 D를 삭제하지 않는다.
- 층위 판단을 건너뛰고 구현 표부터 고치지 않는다.
- 변경과 무관한 섹션을 재작성하지 않는다.
- 간극 표(A*)의 항목을 근거 없이 지우지 않는다 — 해소된 간극은 해소 근거(커밋·PR)와 함께 정리한다.
