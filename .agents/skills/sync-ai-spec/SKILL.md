# AI 서버 스펙 동기화 (sync-ai-spec)

knk-harness의 `docs/domain/<DOMAIN>/AI/AGENTS.md`에서 대상과 읽는 순서를 확인한다.
STORY, CHAT, MODERATION 중 영향을 받는 세트만 갱신하며, 역할별 문서의 형식은 하네스 작성 가이드를 따른다.
아래 파일명은 해당 AI 세트 기준이다.

| 역할 | 문서 | 내용 |
| --- | --- | --- |
| 배경과 요구사항 | `BACKGROUND.md`, `USER-STORY.md`, `OPERATION-REQUIREMENTS.md`, `TASK-DEFINITION.md` | 승인된 사용자 목표와 태스크 범위 |
| 설계와 외부 계약 | `COGNITIVE-ARCHITECTURE.md`, `SOFTWARE-ARCHITECTURE.md`, `CONTRACT.md` | 책임 경계, 입력과 출력 및 실패 계약 |
| 실행과 평가 구현 | `AI-EXECUTION.md`, `SOFTWARE-IMPLEMENTATION.md`, `AI-ALIGNMENT.md`, `AI-EVALUATION-METHOD.md`, `AI-EVALUATION-IMPLEMENTATION.md`, `AI-PERFORMANCE-REPORT.md` | 모델 호출, 설정, 정렬과 평가 |
| 운영과 검증 | `ERROR-HANDLING.md`, `TEST-CASES.md`, `OBSERVABILITY.md`, `DEPLOYMENT.md` | 오류, 테스트, 관측과 배포 |
| 결정 이유 | `DECISIONS.md` | 확정된 기록을 보존하고 후속 결정에 대체 범위 연결 |

기존 통합 AI Design과 ADR은 과거 근거로 보존한다. 새 도메인 계약을 그 문서에 다시 정의하지 않는다.

## 작업 방식

- 스펙 반영은 **작업 티켓과 별도의 티켓**으로 한다. 작업 티켓을 만들 때 Phase별
  "스펙 문서 업데이트" 티켓(예: KNK-1125 "Phase 3 스펙 문서 업데이트") 아래에 자식 티켓을 함께
  만들어 두고, 구현이 `dev`에 머지되면 그 자식 티켓으로 이 스킬을 돌린다. 자식 티켓을 만드는
  규칙은 `AGENTS.md` 작업 워크플로가 정본이다.
- 자식 티켓이 아직 없으면 **만들 내용(제목·부모·담당자·추정치)을 먼저 보여주고 승인받은 뒤** 만든다 → §5
- 하네스 브랜치·커밋·PR 제목은 모두 그 자식 티켓 키를 쓴다(선례: `[KNK-689] Docs: …`,
  브랜치 `docs/KNK-689-…`).

## 같이 쓰는 파일

경로는 레포 루트 기준이다.

- `.agents/skills/sync-ai-spec/scripts/detect-drift.sh` — 드리프트 감지. **읽지 말고 실행한다.**
  종료코드로 결과를 구분하며, 이전 동기화 PR이나 검증 기록의 AI 커밋 SHA를 `--base`로 지정한다.
- `.agents/skills/sync-ai-spec/scripts/test_detect_drift.py` — 스크립트를 수정했을 때 `python3`로 실행하는 경로·종료코드 회귀 검사.
- `.agents/skills/sync-ai-spec/reference.md` — 변경 분류(§1), ADR 4층 서술과 D 카탈로그 규칙(§2),
  갱신 제안·문체(§3), 종료코드 대응(§4), 티켓·커밋·PR(§5), 금지 사항(§6), 완료 보고 형식(§7).

## 하드 룰

- **수정 대상은 관련 `docs/domain/<DOMAIN>/AI/` 세트다.** 다른 서비스와 공용 문서의 불일치는 임의로 고치지 않고 보고한다.
- **Spec은 승인된 계약, Design은 현재 구조를 담는다.** 승인된 계약과 검증된 구조만 각 정본에 반영하고, "이전에는 …였다"류 서술은 지운다.
  근거가 필요하면 ADR 항목으로 연결만 한다.
- **결정이 걸리면 ADR부터 쓴다.** 방법을 갈아탄 변경을 스펙 값만 고쳐 끝내면 ADR의 근거 서술이
  거짓이 된다. 어느 변경이 결정인지 가르는 기준 → §1. 확정된 ADR 본문은 보존하고 새 기록에 대체 ID·범위를 연결한다
- **확인 후 반영한다.** 갱신안(어느 문서·어느 항목·요지)을 먼저 보여주고 승인받은 뒤 고친다.
- **변경과 무관한 곳은 재작성하지 않는다.** diff가 가리키는 항목만 수정한다.
- **모호하면 질문한다.** 근거가 부족한데 "값만 바뀜"으로 단정하지 않는다. 없던 대안 비교를 지어내지도 않는다.
- **압축된 말을 쓰지 않는다.** 일상에서 안 쓰는 짧은 한자말로 뜻을 뭉뚱그리지 않는다 — 금지 목록과
  대체어는 §3에 있다. 문서 본문뿐 아니라 커밋 메시지·PR 본문·사용자 보고에도 적용된다.
- 나머지 금지 사항 → §6

## 1단계 — 감지

- [ ] `bash .agents/skills/sync-ai-spec/scripts/detect-drift.sh --base <AI 기준 SHA>`
- [ ] 종료코드로 갈린다 → 상세는 `reference.md` §4
      - `0` — 기준 SHA 이후 변경 없음. 문서 본문과 코드의 일치까지 검증한 것은 아니다
      - `10` — 감시 경로 안에 변경 있음. 커밋(또는 머지 PR) 단위로 묶어 2단계로
      - `11` — 감시 경로 **밖** 변경만 있음. 끝내지 말고 그 커밋 메시지를 읽어,
        설계 변경을 시사하면 2단계로, 아니면 "문서 반영 대상 변경 없음"으로 보고한다
      - `1`·`3`·`4`·`5` — 대상 세트 문서 없음 / 기준 SHA 미지정 / 기준 SHA가 로컬에 없음 /
        fetch 실패. §4대로 대응한다. **실패를 "최신"으로 보고하지 않는다**

## 2단계 — 변경 분류 (변경 단위마다)

- [ ] 커밋 메시지·PR 본문·`spec/` 동반 변경을 함께 읽고, **값·계약만 바뀌었는지, 결정이 바뀌었는지** 가른다 → §1
      - 승인된 계약 → Spec, 현재 내부 구조·설정 → Design의 해당 절을 고친다
      - 결정 → ADR에 4층으로 새 기록을 쓰고(§2), Spec·Design에는 각 역할의 결과만 반영한다

## 3단계 — 제안과 승인

- [ ] 갱신안을 문서·항목·요지로 보여주고 **승인받는다** → §3
- [ ] 스펙 반영 자식 티켓이 없으면 만들 내용을 함께 보여주고 승인받는다 → §5

## 4단계 — 갱신

- [ ] 승인받은 항목만 수정한다. Spec은 승인된 계약, Design은 현재 구조를 짧게 쓰고, ADR은 확정 본문 보존·4층 순서·기존 문체·LF 유지 → §3
- [ ] 비교에 사용한 이전 SHA와 대상 dev SHA, 도메인별 검토 범위를 동기화 PR과 검증 기록에 남긴다. 모든 도메인을 검토하지 않았다면 전체 AI 문서가 동기화됐다고 기록하지 않는다.
- [ ] 하네스의 제품 및 AI 작성 가이드를 따른다. 현재 명세 본문에 이력용 메타 표를 추가하지 않으며 기존 ADR의 ID와 결정일을 보존한다.

## 5단계 — 커밋·PR

- [ ] knk-harness에서 pull 후 자식 티켓 키로 분기 → 공용 스킬로 커밋·Draft PR → §5
