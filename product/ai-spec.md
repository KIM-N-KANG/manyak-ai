# ai-spec — AI 설계 정본 (SSOT)

> **역할.** 프론트엔드(fe)·백엔드(be)·AI(ai) 세 갈래 개발이 **서로 다른 방향으로 가지 않게** 하기 위한 설계의 단일 진실 공급원(SSOT)이다.
> 마냑 AI가 **무엇을·어떻게 동작해야 하는지**를 한곳에 적고, fe/be는 이 기준에 맞춰 자기 쪽을 같은 방향으로 개발한다.
>
> **층위.** 이 문서는 *설계(무엇을·왜)*다. `spec/chat/`·`spec/story/`는 이 설계를 manyak-ai **레포 내부에서 코드로 옮기는 하위 구현 명세**다.
> 설계 결정은 **여기에만** 적고, [`ai-plan`](./ai-plan.md)·[`ai-ops`](./ai-ops.md)와 하위 `spec/`은 이 문서를 **링크로 참조**한다(복사 금지 — 출처가 한곳이어야 한쪽만 고쳐져 생기는 모순을 막는다).
>
> **fe/be 접점.** 이 문서는 fe-spec·be-spec과 만나는 접점(§7 — API 계약·데이터 형태·동작 시나리오)에서 서로 맞아야 한다.
> be-spec·fe-spec은 이 레포에서 수정하지 않는다(다른 레포 관할). 이 문서 변경이 §7 접점을 건드리면, 어떤 fe/be 계약에 영향을 주는지 명시하고 동기화 필요를 알린다.

---

## 1. 목적과 범위

이 문서는 **be·fe 개발자가 자기 작업을 시작하기 전에 읽고 AI 파트와 합을 맞추는 기준**이다. 성패 기준은 하나다 — **이 문서를 읽고 그대로 작업하면 AI와 충돌(계약·동작 불일치)이 생기지 않아야 한다.**

그래서 이 문서는 "AI가 내부적으로 어떻게 동작하는가"의 설명서가 **아니라**, fe·be·ai 세 갈래가 같은 방향으로 가기 위해 공유해야 할 **약속**을 SSOT로 모은 것이다.

- **답하는 질문**: 마냑 AI가 무엇을·왜 하는가(§3), 데이터가 어떻게 흐르는가(§4), 한 턴/한 작업이 어떻게 도는가(§5), 컨텍스트가 무엇으로 채워지는가(§6), 그리고 **fe/be가 AI와 맞물리는 접점에서 무엇을 주고받는가(§7)**.
- **다루는 것**: fe/be가 AI와 **충돌 없이 작업하기 위해 알아야 할** 계약 · 데이터 형태 · 동작 · 제약.
- **다루지 않는 것**: fe/be의 내부 구현(다른 레포 관할)과, AI 내부의 코드 수준 알고리즘(→ 하위 `spec/chat/`·`spec/story/`). **단 그 알고리즘이 밖으로 노출하는 계약은 §7에 못박는다** — fe/be는 AI가 "어떻게" 만드는지는 몰라도 되지만, "무엇을 주고받는지"는 어긋나면 안 되기 때문이다.
- **독자**: fe·be·ai 개발자. AI에 익숙하지 않아도 데이터 흐름과 턴 루프를 따라갈 수 있게 쓴다.

## 2. 시스템 개요

마냑은 **AI 인터랙티브 스토리 서비스**다. 사용자는 ① 태그로 이야기를 만들고(스토리 제작), ② 그 이야기 안에서 등장인물과 대화하며 전개를 이어간다(채팅 플레이).

제품은 세 영역이 합쳐져 완성된다. AI와의 충돌을 막으려면 **각 영역의 책임 경계**부터 합의돼야 한다.

| 영역 | 레포 | 책임 (요지) | AI와 맞물리는 지점 |
|---|---|---|---|
| **fe** | manyak-web | 화면·입력 UI, 결과 표시, 채팅 SSE 스트림 수신·렌더 | AI 응답의 **형식**(SSE 이벤트·화자 라벨 등)에 의존 → §7.2 |
| **be** | manyak-server | 오케스트레이션·인증·DB. 채팅 상태(History·summary)·스토리 명세를 소유하고, 매 호출에 필요한 재료를 ai에 실어 보낸다 | AI **요청·응답 계약**과 **무엇을 보내야 하는지**에 의존 → §7.1 |
| **ai** | manyak-ai | LLM 게이트웨이. **완전 stateless** — 받은 재료로 프롬프트를 조립해 LLM을 호출하고 응답만 돌려준다. 턴 사이에 아무것도 보관하지 않는다 | be가 보낸 재료에만 의존, 상태를 갖지 않음 |

```text
사용자  ⇄  fe(manyak-web)  ⇄  be(manyak-server)  ⇄  ai(manyak-ai)  ⇄  LLM(DeepSeek)
                                     │
                                     └─ DB (스토리 명세 · History · summary 영속)
```

**가장 흔한 충돌의 뿌리는 "상태를 누가 갖느냐"의 오해다.** ai는 무상태이므로, 대화를 이어 붙이는 책임(History 누적 · 요약 갱신 · DB 영속)은 전적으로 **be**에 있다. ai는 매 호출에서 be가 보낸 재료만으로 응답하는 순수 함수처럼 동작한다. 이 경계가 §4(데이터 흐름) · §5(턴 루프) · §7(접점 계약)의 토대다.

## 3. 기능 정의 — 무엇을·왜

마냑 AI는 두 갈래의 기능을 제공한다. 모두 **be의 호출에 응답하는 stateless 함수**이며(§2), fe/be가 각 기능을 언제 부르는지는 §5(턴 루프)·§7(접점 계약)에서 구체화한다. 아래 입력·출력은 *요지*이며, 정확한 스키마는 §7에 못박는다.

### 3.1 스토리 제작 — 스토리라인 생성 → 컴파일

사용자가 고른 태그로 이야기의 씨앗을 만들고(스토리라인), 그중 한 편을 골라 플레이 가능한 스토리로 부풀린다(컴파일). 두 단계로 나눈 이유는 — 사용자가 **여러 후보를 보고 고른 뒤** 구체화하도록, '가볍게 3편 제시'와 '무겁게 1편 완성'을 분리하기 위해서다.

| 기능 | 입력 (be → ai) | 출력 (ai → be) | 왜 |
|---|---|---|---|
| **스토리라인 생성** (`storylines`) | 태그 3종(장르·주인공·주변인물) | 서로 다른 이야기 **3편** + 각 편 추천 추가정보 3개 | 사용자가 고를 후보를 빠르게 제시. 단일 호출(가벼움) |
| **컴파일** (`compile`) | 선택 스토리라인 + 추가정보 + 태그 | 채팅을 구동할 **스토리 명세**(세계관·인물·주인공·연출·시작 설정) | 희소한 줄거리를 채팅 재료로 확장. 무거운 단발 작업(스토리당 1회) |

> 하위 정본: [`spec/story/1-STORYLINES.md`](../spec/story/1-STORYLINES.md) · [`spec/story/2-COMPILE.md`](../spec/story/2-COMPILE.md)

### 3.2 채팅 플레이 — 턴 단위 인터랙티브 스토리

컴파일된 스토리 안에서, 사용자가 주인공이 되어 등장인물(AI가 연기)과 대화하며 이야기를 이어간다. **한 턴** = 사용자 입력 한 번 → AI 응답 한 번이며, AI는 ① 상황 묘사 ② 인물 대사 ③ 다음 행동 선택지 3개를 돌려준다.

| 기능 | 입력 (be → ai) | 출력 (ai → be) | 왜 |
|---|---|---|---|
| **채팅 턴** (`chat turns`) | 매 턴 재료(스토리 명세 통글 + 시작 설정 + 최근 History + 사용자 입력 + 대화 요약) | SSE 스트림 — 본문 토큰 + 완료(본문 · 선택지 3개 · 메타) | 실시간 대화. AI는 무상태라 매 턴 be가 재료를 모두 실어 보낸다 |

> 하위 정본: [`spec/chat/1-PROMPT-LAYER.md`](../spec/chat/1-PROMPT-LAYER.md) ~ [`spec/chat/4-SERVICE-IMPLEMENTATION.md`](../spec/chat/4-SERVICE-IMPLEMENTATION.md)

## 4. 데이터 흐름 — LLM ↔ ai-spec ↔ DB

데이터는 **두 시점**으로 나뉘어 흐른다. 이 분리를 섞으면 "AI가 매 턴 스토리를 다시 만든다"는 오해로 충돌이 난다.

- **컴파일(스토리당 1회)**: 희소 입력을 부풀려 DB에 영속. 이후 모든 턴이 공유한다.
- **런타임(매 턴)**: be가 DB에서 재료를 꺼내 ai에 싣고, 응답을 받아 다시 DB에 저장한다. ai는 그 사이 아무것도 보관하지 않는다.

### 4.1 스토리 제작 데이터 흐름 (컴파일 — 스토리당 1회)

```text
사용자 태그 ─→ be ─(storylines)→ ai ─→ 이야기 3편 ─→ 사용자가 1편 선택
선택 스토리라인 + 추가정보 + 태그 ─→ be ─(compile)→ ai ─→ 스토리 명세 ─→ be가 DB에 영속
                                              └ stories · story_settings · story_start_settings · story_suggested_inputs
```

- ai는 스토리 명세를 **만들어 돌려줄 뿐** 저장하지 않는다 — 영속은 be의 책임이다.
- `genre`는 예외 — ai 출력을 쓰지 않고 **be가 입력 태그로 채운다**(§7에서 계약화).
- 이 4테이블이 §4.2 채팅의 재료가 된다.

### 4.2 채팅 턴 데이터 흐름 (런타임 — 매 턴)

```text
매 턴:
  be ─[story_settings 통글4 · story_start_settings · genre · History(최근 10턴) · summary · 사용자 입력]→ ai
  ai ─[6레이어 조립 → LLM 호출]→ SSE: token… → completed{ aiOutput · 선택지 3개 · meta }
  be ─[aiOutput을 History에 저장 · summary 갱신(별개 기능)]→ DB
```

- be가 **매 턴 재료를 전부** 싣는다 — ai가 무상태라 이전 턴을 스스로 기억하지 못하기 때문이다.
- ai 응답 중 **본문(aiOutput)만 History에 저장**한다. 선택지는 '제안된 가능성'일 뿐 실제 진행이 아니라 저장하지 않는다(실제 진행 = 사용자가 다음에 보내는 입력).
- `summary`(대화 요약)는 be가 만들어 다음 턴에 싣고, ai는 받은 summary를 **참조만** 한다.

> 무엇이 어떤 형식으로 오가는지(스키마)는 §7, 매 턴이 도는 순서는 §5에서 다룬다.

## 5. 에이전틱 루프(턴 루프) 설계

마냑 AI는 도구를 자율 호출하는 에이전트가 아니라, **정해진 흐름을 도는 파이프라인**이다. 무엇을 LLM이 정하고 무엇을 코드가 보장하는지가 fe/be의 기대(지연·개수·형식)를 좌우하므로 여기서 명확히 한다.

### 5.1 채팅 한 턴이 도는 순서

```text
① 사용자 입력 → ② be: 재료 준비(DB 조회) → ③ ai: 6레이어 조립
  → ④ ai: 본문 LLM 호출(스트리밍) → ⑤ ai: 선택지 LLM 호출(별도)
  → ⑥ ai: 본문+선택지+메타 합쳐 SSE completed → ⑦ be: History 저장 · summary 갱신
```

- **한 턴에 LLM을 2번 부른다** — 본문(상황·대사)과 선택지(다음 행동 3개)는 분리된 호출이다. fe/be는 이를 단일 응답(completed 하나)으로 받는다.
- ④ 본문은 **스트리밍**(token 이벤트), ⑤ 선택지는 본문이 끝난 뒤 비스트리밍 호출이다. 그래서 completed는 본문 토큰이 다 흐른 뒤 도착한다.

### 5.2 스토리 컴파일이 도는 순서

```text
① be: 선택 스토리라인+추가정보+태그 → ② ai: LLM 호출(세분 JSON)
  → ③ ai: 빈 필수 필드 검사 → (있으면) ④ ai: 그 블록만 부분 재호출(최대 2회)
  → ⑤ ai: 통글 4필드로 변환 → ⑥ be: DB 영속
```

- 빈 필드가 있으면 **ai가 코드로 부분 재호출**한다(최대 2회). 그래서 compile 응답은 재호출만큼 길어질 수 있다 — fe/be는 타임아웃을 넉넉히 잡아야 한다(§7에서 수치 확정).

### 5.3 누가 무엇을 정하는가 (LLM vs 코드)

| | LLM이 정함 | 코드가 보장함 |
|---|---|---|
| 스토리·명세·본문·선택지의 **내용** | ✅ 창작 | — |
| 선택지 **개수(정확히 3개)** | — | ✅ 검증·보충·패딩 |
| 컴파일 빈 필드 **재호출** | — | ✅ 빈 필수키 탐지 |
| 화자 라벨·형식 정규화 | — | ✅ 출력 후처리 |

> 이 표가 중요한 이유 — fe/be는 "선택지가 3개 미만일 수 있다"거나 "형식이 들쭉날쭉할 수 있다"고 가정하면 안 된다. **개수·형식은 코드가 보장**하므로 그 계약(§7)을 믿고 작업하면 된다.

## 6. 컨텍스트 주입 규칙

AI가 한 턴을 응답하려면 be가 **재료를 빠짐없이** 실어야 한다. 빠진 재료는 오류가 아니라 "그 정보 없이 응답"하는 조용한 실패가 되므로(AI는 받은 것만 본다), be가 무엇을 왜 보내야 하는지를 계약으로 둔다. *어떻게 조립하는지*(6레이어 순서·PHI·Depth)는 AI 내부이며 하위 정본에 있다 → [`spec/chat/`](../spec/chat/).

### 6.1 be가 매 턴 보내야 하는 재료

| 재료 | 무엇 | 빠지면 |
|---|---|---|
| `story_settings`(통글 4필드) | 세계관·인물·주인공·연출 규칙 | 무대·인물이 사라져 일반 대화로 흐름 |
| `story_start_settings` | 이 플레이의 시작점(전개 방향 전제) | 출발 맥락을 잃음 |
| `genre` | 장르 | 장르 톤이 흐려짐 |
| `history`(최근 10턴) | 직전 대화 맥락 | 직전 흐름을 잊고 어긋남 |
| `summary` | 누적 대화 요약 | 오래된 맥락을 잃음(MVP는 빈 값 허용) |
| `user_input` | 이번 사용자 입력 | 응답할 대상이 없음 |

- **History 첫 항목(오프닝 시드)**: be가 작가의 시작 장면(prologue+start_situation)을 History 첫 줄로 깔아 보낸다. 그래야 첫 턴부터 AI가 직전 장면을 안다.
- 재료의 정확한 필드명·형식은 §7.1에 못박는다.

### 6.2 입력·출력 표기 규약 (fe·be·ai 공유)

대화의 입력과 출력은 **같은 표기**를 쓴다. 이게 어긋나면 화면 표시와 다음 턴 맥락이 함께 깨진다.

- `*별표*` = 행동·상황 묘사(지문), 그 외 텍스트 = 대사.
- AI가 연기하는 인물 대사는 `인물명: 대사` 형식(화자 라벨). 주인공(사용자)은 화자가 하나라 라벨을 생략한다.
- 이 표기는 **와이어 포맷**이다 — fe는 이를 파싱해 말풍선·이름표로 표시하되, History에는 원문 그대로 보존해 다음 턴 AI에 되먹인다(§7.2).

## 7. fe/be 접점 계약 (교차 스택 정렬)

이 절은 **AI가 노출하는 계약**만 못박는다 — be는 이대로 보내고 받으면 되고, fe는 be를 거쳐 이 형식에 의존한다. AI가 *어떻게* 만드는지(내부)는 §5·§6과 하위 `spec/`에 있다. 다른 레포가 이 계약을 어떻게 구현·소비하는지는 각 레포 spec의 몫이다. **이 절을 바꾸면 fe/be 동기화가 필요하다.**

> 필드 표기: `storylines`·`compile`은 **snake_case**, `chat` completed 메타는 **camelCase**(SSE 와이어 계약). 아래 그대로 따른다.

### 7.1 API 계약 (요청 · 응답)

**① 스토리라인 생성 — `POST /api/v1/story/storylines`**

```json
// 요청
{ "genre_tags": ["..."], "protagonist_tags": ["..."], "supporting_tags": ["..."] }
// 응답 — stories 항상 3편, 각 recommended_infos 3개
{
  "stories": [ { "id": 1, "story": "본문 6~9문장", "recommended_infos": ["...", "...", "..."] } ],
  "meta": { "model": "...", "prompt_versions": {"STORYLINES": 0}, "provider": "deepseek",
            "input_token_count": 0, "output_token_count": 0, "retry_count": 0 }
}
```

**② 스토리 컴파일 — `POST /api/v1/story/compile`**

```json
// 요청 (extra_info는 선택, 기본 "")
{ "selected_storyline": "...", "extra_info": "...",
  "genre_tags": ["..."], "protagonist_tags": ["..."], "supporting_tags": ["..."] }
// 응답 — ERD 4테이블 nested
{
  "stories": { "title": "...", "one_line_intro": "...", "description": "..." },
  "story_settings": { "world_setting": "통글", "character_setting": "통글",
                      "user_role_setting": "통글", "rule_setting": "통글" },
  "story_start_settings": { "name": "...", "start_situation": "...", "prologue": "..." },
  "story_suggested_inputs": ["...", "...", "..."],
  "meta": { "prompt_versions": {"COMPILE": 0}, "retry_count": 0, "...": "나머지는 ①과 동일" }
}
```

- `genre`는 응답에 **없다** — be가 입력 태그로 채운다(§4.1).
- 인물 카드는 `character_setting` 통글 안에 **최대 5명**.

**③ 채팅 턴 — `POST /api/v1/chat/turns` (SSE)**

```json
// 요청 — role은 대문자, summary는 빈 문자열 허용
{
  "genre": "...",
  "story_settings": { "world_setting": "...", "character_setting": "...",
                      "user_role_setting": "...", "rule_setting": "..." },
  "start_settings": { "name": "...", "prologue": "...", "start_situation": "..." },
  "history": [ { "role": "USER|ASSISTANT", "content": "..." } ],
  "user_input": "...",
  "summary": ""
}
```

```text
// 응답 — SSE 이벤트 3종
event: token      data: { "text": "델타" }
event: completed  data: { "aiOutput": "본문 전체",
                          "choices": ["...","...","..."],
                          "meta": { "model": ..., "promptVersions": {...}, "provider": ...,
                                    "inputTokenCount": ..., "outputTokenCount": ..., "retryCount": ... } }
event: error      data: { "code": "...", "message": "..." }
```

- `started`·`chatId`·`turnId`는 **AI가 발행하지 않는다** — be가 부착한다.
- completed의 `aiOutput`은 본문(상황·대사)만, 선택지는 `choices`(항상 3개)로만 — 본문에 섞이지 않는다.

### 7.2 공유 데이터 형태

- **통글 4필드(`story_settings`)** — 사람이 읽는 마크다운. 헤더 구조: `world_setting`=`# 세계관`/`# 전제`/`# 갈등`, `character_setting`=`# 등장인물`+인물별 `## 블록`, `user_role_setting`=`# 주인공`+`## 호칭/역할/배경/성격/입력 선호`, `rule_setting`=`# 전개 규칙`/`# 문체 톤`/`# 분량 배분`.
- **표기 규약** — `*별표*`=지문(행동·상황), 그 외=대사. AI가 연기하는 인물 대사는 `인물명: 대사`(화자 라벨), 주인공은 라벨 생략. History엔 이 **원문 그대로 보존**해 다음 턴 AI에 되먹인다.
- **메타** — `storylines`·`compile`은 snake_case, `chat` completed는 camelCase. 토큰 필드는 `null` 가능.

### 7.3 동작 · 에러 시나리오

- **제작 흐름**: 태그 → `storylines`(3편) → 사용자 1편 선택 → `compile`(명세) → be가 DB 영속.
- **플레이 흐름**: 매 턴 be가 재료 전부 전송(§6.1) → `token` 스트림 → `completed`(본문·선택지 3·메타).
- **에러**:
  - `storylines`·`compile`: 호출 실패·빈 응답·파싱·스키마 실패 → **HTTP 502**(본문엔 사용자용 메시지만, 원문은 Sentry).
  - `chat`: 본문 스트림 실패 → **`error` 이벤트**(SSE는 HTTP 200이라 502가 아니다). 선택지 호출이 통째로 실패해도 폴백으로 3개를 채워 **턴 자체는 완료**된다.
- **상관관계**: be가 `X-Manyak-Request-Id`·`-Session-Id`·`-Anonymous-Id-Hash` 헤더를 실으면 AI가 Sentry scope에 연결한다(`unknown`이면 무시).

## 8. 설계 결정 (SSOT)

ai-plan·ai-ops·하위 spec이 링크로 참조하는 핵심 결정과 근거다.

| # | 결정 | 근거 |
|---|---|---|
| **D1** | AI는 **완전 stateless** — 세션 저장소·session_id 없음 | 상태는 be가 소유(§2). 슬롯 치환은 매 턴 결정적 `.replace`라 부담 없고, 프롬프트 캐싱이 정적 prefix 비용을 무력화. 수평 확장·단순성 |
| **D2** | **하이브리드 컴파일** — LLM은 세분 JSON, 코드가 통글 4필드로 변환 | 검증·부분 재호출은 세분 구조가, 저장·슬롯 주입은 통글이 유리 |
| **D3** | **본문·선택지 분리 2호출** | 선택지가 본문에 섞여 누락되던 문제 해결. 본문 스트리밍과 선택지 JSON을 분리 |
| **D4** | **선택지 정확히 3개는 코드가 보장** | 프롬프트 요청 + 누적 재호출(최대 2) + 폴백 패딩으로 LLM 변동을 흡수 |
| **D5** | **genre는 be가 입력 태그로 덮어씀** | 장르는 입력 태그가 정본. LLM 임의 변경 방지 |
| **D6** | **화자 라벨 볼드는 코드가 정규화** | 모델이 `**이름:**`을 자주 생성 — 프롬프트로 못 막아 출력 후처리 |
| **D7** | **LLM 비추론 호출**(thinking 비활성) | 창작 태스크에서 추론 모드가 외국어 오염·평면화·첫 토큰 지연을 유발(KNK-208 벤치) |
| **D8** | **프롬프트 버전은 frontmatter `version`이 SSOT** | 파일명 고정, 버전은 메타 로깅(`prompt_versions`)으로 노출(KNK-243) |
| **D9** | **실패 원문은 Sentry로만, 클라이언트엔 정제 메시지** | PII·내부 상세 비노출(AN-4) |

## 9. 범위 밖 / MVP 제외

현 단계에서 의도적으로 두지 않는 것. ERD에 컬럼이 있어도 채우지 않는다.

| 제외 | 이유 |
|---|---|
| 키워드북(조건부 삽입, World Info) | 트리거 기반 동적 주입은 MVP 이후 |
| 스탯 시스템(호감도·관계 수치) | MEMORY는 현재 `summary` 한 칸만(대화 맥락만 기억) |
| 해시태그(검색용 태그) | 태그 중 장르만 `stories.genre`로 남김 |
| AI 세션 상태 저장소 | 완전 stateless(D1). 캐싱이 필요하면 be가 담당 |
| AI 선제 첫 메시지(`first_ai_message`) 생성 | 작가의 `prologue`를 be가 첫 화면 + History 시드로 사용 |
| 메모리 요약(`summary`) 생성 | be 몫(Phase 4). AI는 받은 summary를 참조만 |
