# ai-ops — 운영·변경 이력 정본

> **역할.** 운영 중 생긴 **문제와 그 해결(패치노트)**, 그리고 머지된 **PR이 무엇을 바꿨는지**를 최신순으로 기록한다.
> **규칙.** 설계의 *내용*은 [`ai-spec`](./ai-spec.md), 구현 *현황·계획*은 [`ai-plan`](./ai-plan.md)을 가리킨다. 여기엔 '무엇이 바뀌었나'와 '무슨 문제를 어떻게 고쳤나'만 적는다.

---

## 1. 운영 루프 (문제 → 정본 반영)

운영 중 문제가 생기면 **추측으로 코드만 고치지 않는다.** 정본을 다음 순서로 갱신하고, 패치노트(§2)는 이 루프의 마지막 산출물이다.

1. **ai-spec 갱신** — 설계가 틀렸거나 빠졌으면 먼저 [`ai-spec`](./ai-spec.md)을 고친다(설계 SSOT). fe/be 접점(§7)을 건드리면 어떤 계약에 영향을 주는지 명시하고 동기화가 필요하다고 알린다.
2. **ai-plan 갱신** — 바뀐 설계가 *어디에 구현되는지/됐는지*를 [`ai-plan`](./ai-plan.md)의 현 구현 맵·계획에 맞춘다.
3. **ai-ops 기록** — 아래 §2 패치노트에 *티켓(KNK)·증상·원인·해결·관련 변경*을 남긴다.
4. **PR 머지** — 코드·프롬프트 변경이면 PR로 머지하고 §4 PR 이력에 한 줄 추가한다.

```
문제 발견
  └→ ① ai-spec  (설계 수정·접점 영향 명시)
       └→ ② ai-plan  (현 구현 맵·계획 수정)
            └→ ③ ai-ops §2  (증상·원인·해결 기록 = 패치노트)
                 └→ ④ PR 머지 → §4 PR 이력
```

> **진입점은 둘이다.** ① 설계가 먼저 바뀌면 위 `①→④` 순서로 돈다. ② 코드·버그를 먼저 고치면 `PR → ai-ops §2 패치노트 기록`으로 끝내고, 그 수정이 **설계까지 바꾼 경우에만** ai-spec → ai-plan도 갱신한다. 설계가 안 바뀌면 **§2 패치노트 기록만으로 충분**하다(ai-spec·ai-plan은 건드리지 않는다). 어느 경우든 무엇을 왜 고쳤는지는 반드시 §2에 남긴다.

## 2. 패치노트 (문제·해결 기록)

운영 중 발견한 문제와 해결을 최신순으로. 각 항목은 **티켓(KNK)**으로 식별하고, *증상 → 원인 → 해결*과 그로 인한 *정본 변경*(ai-spec 절·ai-plan 항목·PR)을 함께 적는다.

| 티켓(KNK) | 일자 | 증상(무슨 문제) | 원인 | 해결 | 관련 변경(ai-spec·ai-plan·PR) |
|---|---|---|---|---|---|
| _아직 기록 없음 — 운영 루프(§1)로 문제를 해결할 때마다 이 표를 채운다._ |  |  |  |  |  |

> 정본 신설 이전(2026-06-28 이전)의 수정은 §4 PR 이력의 `Fix`/`Chore` 항목에 남아 있다. 이후 발생하는 문제부터 위 표로 추적한다.

## 3. 기록 규칙 (PR 이력)

- 각 항목: **PR(KNK 이슈) · 유형 · 변경 요약**. 필요하면 관련 ai-spec 절·fe/be 접점을 덧붙인다.
- 유형: `Feat`(기능) · `Fix`(수정) · `Docs`(문서) · `Chore`(유지보수) · `CICD`(배포) · `Init`(초기).
- 정렬: 최신순.
