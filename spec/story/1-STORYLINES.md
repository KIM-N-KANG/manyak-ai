# 스토리라인 생성 시스템 명세

---

## 1. 목적

사용자가 선택한 태그(장르 / 주인공 특징 / 주변 인물 특징)를 기반으로, LLM이 서로 다른 분위기의 이야기 3편과 각 이야기에 특화된 추천 추가 정보 3개를 자동 생성하는 시스템입니다.

사용자는 3편 중 마음에 드는 이야기를 선택하고, 추천 추가 정보를 골라 스토리를 구체화합니다. 이 흐름은 와이어프레임의 "스토리 만들기 → 스토리 라인 선택 → 추가 정보 입력" 3단계에 대응합니다.

선택한 스토리라인을 한 편의 플레이 가능한 스토리 명세로 확장하는 **컴파일(COMPILE)** 단계는 별도 문서 `2-COMPILE.md`에서 다룹니다.

---

## 2. 시스템 구성 요소와 존재 이유

이 시스템은 클라이언트, AI 서버, LLM API, 프롬프트 템플릿 4가지로 구성됩니다.

```
클라이언트 (앱)
    ↕
AI 서버 (FastAPI)
    ↕
LLM API (DeepSeek)
```

### 클라이언트
사용자가 태그를 선택하고 결과 이야기를 보는 화면입니다. 태그를 AI 서버에 전달하고, 응답받은 이야기를 화면에 표시합니다.

### AI 서버 (FastAPI)
클라이언트와 LLM API 사이의 중간 역할을 합니다.

AI 서버가 필요한 이유는 두 가지입니다. 첫째, LLM API 호출에는 비밀 키(API Key)가 필요한데, 이 키를 클라이언트(앱)에 두면 외부에 노출될 위험이 있습니다. 키는 서버에서만 보관하고 서버가 대신 LLM을 호출해야 합니다. 둘째, 클라이언트에서 받은 태그를 LLM이 이해할 수 있는 프롬프트로 변환하는 로직이 필요합니다. 이 변환은 서버에서 처리합니다.

### 프롬프트 템플릿 (prompt/story/STORYLINES-TEMPLATE.md)
LLM에게 전달할 지시문의 틀입니다. 별도 파일로 분리하는 이유는, 프롬프트 내용(기획 영역)과 서버 로직(개발 영역)을 독립적으로 관리하기 위해서입니다.

템플릿 파일은 `[SYSTEM]`과 `[USER]` 두 블록으로 구성됩니다.

| 블록 | 내용 | 특징 |
|---|---|---|
| `[SYSTEM]` | 역할·규칙·출력 형식 | 고정. API 호출마다 동일 |
| `[USER]` | 태그 자리표시자 | 호출마다 실제 태그로 치환 |

두 블록을 분리하는 이유는, LLM이 `system`을 "내가 따라야 할 규칙"으로, `user`를 "지금 처리할 입력"으로 구분해 인식하기 때문입니다. 하나의 텍스트로 합치면 소형 모델이 지시를 실행하지 않고 분석·설명하는 오동작이 발생합니다.

### LLM API (DeepSeek)
완성된 프롬프트를 받아 이야기와 추천 추가 정보를 생성합니다. DeepSeek은 OpenAI 호환 API라서 서버는 OpenAI SDK(`AsyncOpenAI`)로 호출합니다. LLM의 출력은 항상 텍스트(String)입니다. JSON 모양으로 생긴 텍스트일 뿐이며, 서버가 이를 실제 JSON 데이터로 변환하는 파싱 작업을 수행합니다.

## 3. 시스템 흐름과 각 단계의 이유

```
[1] 클라이언트  →  태그 전송 (POST /api/v1/story/storylines)  →  AI 서버
[2] AI 서버    →  자리표시자에 태그를 끼워 완성된 프롬프트 생성
[3] AI 서버    →  완성된 프롬프트 전송  →  LLM API
[4] LLM API   →  JSON 형태의 텍스트(String) 반환  →  AI 서버
[5] AI 서버    →  텍스트를 JSON 데이터로 파싱
[6] AI 서버    →  파싱된 결과 반환  →  클라이언트
[7] 클라이언트  →  이야기 3편 화면에 표시
```

**[2] 자리표시자 치환이 필요한 이유**: 프롬프트 템플릿은 고정된 지시문이지만, 태그는 호출마다 달라집니다. 따라서 태그가 들어갈 빈칸을 미리 만들어 두고, 호출 직전에 실제 태그 값으로 채워 완성된 프롬프트를 만들어야 합니다.

**[5] 파싱이 필요한 이유**: LLM은 텍스트 생성 모델이므로 출력은 항상 문자열입니다. 클라이언트가 이야기와 추천 추가 정보를 각각 꺼내 화면에 표시하려면, 문자열을 구조화된 데이터(JSON 객체)로 변환하는 파싱이 반드시 필요합니다.

## 4. AI 서버 요구사항

### 4-1. 프롬프트 완성

DeepSeek은 OpenAI 호환 API이므로, 템플릿의 두 블록을 `messages` 배열에 역할(role)로 나눠 전달합니다. `[SYSTEM]` 블록은 `system` 역할 메시지로, `[USER]` 블록은 `user` 역할 메시지로 보냅니다(`messages=[{"role":"system","content":...},{"role":"user","content":...}]`).

`[USER]` 블록의 자리표시자를 태그 배열로 치환합니다. 각 배열은 쉼표로 연결된 문자열로 변환하여 삽입합니다.

| 자리표시자 | 치환 대상 |
|---|---|
| `{{장르_태그}}` | genre_tags 배열 → 쉼표 구분 문자열 |
| `{{주인공_특징_태그}}` | protagonist_tags 배열 → 쉼표 구분 문자열 |
| `{{주변_인물_태그}}` | supporting_tags 배열 → 쉼표 구분 문자열 |

치환 전후 예시:

```
치환 전: - 장르: {{장르_태그}}
치환 후: - 장르: 게임, 회귀, 환생
```

### 4-2. LLM 응답 파싱

LLM의 응답은 텍스트(String)이므로, 이를 JSON 객체로 파싱해야 합니다. 출력을 JSON으로 강제하기 위해 호출 시 `response_format={"type": "json_object"}`를 지정합니다.

다만 JSON 모드는 최선 노력(best-effort)일 뿐이라, LLM이 JSON 앞뒤에 코드 펜스(` ```json ` ... ` ``` `)를 붙이는 경우가 있습니다. 이 상태에서 파싱을 시도하면 오류가 발생하므로, 파싱 전에 코드 펜스가 있으면 제거하는 방어 처리가 필요합니다. 또한 빈 응답이거나 파싱 결과가 객체(dict)가 아니면 유효하지 않은 응답으로 간주합니다.

### 4-3. 에러 처리

아래 상황에 대한 처리가 필요합니다.

| 상황 | 요구 동작 |
|---|---|
| LLM API 호출 실패(타임아웃·rate limit·요청 거부·연동 오류) | 게이트웨이 오류(502)를 클라이언트에 반환 |
| LLM 응답이 빈 응답이거나 유효하지 않은 JSON | 파싱 실패로 간주하고 게이트웨이 오류(502) 반환 |

502 응답 본문에는 사용자에게 보일 안내 메시지만 담고, 공급자 원문 오류는 Sentry로만 보냅니다(KNK-262). LLM 호출은 90초 타임아웃을 두어 무한 대기를 막고, 초과 시 502로 변환합니다.

### 4-4. API 키 관리

LLM API 키는 환경 변수로 관리해야 합니다. 코드에 직접 작성하면 버전 관리 시스템(Git 등)에 노출될 위험이 있으므로, `.env` 파일 또는 서버 환경 변수에서 읽어야 합니다.

### 4-5. 프롬프트 캐싱

`[SYSTEM]` 블록은 모든 호출에서 동일하므로 캐싱 이점이 큽니다. DeepSeek은 Anthropic처럼 `cache_control`을 명시할 필요 없이, 동일한 접두 컨텍스트(같은 `system` 메시지)를 자동으로 컨텍스트 캐시 처리합니다. 따라서 서버는 별도 캐시 설정 없이 매 호출에 동일한 `[SYSTEM]` 블록을 그대로 전달하면 됩니다.

캐시 적중 여부는 응답의 `usage.prompt_cache_hit_tokens`로 확인하며, 진단 로그에 적중 토큰 수를 남겨 비용·지연을 실측합니다.

## 5. 데이터 명세

### 5-1. 태그 명세

태그가 3가지 종류로 나뉘는 이유는, 각 종류가 이야기의 서로 다른 차원(세계관 / 주인공 / 주변 인물)을 구성하기 때문입니다. 종류별로 LLM에게 전달되는 역할이 다르므로 구분합니다.

| 종류 | 설명 | 권장 개수 | 권장 이유 |
|---|---|---|---|
| 장르 | 이야기의 장르 (게임, 회귀, 환생 등) | 5개 | 장르가 많아지면 이야기의 방향이 흐려짐 |
| 주인공 특징 | 주인공의 성격·능력 특징 | 5개 | 핵심 특징에 집중해야 캐릭터성이 살아남 |
| 주변 인물 특징 | 주변 인물들의 분위기·성격 | 10개 | 주변 인물은 다양할수록 관계의 층위가 풍부해짐 |

위 개수는 입력 설계 권장값입니다. 현재 AI 서버는 태그 개수를 검증·제한하지 않으며, 개수 정책은 상위 백엔드가 관장합니다.

### 5-2. API 계약

#### 요청 (Request)

```
POST /api/v1/story/storylines
```

```json
{
  "genre_tags":       ["게임", "회귀", "환생"],
  "protagonist_tags": ["소심한", "순진한", "눈치 빠른", "책임감 있는"],
  "supporting_tags":  ["위험한", "거친", "압도적인", "비극적인"]
}
```

| 필드 | 타입 | 제약 |
|---|---|---|
| genre_tags | string[] | 필수 |
| protagonist_tags | string[] | 필수 |
| supporting_tags | string[] | 필수 |

#### 응답 (Response)

```json
{
  "stories": [
    {
      "id": 1,
      "storyline": "이야기 본문 6~9문장",
      "recommended_infos": ["추천 추가 정보 1", "추천 추가 정보 2", "추천 추가 정보 3"]
    },
    {
      "id": 2,
      "storyline": "이야기 본문 6~9문장",
      "recommended_infos": ["추천 추가 정보 1", "추천 추가 정보 2", "추천 추가 정보 3"]
    },
    {
      "id": 3,
      "storyline": "이야기 본문 6~9문장",
      "recommended_infos": ["추천 추가 정보 1", "추천 추가 정보 2", "추천 추가 정보 3"]
    }
  ],
  "meta": {
    "model": "deepseek-v4-flash",
    "prompt_versions": { "STORYLINES": 3 },
    "provider": "deepseek",
    "input_token_count": 2100,
    "output_token_count": 1450,
    "retry_count": 0
  }
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| stories | object[] | 항상 3편 고정 — 편수는 프롬프트가 담보하며 코드는 검증하지 않음(상위 `5-ai-server.md` D7의 부분 적용 예외) |
| stories[].id | number | 이야기 식별자 (1, 2, 3) |
| stories[].storyline | string | 이야기 본문 (6~9문장) |
| stories[].recommended_infos | string[] | 해당 이야기의 추천 추가 정보 (항상 3개 — 편수와 마찬가지로 프롬프트가 담보하며 코드는 검증하지 않음) |
| meta | object | 응답 로깅 메타(백엔드 `ai_call_logs` 적재용, KNK-243) |
| meta.model | string | 실제 응답에 쓰인 모델명 |
| meta.prompt_versions | object | 프롬프트 버전 (예: `{"STORYLINES": 3}`) |
| meta.provider | string | LLM 공급자 (`"deepseek"`) |
| meta.input_token_count | number\|null | 입력 토큰 수 |
| meta.output_token_count | number\|null | 출력 토큰 수 |
| meta.retry_count | number | 부분 재호출 횟수(storylines는 항상 0) |

stories와 recommended_infos의 개수를 항상 고정으로 정의하는 이유는, 클라이언트가 배열 길이를 매번 확인하지 않고 안전하게 렌더링할 수 있게 하기 위해서입니다.

## 6. 프롬프트 요구사항

### 6-1. 이야기 생성 요구사항

**다양성**: 3편은 서로 확연히 달라야 합니다. 같은 태그를 받더라도, 아래 5가지 축에서 각 편이 서로 다른 선택을 해야 합니다.

| 축 | 선택지 예시 |
|---|---|
| 서술 초점 | 세계관·운명 중심 / 주인공 내면·성장 중심 / 인물 관계·동맹 중심 / 적대자·음모 중심 |
| 핵심 갈등 | 생존 / 복수 / 속죄 / 미스터리 추적 / 권력 음모 / 금지된 거래 / 배신 / 정체 은폐 |
| 지배 정서 | 웅장함 / 서늘한 비장함 / 불안과 긴장 / 통쾌한 반전 / 쓸쓸한 여운 |
| 무대와 규모 | 탑·던전·학원·전장·가상현실·멸망 이후 중 각각 다르게 / 개인적·집단적·국가적 규모로 다르게 |
| 이야기 구조 | 정방향 상승 / 결정적 반전 중심 / 미스터리 해명 / 몰락 후 재기 |

한 편에서 사용한 핵심 장치(도입 장치, 결말 방향)는 다른 편에서 반복하지 않습니다.

다양성을 요구하는 이유는, 사용자가 같은 태그로 비슷한 이야기 3편을 받으면 선택의 의미가 없어지기 때문입니다.

**태그 귀속**: 태그는 아래 원칙에 따라 올바른 대상에만 귀속시켜야 합니다.

| 태그 종류 | 귀속 원칙 |
|---|---|
| 장르 | 분위기·소재·세계관·서사 구조 등 이야기의 무대 전반에 반영 — 인물 특징으로 전용 금지(상위 `5-ai-server.md`의 태그 귀속 서술과 동일) |
| 주인공 특징 | 주인공의 성격·행동·판단에만 귀속 |
| 주변 인물 특징 | 이야기에 실제로 등장하는 주변 인물의 성격·행동·태도에 귀속. 상황·배경·분위기의 수식어로 전용 금지 |

입력에 없는 특징 태그를 임의로 만들어 사용해서는 안 됩니다.

주인공·주변 인물 특징 태그는 이야기에 실제 등장하는 인물 1명 이상에 구현합니다(장르 태그는 위 표대로 무대에 반영하며 인물에 구현하지 않음. 한 명에게 몰지 않되, 여러 태그를 겸한 입체적 인물은 허용). 단 **태그 단어·동의어·파생형을 본문에 직접 쓰지 않습니다** — 이름 앞 수식(예: "라이벌 강민재")이든 문장의 주어·명사든 어떤 형태로도 노출하지 않고, 오직 행동·상황으로만 드러냅니다(태그 비노출, KNK-212).

**서술 방식**: 본문은 1인칭 '나' 시점으로 쓰되 '나/나는/내'를 매 문장 반복하지 않고, 첫 문장은 시간·장소·사건·타인으로 엽니다. **대사는 금지**입니다 — 인물의 말을 따옴표로 직접 인용하지 않고 간접화법·상황으로 풀어 전합니다.

**짜임새**: 각 이야기는 아래 4단계 흐름이 모두 담겨야 합니다. 텍스트만으로 전체 스토리 라인이 파악 가능해야 합니다.

| 단계 | 역할 | 세부 요건 |
|---|---|---|
| 도입 | 주인공의 처지와 이루려는 목표를 압축 제시 | 주인공을 사건에 휩쓸리는 구경꾼이 아니라, 원하는 것이 한 문장으로 분명하고 그걸 스스로 좇는 주체로 둔다 |
| 전개 | 이야기를 굴리는 핵심 사건·선택의 촉발 | 사건이 일어난 계기나 원인을 한 구절 이상 담는다 |
| 위기 | 갈등 심화 또는 결정적 반전, 관계 변화 | 관계가 맺어진 사연이나 이해관계를 드러낸다 |
| 방향 | 주인공이 직면한 최종 선택과 이야기의 방향 | 선택이 불러올 대가를 담되, 결과(승패·생사)는 확정도 암시도 말고 선택의 기로에서 멈춘다. 다만 무엇을 하려는지(의지)는 뚜렷이 남긴다 — 결과만 열고 목표는 닫는다 |

뒤 단계는 앞 단계의 흐름을 이어받아야 합니다. 상황이나 감정이 크게 전환될 때는 그 계기를 한 구절 이상 드러냅니다.

이야기에 능력·힘·특수 기술이 등장할 경우, 그것이 어떤 조건·한계·대가를 수반하는지 반드시 한 가지 이상 이야기 안에 녹여야 합니다.

**출력 제약**

| 항목 | 기준 |
|---|---|
| 문장 수 | 6~9문장 |
| 글자 수 | 공백 포함 450~600자 내외 |
| 문장 구분 | 문장이 끝날 때마다 이중 개행(`\n\n`)으로 한 문장씩, 문장 사이에 빈 줄 하나 |
| 이모지 | 사용 금지 |

### 6-2. 추천 추가 정보 생성 요구사항

추천 추가 정보가 필요한 이유는, LLM이 생성한 이야기에는 의도적으로 비워둔 빈칸이 있기 때문입니다. 추천 추가 정보는 그 빈칸을 채울 만한 설정을 미리 한 문장으로 제안해, 사용자가 고르거나 다듬어 스토리를 완성하도록 돕는 역할을 합니다.

추천 추가 정보는 해당 이야기에서 아직 정해지지 않은 요소를 구체적 설정으로 제안합니다. 주인공의 핵심 목표와 동기, 주요 인물의 정체와 관계, 결말의 분위기와 방향이 주요 대상입니다. 물음표로 끝나는 질문이 아니라 '~다'로 끝나는 평서문 한 문장으로 쓰며, 이야기의 고유한 설정과 등장인물을 직접 언급해야 하고, 어느 이야기에나 통하는 일반적인 내용은 허용되지 않습니다.

**출력 제약**

| 항목 | 기준 |
|---|---|
| 추가 정보 수 | 이야기 1편당 정확히 3개 (총 9개) |
| 문장 수 | 추가 정보 1개당 평서문 1문장 |
| 글자 수 | 공백 포함 25~45자 내외 |
| 이모지 | 사용 금지 |

### 6-3. 출력 품질 유도 방식 — 예시 대신 설계 원칙 주입

LLM이 태그 귀속·인과 구조·다양성 규칙을 일관되게 따르도록 유도하되, 고정된 출력 예시(few-shot)는 프롬프트에 포함하지 않습니다. 구체적 예시를 박아 두면 모델이 그 예시의 표현·소재를 그대로 베끼거나(앵커링), 금지 표현을 토큰만 바꿔 우회해 재출력하는 경향이 있어 다양한 태그에 일반화되지 않기 때문입니다.

대신 아래를 프롬프트에 명시해, 모델이 스스로 점검하고 결과(JSON)에만 반영하게 합니다.

- **성질 테스트**: 태그를 단어로 박지 말고, "그 태그 단어를 문장에서 지워도 특징이 행동으로 남는지" 자기점검하게 한다.
- **showing 우선**: 감정·특징을 이름표로 선언하지 말고 행동·표정·선택으로 드러낸다.
- **전형 회피**: 가장 먼저 떠오르는 도입·계기·공간은 평균값이니 한 박자 비틀어 덜 뻔한 쪽을 고른다.
- **다양성 축**: 3편이 서술 초점·핵심 갈등·지배 정서·무대·이야기 구조에서 서로 다른 조합을 쓰게 한다.
- **출력 직전 자기 점검**: 위 원칙을 지켰는지 모델이 스스로 확인하고 결과에만 반영한다.

프롬프트 문구를 수정할 때는, 특정 예시를 더하기보다 위와 같은 원칙·자기점검 형태로 기술해야 다양한 장르·태그에 고르게 적용됩니다.

### 6-4. LLM 출력 형식 요구사항

LLM의 출력은 순수 JSON 텍스트여야 합니다. 설명, 머리말, 코드 펜스 없이 JSON만 반환해야 합니다.

출력을 JSON으로 강제하는 이유는, 서버가 응답을 파싱해 클라이언트에 전달하는 구조이기 때문입니다. 형식이 일정하지 않으면 파싱이 실패합니다.

```json
{
  "stories": [
    { "id": 1, "storyline": "...", "recommended_infos": ["...", "...", "..."] },
    { "id": 2, "storyline": "...", "recommended_infos": ["...", "...", "..."] },
    { "id": 3, "storyline": "...", "recommended_infos": ["...", "...", "..."] }
  ]
}
```

## 7. 테스트 기준

| 항목 | 기준 |
|---|---|
| 이야기 개수 | 응답에 항상 3편 포함 |
| 추가 정보 개수 | 각 이야기마다 정확히 3개 |
| 이야기 문장 수 | 각 이야기 6~9문장 |
| 다양성 | 3편의 서술 초점·갈등·정서가 서로 다른지 확인 |
| 태그 반영 | 입력 태그가 이야기에 자연스럽게 반영됐는지 확인 |
| 추가 정보 특화성 | 추천 추가 정보가 해당 이야기의 고유 설정을 언급하는지 확인 |
| 응답 형식 | 응답이 유효한 JSON인지 파싱 성공 여부로 확인 |
| 응답 메타 | `meta`에 model·prompt_versions·provider·토큰 수·retry_count가 실리는지 확인 |
| 에러 처리 | LLM 호출 실패·빈 응답·파싱 실패 시 502 반환 |
