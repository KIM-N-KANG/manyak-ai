# [서비스 구현 명세서] — 6레이어 채팅 시스템의 구체화

> 본 문서는 **[1-PROMPT-LAYER.md]**(누가 무엇을 담는가), **[2-LAYER-PLACEMENT.md]**(어디에·언제·얼마나 자주 배치되는가), **[3-CONTEXT-ARCHITECTURE.md]**(왜 그렇게 조립해야 하는가의 설계 철학)의 추상 명세를, **마냑(Manyak) 채팅 서비스에서 실제로 어떻게 바인딩·구현하는가**로 구체화하는 구현 명세서다.
>
> 즉 1~3이 "보편 원리"라면, 본 문서는 **이 서비스 한정의 구현 결정과 데이터 흐름**을 확정한다. 콘텐츠 소유권·배치의 **정본(SSOT)은 여전히 [1-PROMPT-LAYER.md]·[2-LAYER-PLACEMENT.md]**이며, 본 문서는 그 위에서 구현 선택만 고정한다. 어긋날 경우 1·2가 우선한다.

---

## 0. 이 문서가 메우는 공백

1~3 문서는 6레이어가 **무엇을 담고**, **어디에 놓이고**, **왜 그렇게 조립되는지**를 보편적으로 정의한다. 그러나 다음 질문에는 답하지 않는다.

- 마냑은 **희소한 입력**(태그 + 선택 스토리라인 + 추가정보)만 받는데, 이걸로 STORY/CHARACTER/USER 레이어를 **언제·어떻게 채우는가?**
- "실시간 조립"은 **어느 시점에, 어떤 코드 경계에서** 일어나는가?
- 동적 상태(MEMORY)는 **무엇에·어떻게 저장**되고 매 턴 주입되는가?
- 모델·저장소를 **어떤 추상 경계**로 두는가?

본 문서는 그 공백을 메운다.

## 1. 핵심 원칙 — 두 시점을 분리한다

이 서비스의 모든 혼란은 **서로 다른 시점을 뭉뚱그릴 때** 발생한다. 반드시 둘을 분리한다 — **스토리 컴파일(A-1)**과 **런타임(B)**. (이전 명세는 그 사이에 "세션 초기화(A-2)"를 별도 시점으로 두었으나, **AI를 완전 stateless로 확정**하면서 A-2는 B에 흡수됐다 — 아래 참조.)

### 시점 A-1 — 스토리 컴파일 (작가 시점), **스토리당 1회**
희소 입력(태그·스토리라인·추가정보)을 **풍성한 스토리 명세 JSON**으로 확장해 DB(`story_settings` 등)에 저장하는 시점. **컴파일 LLM은 여기서만 1회 돈다.** 이후 어떤 턴도 재컴파일하지 않으며, 같은 스토리를 여러 플레이어가 이 저장본으로 공유한다.

### 시점 B — 런타임 (조립), **매 턴**
백엔드가 매 턴 모든 재료(통글 4필드 + 장르 + 시작 설정 + 최근 10턴 History + 사용자 입력 + 메모리 요약)를 실어 보내면, AI가 **슬롯 치환 → 6레이어 조립 → 채팅 LLM 호출 → 응답**을 수행하고 **턴 사이에 아무것도 보관하지 않는다(완전 stateless·순수 함수).** 슬롯 치환은 LLM 없는 결정적 `.replace()`라 매 턴 다시 해도 거의 공짜이고, 프롬프트 캐싱이 정적 레이어 prefix를 캐시 read로 만들어 "매 턴 통글 전송"의 토큰 비용도 무력화한다. 따라서 "세션당 1회 초기화"가 따로 필요 없다.

> **세션 초기화(옛 A-2)는 어디로 갔나.** 슬롯 치환·MEMORY 초기화·오프닝 시드를 "채팅방 열 때 1회" 해두고 세션 내내 재사용하던 단계였다. AI가 무상태이므로 보관·재사용이 불가능하고, 대신 ⓐ **슬롯 치환은 매 턴 B가 수행**, ⓑ **오프닝 시드**(prologue+start_situation)는 **백엔드가** History 첫 항목으로 깔아 전달, ⓒ **메모리 요약(summary)**은 **백엔드가** 매 턴 request로 전달한다. AI는 `session_id`도, 첫 턴/이후 턴 구분도 갖지 않는다 — 매 턴 받은 재료로 동일하게 조립할 뿐이다.

```text
┌──────────── 시점 A-1: 스토리 컴파일 (작가, 스토리당 1회) ────────────┐
│  희소 입력                                                            │
│   · 선택 스토리라인 (3편 중 1편)                                      │
│   · 사용자 추가정보                                                   │
│   · (원래 태그 carry-over)                                            │
│        │                                                             │
│        ▼  하이브리드 = 컴파일 LLM 확장 + 결정적 치환                  │
│   스토리 명세 JSON (story_settings 등) → DB 저장                      │
└──────────────────────────────────────────────────────────────────────┘
                   │ (스토리당 1회 컴파일 — 이후 모든 턴이 공유)
                   ▼
┌──────────── 시점 B: 런타임 (매 턴, 완전 stateless) ─────────────────┐
│  백엔드가 매 턴 전달: 통글 4필드 + 장르 + 시작 설정                   │
│   + 최근 10턴 History(오프닝 시드 포함) + 사용자 입력 + 메모리 요약   │
│        │                                                             │
│        ▼  조립기(assembler) — 슬롯 치환 + 6레이어 조립 (LLM 없음)     │
│   [시스템 앞] SAFETY→CORE→STORY→CHARACTER→USER  (매 턴 슬롯 치환)     │
│   [History]  누적 대화 (백엔드가 전달)                                │
│   [Depth]    MEMORY 현재 상태 = 받은 summary (끝에서 1~2번째)         │
│   [PHI]      CHARACTER→STORY→CORE→SAFETY 핵심만                      │
│        │                                                             │
│        ▼                                                             │
│   채팅 LLM 호출 → 응답(SSE 스트림) → 백엔드  (AI는 보관 안 함)        │
└──────────────────────────────────────────────────────────────────────┘

(메모리 요약 생성은 별개 기능 — Phase 4. 백엔드가 History를 압축해 summary를
 만들어 다음 턴에 전달한다. AI는 그 summary를 참조만 하고 만들지 않는다.)

(턴 엔드포인트(/chat/turns)의 LLM 호출은 본문(스트리밍) 하나이고, 주요 사건·엔딩
 재료가 실린 턴은 본문 후 판정 호출이 더해진다 — 2.8. 다음 행동 선택지 3개는
 전용 엔드포인트(/chat/choices)가 만든다 — completed가 선택지를 기다리지 않도록
 분리했고(KNK-625), 백엔드가 completed 이후 같은 재료 + 방금 본문으로 호출한다.
 2.5·4.2.)
```

> **컴파일(시점 A-1, 스토리당 1회)·런타임 조립(시점 B, 매 턴)을 섞지 않는다.** 컴파일 LLM은 A-1에서만 돌고, 슬롯 치환·조립은 B에서 매 턴 일어난다. **AI는 턴 사이 상태를 보관하지 않으며(완전 stateless), 세션 초기화라는 별도 단계가 없다.**

## 2. 확정된 설계 결정 (Phase 0)

### 2.1 역할 매핑 — USER = 주인공, AI = 주변인물 + 스토리 진행

스토리 생성 단계의 산출물을 채팅 레이어에 다음과 같이 귀속한다.

| 스토리 생성 산출물 | 채팅 레이어 | 연기 주체 |
|---|---|---|
| **주인공** (storyline의 "주인공은…") | **USER** | 사람이 1인칭으로 플레이 |
| **주변 인물** (예: 레이, 칸, 세린) | **CHARACTER** | AI가 연기하는 NPC |
| 장르·세계관·전개 | **STORY** | AI가 무대·진행 운용 |

- 사람은 **주인공을 1인칭(First-person)으로 플레이**한다. ([1-PROMPT-LAYER.md:127]의 "철저히 일인칭 관점의 플레이어 프로필" 원칙과 정합.)
- **AI는 주변 인물(들)을 연기하고, 동시에 스토리 진행(무대·연출)을 운용**한다.
- 따라서 CHARACTER-PROMPT의 "사용자에 대한 내적 태도"는 **NPC가 주인공(=사용자)을 어떻게 인식하는가**를 의미한다.

### 2.2 레이어 채우기 — 하이브리드 (컴파일 + 치환)

STORY/CHARACTER/USER를 채울 때 **두 방식을 결합**한다.

- **결정적 치환**: 이름·태그처럼 그대로 꽂으면 되는 값은 `{{슬롯}}` 치환. (현 `prompt.py` 패턴)
- **컴파일 LLM 확장**: 말투·동기·세계관 디테일처럼 **풍부함이 필요한 부분**은 스토리 컴파일(A-1, 스토리당 1회) LLM 호출로 생성.

근거: 순수 치환만으로는 캐릭터 카드가 얇아져 긴 세션 몰입이 약해지고, 풀 컴파일은 비용·지연·검증 난도가 크다. 하이브리드가 **풍부함과 결정성**을 동시에 확보한다.

### 2.3 모델 추상화 — 인터페이스 1개 + OpenAI 호환 구현 1개

- **얇은 `ChatProvider` 인터페이스**(예: `async def complete(messages, **opts) -> str`) 하나만 정의한다.
- 1차 구현은 **OpenAI 호환 chat completions** 클라이언트 하나(`chat_llm.py`의 `AsyncOpenAI` + `base_url` 교체 방식). DeepSeek·Upstage·OpenAI 대부분이 그대로 붙는다.
- 모델·`base_url`·키는 `config.py`에서 주입한다.
- **과잉 추상화 금지**: provider별 클래스를 처음부터 만들지 않는다. messages 구조가 다른 provider(예: Anthropic)가 실제 필요해질 때 **어댑터를 추가**한다.

### 2.4 세션 상태 저장소 — 두지 않는다 (완전 stateless)

- **manyak-ai는 턴 사이에 아무것도 보관하지 않는다.** 세션 상태 저장소(SessionStore)·`session_id` 키 dict를 **두지 않는다.** 런타임에 필요한 모든 재료(통글 4필드·장르·시작 설정·최근 10턴 History·사용자 입력·메모리 요약)는 **매 턴 백엔드가 request로 전달**하고, AI는 `치환 → 조립 → LLM → 응답`만 하고 잊는다(순수 함수: 같은 입력 → 같은 출력, 사이드이펙트 없음).
- 슬롯 치환은 LLM 없는 결정적 `.replace()`라 매 턴 재치환해도 부담이 없고, 프롬프트 캐싱이 정적 레이어 prefix를 캐시 read로 만들어 "매 턴 통글 전송 = 토큰 낭비"도 무력화한다. 따라서 SessionStore로 아낄 실익이 없고, 휘발성·다중 워커·TTL/eviction·구현 복잡도만 떠안는다.
- **메모리 요약(summary)의 영속·생성은 AI 밖에 있다.** History 원본은 백엔드 DB가 소유하고, summary는 백엔드가 만들어(Phase 4) 매 턴 전달한다. AI는 받은 summary를 **참조만** 한다(5절).
- (이력) 이전 명세는 in-memory dict `SessionStore`를 두는 안을 검토했으나, **완전 stateless로 확정**하며 미채택했다. 수평 확장 시에도 AI는 stateless를 유지하고, 캐싱이 필요하면 백엔드(manyak-server)가 담당한다.

### 2.5 입출력 표기·구조 규약 (CORE 소유)

- **표기 규약**: 사용자 입력과 AI 출력은 **동일한 표기**를 공유한다. `*...*` = 행동·상황 묘사(지문), 따옴표 없는 일반 텍스트 = 대사. 이 규약의 소유는 **CORE**다([1-PROMPT-LAYER.md]의 "대사·지문·내면 묘사의 표기 규약"). 입력·출력이 같은 형식이라야 History가 일관된 문체 본보기가 된다([3-CONTEXT-ARCHITECTURE.md] 3부).
  - **화자 라벨**: AI가 연기하는 주변 인물의 대사는 `인물명: 대사` 형식으로 화자를 매 줄 명시한다(예: `레이: 늦었군.`). 따옴표·볼드·괄호 화자 표기 등 다른 장식은 쓰지 않으며, 화자를 지문 서술로만 암시하지 않는다. 주인공(사용자)은 화자가 하나뿐이므로 라벨을 **생략**한다(`*...*`는 연출, 그 외 텍스트는 주인공 대사). 라벨 형식의 세부는 **CORE 소유**이며 그 구현은 `CORE-TEMPLATE.md`에 둔다.
    - **와이어 포맷 ↔ UI 표시 분리**: 이 라벨은 **모델이 출력하는 와이어 포맷**이다. 프론트엔드는 이를 **파싱해 화자를 식별한 뒤 이름 헤더·말풍선 등으로 변환·표시**(단일 화자 시 숨김 가능)하고, **History에는 라벨 원문을 그대로 보존**해 다음 턴 모델에 되먹인다. 즉 라벨은 payload(모델 출력·History)에 항상 존재하되, 최종 화면에 글자 그대로 `인물명:`을 노출할지는 표현 계층의 자유다.
- **턴 결과 3종 = 분리된 두 엔드포인트**: 한 턴의 결과는 ① 상황 묘사 ② 인물 대사 ③ 다음 행동 선택지 3개로 구성되지만, **①②(본문)는 `/chat/turns`가, ③(선택지)은 전용 엔드포인트 `/chat/choices`가** 별개 LLM 호출로 만든다(4.2). 매 응답에 선택지를 함께 담던 옛 단일 호출 설계를 두 호출 합산 발행으로 대체했다가, completed가 선택지 생성까지 기다려 본문 확정이 밀리는 지연을 없애려 **엔드포인트 자체를 분리**했다(KNK-625) — completed 이후 백엔드가 같은 재료 + 방금 본문(`ai_output`)으로 선택지를 별도 요청한다. (주요 사건·엔딩 재료가 실린 턴은 화면 출력이 아닌 **판정 메타**를 만드는 호출이 본문 뒤에 더해진다 — 2.8 ④.)
  - **본문 호출(스트리밍)**: 6레이어 조립 프롬프트로 ① 상황 ② 대사만 생성한다. **본문은 선택지를 담지 않는다** — `CORE`가 "선택지·`[다음 행동]`·번호 목록을 본문 끝에 붙이지 않는다"를 명시한다.
  - **선택지 호출(전용 엔드포인트·JSON)**: 요청에 실려 온 방금 본문(`ai_output`)을 이어, **독립 프롬프트 `CHOICES-TEMPLATE.md`**(6레이어에 들지 않는 별도 위상 — STORYLINES/COMPILE 템플릿과 같다)로 다음 행동 3개를 JSON으로 만든다.
  - **개수(정확히 3개) 보장은 코드 소유**: 프롬프트가 3개를 요청하고, 코드가 검증해 모자라면 "이미 가진 것 제외, 모자란 수만" 재호출로 보충(최대 2회)하며, 그래도 모자라면 **결정적 기본 선택지로 패딩**해 **항상 정확히 3개**를 보장한다(LLM 오류·JSON 파싱 실패도 패딩이 흡수). 즉 선택지 슬롯의 존재·개수·형식은 **CORE 봉투가 아니라 코드**가 담보한다.
  - **선택지의 내용은 `CHOICES` 프롬프트 소유(명세상 STORY 귀속)**: "어떤 선택지인가"(서로 다른 방향 + 이야기 전진 + 급전개 없는 페이싱·약 30턴 보폭)는 이 프롬프트가 결정한다. 본문을 책임지는 STORY와 직교하는 스타일 책임이되, 본문 6레이어가 아닌 **별도 프롬프트**에 둔다.

### 2.6 사용자 입력 유형과 갓모딩 굴절

- 런타임 사용자 입력은 세 가지이며, **모두 변환 없이 History의 user 턴으로** 들어간다.
  - ① 주인공 1인칭 대사 → 그대로
  - ② `*지문*` 연출(행동·상황 묘사) → 그대로
  - ③ AI 추천 선택지 선택 → 선택지 문구 그대로
- 입력창의 `*` 도우미 버튼은 `**`를 자동 삽입하는 **UI 편의**일 뿐, 백엔드·모델에는 `*...*` 텍스트 한 줄로 보인다. 별도 처리 없음.
- **갓모딩 굴절(STORY 소유)**: 사용자의 `*...*` 연출은 존중하되, ① 다른 인물의 대사·내면을 확정하거나 ② 결정적 사건(주요 인물 즉사, 즉시 승리 등)을 일방 선언하면, AI는 그대로 따르지 않고 개연성 있게 굴절시킨다. 입력을 받아들이는 정도(서사 권한)는 STORY가 통제한다.

### 2.7 MVP 범위 — 키워드북·스탯 제외

첫 구현(MVP)에서는 다음을 **구현하지 않는다**. 명세서·슬롯·런타임 어디에도 반영하지 않으며, ERD에 컬럼이 존재하더라도 채우지 않는다.

| 제외 항목 | 관련 ERD | 제외 이유 |
|---|---|---|
| **키워드북(조건부 삽입)** | `story_keyword_notes`, `story_keyword_triggers` | 트리거 기반 동적 주입은 STORY 조건부 메커니즘으로, MVP 이후로 미룬다. |
| **스탯 시스템** | `story_stats`, `play_session_stats` | 5.1과 일관 — 현 단계 MEMORY는 스탯 없이 "대화 맥락"만 기억한다. 호감도·관계 수치 등은 도입하지 않는다. |
| **해시태그(검색용 태그)** | (ERD 저장처 미정) | 발행 스토리에는 태그 중 장르만 `stories.genre`로 남기고, 검색용 해시태그는 MVP 이후로 미룬다. |

> 따라서 MVP의 동적 상태(MEMORY)는 `summary` 한 칸뿐이며(5.1), 정적 레이어를 채우는 입력은 키워드·스탯을 포함하지 않는다.

### 2.8 주요 사건·엔딩 진행 (Phase 1)

작가가 스토리에 심은 **주요 사건(이야기의 갈림길)**과 **엔딩**을 채팅 런타임이 향해 가고 도달하게 만드는 기능이다. 설계·계약의 정본은 knk-harness `5-ai-server §5-3-4·D11`이며, 본 절은 그 manyak-ai 측 구현 결정(슬롯·호출·표기)을 고정한다. **AI는 무상태(2.4)라 진행 상태를 보관하지 않는다** — 재료는 매 턴 백엔드가 실어 보내고, AI의 판정 결과는 응답에 실어 돌려주면 백엔드가 저장했다가 다음 턴에 되싣는다.

> ⚠️ **효용 미검증(실험 게이트).** 아래 슬롯·계약·호출 구조는 확정 구현이지만, 프롬프트 **규칙의 문구**(빌드업 페이싱·3구성 배분 등)는 실험환경으로 baseline 대비 효용을 실측하기 전까지 **잠정**이다. 계약(필드·표기·호출 흐름)은 안정, 규칙 세부는 튜닝 여지가 있다.

**① 요청 추가 필드 (백엔드 → AI, 전부 선택 · 하위호환).** 재료가 없으면 기존 요청과 동일하게 동작한다(현행 트래픽). 넷 다 `ChatTurnRequest`의 선택 필드다.

| 필드 | 내용 |
|---|---|
| `main_events[]` | 주요 사건 전체 `{name, description, key_sentence}` (최대 10) |
| `target_main_event` | 지금 향하는 목표 `{name, progress_turns}` 또는 null (직전 턴 판정 메타를 백엔드가 저장했다 되싣음) |
| `occurred_main_event_names[]` | 이 채팅에서 이미 완결된 사건 이름 |
| `endings[]` | 도달 후보 `{name, achievement_condition, epilogue}` (백엔드가 최소 턴 수 충족분만 걸러 전달) |

**② STORY 슬롯 3종 (본문이 사건·엔딩을 인지).** 재료는 STORY 레이어 슬롯 `{{main_events}}`·`{{target_main_event}}`·`{{endings}}`로 치환돼(재료 없으면 "(없음)"), 본문 호출이 ⓐ 목표 사건을 향해 빌드업하고(`progress_turns`를 페이싱 기준으로) ⓑ 달성 조건을 충족한 턴에 에필로그를 반영한 엔딩 응답을 만들게 한다. **강제 수렴 금지** — 사용자가 벗어나면 억지로 사건·엔딩으로 끌고 오지 않으며, 방향 제안은 선택지가 담당한다(③·D11). 슬롯 소스는 `story_settings`가 아니라 **요청 재료**라 3.3 통글 슬롯과 다르다(예외 소스).

**③ 선택지 3구성 (`CHOICES` 프롬프트).** 재료가 있으면 세 선택지를 **목표 진행 1 + 다른(안 거친) 사건 1 + 자유 맥락 1**로 배분한다(강제 아닌 방향 제안). 향할 다른 사건이 없거나 재료가 비면 기존 "서로 다른 방향" 규칙으로 폴백한다.

**④ 판정 호출 (본문 후 후속 LLM).** 본문 스트림이 끝난 뒤, 방금 장면과 재료로 **판정 전용 프롬프트 `JUDGEMENT-TEMPLATE.md`**(6레이어 밖 독립 위상 — CHOICES/COMPILE과 같다)를 JSON 모드로 호출해 진행을 판정한다. 마커 파싱(신뢰성 문제로 폐기)도, 본문 생성 전 선행 판정(첫 토큰 지연)도 아닌 **사후 전용 호출**이다. (처음엔 선택지 호출과 병렬이었으나 선택지가 `/chat/choices`로 분리되며(KNK-625) 턴 안에서는 판정 단독 후속 호출이 됐다 — completed는 판정만 기다린다.) **재료가 없으면 호출 자체를 스킵**한다(비용·지연 0).

**⑤ completed 판정 메타 (AI → 백엔드, camelCase).** 판정 결과는 `completed` 이벤트에 3필드로 실린다. 백엔드가 채팅 상태로 저장했다 다음 턴 요청(①)에 되싣는다(D11 — 상태는 백엔드, 판정은 AI, 관측 메타와 같은 "응답 계약의 일부" 방식).

| 필드 | 내용 |
|---|---|
| `targetMainEvent` | 이번 턴 판정 후 목표 `{name, progressTurns}`. 목표 없음·완결 직후 null |
| `occurredMainEventName` | 이번 턴 완결된 사건 이름 — 한 턴 최대 1건 |
| `endingName` | 엔딩 응답 턴이면 도달한 엔딩 이름(요청 `endings`의 `name`), 아니면 null |

**⑥ 책임 분담(D7·D11).** 판정의 **정성 판단**(관련성·완결·조건 충족)은 프롬프트(AI) 소유, **형식·유효성 담보**는 코드 소유다. 코드는 목록 밖 이름·형식 위반을 무효화하고, 이미 완결된 사건을 목표·완결로 되보고하면 무효화하며(target·occurred 대칭 가드), 판정 호출이 실패해도 3필드 null로 흡수해 **판정 실패가 턴을 깨지 않는다**(선택지 폴백과 같은 원칙). 진행 카운터 증가/동결, 목표 교체(0부터), 엔딩 최소 턴 수 선별(백엔드) 등 규칙은 `5-ai-server §5-3-4`를 따른다.

## 3. 스토리 컴파일 파이프라인 — 시점 A-1 상세

### 3.1 입력 스키마 (백엔드 → AI 서버)
- `selected_storyline`: 사용자가 선택한 스토리라인 1편 (4문장 본문)
- `additional_info`: 사용자가 입력한 추가정보 (자유 텍스트)
- `genre_tags`·`protagonist_tags`·`supporting_tags` (carry-over): 원래 장르·주인공·주변인물 태그
- `lorebooks` (선택): 장르 공용 용어 사전 `{name, content}` 배열 — 세계관·용어 확장 재료로만 쓰고 원문을 출력 계약에 노출하지 않는다(KNK-422). 비거나 미전달이면 프롬프트에 주입하지 않는다

> **컴파일 산출물 = "스토리 명세 JSON" (영속 대상).** 위 희소 입력을 컴파일한 결과는 **스토리당 1번** 만들어져 백엔드 DB에 저장되고, 이후 채팅 세션은 이 저장본을 읽어 슬롯을 채운다(템플릿 6개는 모든 스토리가 공유, 스토리별로 다른 것은 이 JSON뿐). 마냑 ERD에서의 영속 위치는 다음과 같다.
>
> | 명세서 영역 | ERD 테이블 | 용도 |
> |---|---|---|
> | 프롬프트 재료 (STORY/CHARACTER/USER) | `story_settings` | 정적 레이어 슬롯의 소스 — 3.3 바인딩 |
> | 노출 메타 | `stories` (`title`, `one_line_intro`, `description`, `genre`) | 목록·상세 노출 전용(`genre`만 `{{장르}}` 슬롯에도 치환). **프롬프트 레이어 아님** |
> | 세션 시작 화면 / STORY 슬롯 | `story_start_settings` (`name`, `prologue`, `start_situation`) | 세 곳에 쓰인다 — ⓐ `name`=시작 설정 이름(UI 표시), ⓑ `prologue`·`start_situation`=첫 화면 도입 + 첫 턴 History 시드(3.4·4.2, 백엔드 담당), ⓒ 세 필드를 통글로 엮어 **STORY `{{start_setting}}` 슬롯**에 매 턴 고정 삽입(이 플레이의 출발점·전개 방향 전제, 3.3). 시드(ⓑ)는 직전 장면 연속성이라 10턴 윈도우 밖으로 밀려나지만 슬롯(ⓒ)은 세션 내내 유지된다. |
> | 첫 입력 추천 | `story_suggested_inputs` (`input_text`, 정확히 3) | UI 추천 문구. 레이어 아님 |
> | 주요 사건 | `story_main_events` (`name`·`description`·`key_sentence`, 3~5개) | 이야기의 갈림길. 컴파일 산출물이되 채팅엔 매 턴 **요청 재료**로 되실려 STORY 슬롯·판정에 쓰인다(2.8) |
> | 엔딩 | `story_endings` (`name`·`min_turns`·`achievement_condition`·`epilogue`, 0 또는 3개) | 도달 후보. 백엔드가 최소 턴 수 충족분만 걸러 매 턴 요청에 싣는다(2.8) |
>
> **SSOT 주의**: `stories.description`(노출 상세 소개)과 `story_settings.world_setting`(STORY 재료)은 내용이 겹치기 쉽다. 프롬프트에는 `world_setting`만 쓰고 `description`은 노출 전용으로 분리한다(0절 원칙).
>
> **정본 주의**: 컴파일 입출력 계약의 상세(스키마·검증·재호출·폴백 규칙)는 `spec/story/2-COMPILE.md`가 정본이다. 본 절(3절)은 채팅 슬롯 재료 관점의 요약만 유지하며, 어긋나면 2-COMPILE이 우선한다.

### 3.2 레이어별 채우기 (하이브리드)

| 레이어 | 채우는 방식 | 소스 |
|---|---|---|
| **STORY** | 컴파일 LLM이 선택 스토리라인 + 장르 태그 → 세계관·전개 규칙·서사 문체로 확장 | 스토리라인, 장르 태그 |
| **CHARACTER** | 스토리라인에 등장하는 주변인물명 + 주변인물 태그 → 인물별 카드(성격·말투·동기) 생성 | 스토리라인, 주변인물 태그 |
| **USER** | 주인공 태그 + 추가정보 → 1인칭 플레이어 프로필로 치환·정리 | 주인공 태그, 추가정보 |
| **SAFETY / CORE** | 채우지 않음 — **완전 정적**(콘텐츠 비의존) | 고정 템플릿 |
| **MEMORY** | 빈 상태로 초기화 — 대화가 쌓이면서 요약·압축됨 | — |

> **인물 수 상한**: 컴파일 LLM에 "스토리라인에 실제 등장하는 **주요 인물 최대 5명만** CHARACTER 카드로 만들고, 나머지는 STORY 배경 인물로 흡수"를 지시한다. 시스템 프롬프트 비대화·토큰 폭증을 막기 위함이다. (주인공은 카드가 아니라 **USER**가 소유한다.)

### 3.3 레이어별 슬롯 스키마

> 슬롯은 **사용자 입력을 꽂는 곳이 아니라, 매 턴 런타임 조립(시점 B)에서 `story_settings` 등으로부터 채워지는 출력 칸**이다. 아래 표의 **소스 열은 대부분 `story_settings` 필드(또는 그 하위 키)**이며, 예외는 둘 — `{{장르}}`는 `stories.genre`, `{{start_setting}}`은 `story_start_settings`에서 온다. 슬롯 채움은 전부 결정적 치환이다(LLM 없음). 방식 열의 **컴파일**은 그 필드가 시점 A-1에서 컴파일 LLM으로 생성됐다는 뜻이고, **치환**은 원본 값이 가공 없이 그대로 들어간다는 뜻이다.

> **마냑 DB 바인딩 (`story_settings` → 레이어).** 슬롯의 재료는 한 흐름을 거쳐 형태가 두 번 바뀐다: **태그·스토리라인 → 컴파일(AI 부풀림, 시점 A-1) → `story_settings` 저장 → 슬롯 채움(시점 B, 매 턴).** 따라서 3.2(레이어별 채우기)가 "태그·스토리라인"을 소스로 적은 것(흐름의 앞 토막 = 컴파일 입력)과, 3.3 슬롯표가 `story_settings`를 소스로 적은 것(흐름의 뒤 토막 = 매 턴 슬롯 채움)은 같은 흐름의 다른 지점일 뿐 충돌이 아니다.
>
> 컴파일 결과가 영속되는 `story_settings`는 **통글 마크다운 4필드**이며, **STORY·CHARACTER·USER 세 정적 레이어에만** 귀속한다. 컴파일 LLM은 검증·부분 재호출이 쉽도록 **세분 JSON**으로 답하지만(3.4), 백엔드로 전달·DB 저장되는 형태는 `story_compile_render`가 조립한 **통글 4필드**다(세분→통글 변환은 컴파일 단계 A-1에서 끝난다). 마냑 ERD 기준 귀속을 다음과 같이 **확정**한다.
>
> | `story_settings` 필드(통글) | 소유 레이어 | 대응 슬롯 | 비고 |
> |---|---|---|---|
> | `world_setting` | STORY | `{{world_setting}}` | 세계관 + 전제 + 갈등을 한 통글로(`# 세계관` / `# 전제` / `# 갈등`). |
> | (`story_start_settings`) | STORY | `{{start_setting}}` | **예외 소스 — `story_settings` 아님.** `name`+`prologue`+`start_situation`을 통글로 엮어(`# 시작 설정: {name}` + 프롤로그·시작 상황) 매 턴 고정 삽입한다. 같은 세계관이어도 이 출발점이 전개 방향을 정하므로 STORY 소속. 첫 턴 History 시드(3.4)와 병행하며, 시드가 윈도우 밖으로 밀려나도 이 슬롯이 출발 전제를 유지한다. |
> | `rule_setting` | STORY | `{{rule_setting}}` | 전개 규칙 + 문체 톤 + 분량 배분을 한 통글로(`# 전개 규칙` / `# 문체 톤` / `# 분량 배분`). 작가가 쓴 스토리별 콘텐츠라 **CORE 아님**(CORE는 콘텐츠 비의존 고정, 2.5·3.2). 출력 형식의 고정 봉투만 CORE가 소유. |
> | `character_setting` | CHARACTER | `{{character_setting}}` | 주변인물 카드를 한 통글로(`# 등장인물` + 인물 1명당 `## 블록`, **최대 5명**). **주변인물만** — 텍스트에 주인공이 섞이면 컴파일 시 분리해 주인공 정보는 USER로 보낸다(2.1). 통글의 태도 서술은 **초기 고정값**이며 이후 변화는 MEMORY가 기록한다. |
> | `user_role_setting` | USER | `{{user_role_setting}}` | 주인공(1인칭 플레이어) 프로필 통글(`# 주인공` …). |
>
> **통글 슬롯 = 통째 삽입 (확정).** 매 턴 런타임 조립(B)은 각 통글 필드를 대응 슬롯에 **통째로 삽입**한다 — 하위 키 분해·재분석·LLM이 필요 없다. 컴파일(A-1)에서 세분 JSON의 필수 키를 검증한 뒤 `story_compile_render`가 이미 레이어별 통글로 조립해 두므로(세계관+전제+갈등→`world_setting`, 전개규칙+문체톤+분량배분→`rule_setting`, 인물 카드 반복→`character_setting`, 주인공→`user_role_setting`), 조립 시 슬롯 채움은 순수 치환이다. 이로써 "슬롯 치환 = LLM 없는 결정적 치환" 원칙이 **통글 단위**로 성립한다.
>
> **장르는 예외.** `{{장르}}` 슬롯만 위 흐름을 따르지 않고 `stories.genre`에서 **그대로 치환**된다(`story_settings`를 거치지 않으며 AI 부풀림도 없음). 주인공·등장인물 태그와 달리 장르만 최종 스토리에 원본으로 남기 때문이다(태그 중 장르만 `stories`에 저장). 나머지 태그는 `story_settings` 통글에 녹아든 형태로만 존재하므로 별도 슬롯 소스가 아니다.
>
> **레이어 직교성은 통글 안에서 유지 (확정).** 전개 규칙·서술 톤·분량 배분은 1번 명세서의 스타일 직교 분리(원칙 0 — STORY 안에서도 서로 다른 하위 책임)에 따라 구분되지만, **저장·슬롯 단위로는 `rule_setting` 한 통글**로 합친다(`# 전개 규칙` / `# 문체 톤` / `# 분량 배분` 헤더로 통글 내부에서 구분). 세계관·전제·갈등도 `world_setting` 한 통글에 헤더로 구분해 담는다. 직교성은 별도 슬롯이 아니라 **통글 내부 섹션 헤더**로 보존된다. STORY 템플릿은 이 통글 2개(+장르) 슬롯으로 작성한다(8절).
>
> SAFETY·CORE에는 대응하는 `story_settings` 필드가 없다(콘텐츠 비의존). MEMORY는 명세서가 아니라 런타임 대화로 채워진다(5절).

#### STORY-TEMPLATE.md (정적 무대·연출)
| 슬롯 | 채우는 방식 | 소스 |
|---|---|---|
| `{{장르}}` | 치환 | `stories.genre` (예외 경로 — 유일하게 원본에서 직접 치환) |
| `{{world_setting}}` | 통글 삽입 | `world_setting` 통글(`# 세계관` / `# 전제` / `# 갈등`; 장르 세계관·도입 상황·갈등 가능성이 컴파일 시 반영됨) |
| `{{start_setting}}` | 통글 삽입(예외 소스) | `story_start_settings`(`name`+`prologue`+`start_situation`)를 통글로 엮음(`# 시작 설정: {name}` + 프롤로그·시작 상황). 매 턴 고정 — 이 플레이의 출발점·전개 방향 전제. 첫 턴 History 시드(3.4)와 병행. |
| `{{rule_setting}}` | 통글 삽입 | `rule_setting` 통글(`# 전개 규칙` / `# 문체 톤` / `# 분량 배분`; 장르 속도·긴장 곡선이 컴파일 시 반영됨) — **전개 규칙·분량 배분 핵심이 PHI로 재주입** |
| `{{main_events}}` | 치환(요청 재료) | 요청 `main_events[]` — **예외 소스: `story_settings` 아님, 매 턴 요청에서 옴**(2.8 ②). 없으면 "(없음)" |
| `{{target_main_event}}` | 치환(요청 재료) | 요청 `target_main_event`(백엔드가 되싣는 진행 상태). 없으면 "(없음)" |
| `{{endings}}` | 치환(요청 재료) | 요청 `endings[]`(에필로그 가이드 포함 — 본문이 엔딩 응답 생성). 없으면 "(없음)" |

> 위 사건·엔딩 슬롯 3종은 컴파일 산출물(`story_settings`)이 아니라 **매 턴 요청 재료**에서 채워진다(장르·시작 설정과 같은 예외 소스 계열). 상세는 2.8. 재료가 실리지 않는 현행 트래픽에서는 "(없음)"으로 치환돼 기존 동작과 동일하다(하위호환).

| 슬롯 | 채우는 방식 | 소스 |
|---|---|---|
| `{{character_setting}}` | 통글 삽입 | `character_setting` 통글(`# 등장인물` + 인물 1명당 `## 블록`; 성격·말투·동기·주인공에 대한 태도 포함, 최대 5명). NPC가 주인공을 대하는 태도는 **초기 고정값**이며 이후 변화는 MEMORY가 기록한다. |

### 3.4 스토리 명세 JSON 스키마 (MVP 확정본)

시점 A-1(스토리 컴파일)의 산출물이 **"스토리 명세 JSON"**이다. 이는 컴파일 LLM이 검증·부분 재호출을 위해 내놓는 **세분 JSON(내부 표현)**이며, 백엔드로 전달·DB 저장되는 형태는 `story_compile_render`가 이를 변환한 **통글 4필드(`story_settings`) + 노출 메타/시작/추천**이다(아래 「세분 JSON → 백엔드 계약」 참조). MVP 확정 필드는 다음과 같다.

> **요지**: 이 세분 JSON 중 `prompt_settings`(7필드) + `meta.genre`가 STORY·CHARACTER·USER 3개 프롬프트의 재료가 된다 — 단 프롬프트에 실제로 꽂히는 것은 이들을 레이어별로 합친 **통글 4필드 + 장르**다(3.3). 나머지(노출 메타·시작 화면·추천)는 프롬프트 바깥(노출·UI)에서 쓰인다.

| 영역 | 필드(컬럼) | 한글명 | 누가 채우나 | 프롬프트 유입 | 레이어 |
|---|---|---|---|---|---|
| 노출 메타 (`stories`) | `title` | 스토리 제목 | AI 초안 + 사용자 확정 | ❌ 노출 | — |
| | `one_line_intro` | 한 줄 소개 | AI 초안 + 사용자 확정 | ❌ 노출 | — |
| | `description` | 스토리 소개 | AI 초안 + 사용자 확정 | ❌ 노출 (`world_setting`과 SSOT 분리) | — |
| | `genre` | 장르 | 사용자 선택(태그) | ✅ `{{장르}}` 치환(예외 경로) | STORY |
| 프롬프트 재료 (세분 JSON → `story_settings` 통글 4필드) | `world_setting` | 세계관 설정 | AI 컴파일 | ✅ `{{world_setting}}` 통글 | STORY |
| | `plot_setting` | 사건 설정(객체 `{premise, conflict}`) | AI 컴파일 | ✅ `{{world_setting}}` 통글로 흡수(`# 전제`/`# 갈등`) | STORY |
| | `rule_setting` | 규칙 설정 | AI 컴파일 | ✅ `{{rule_setting}}` 통글 | STORY |
| | `tone_setting` | 문체 설정(서술 톤) | AI 컴파일 | ✅ `{{rule_setting}}` 통글로 흡수(`# 문체 톤`) | STORY |
| | `length_ratio` | 분량 배분(묘사 대 대사 비중) | AI 컴파일 | ✅ `{{rule_setting}}` 통글로 흡수(`# 분량 배분`) | STORY |
| | `character_setting` | 인물 설정(객체 배열, **주변인물만**, 최대 5) | AI 컴파일 | ✅ `{{character_setting}}` 통글 | CHARACTER |
| | `user_role_setting` | 역할 설정(객체, 주인공) | AI 컴파일 | ✅ `{{user_role_setting}}` 통글 | USER |
| 시작 화면 (`story_start_settings`) | `name` | 시작 설정 이름 | AI 초안 + 사용자 확정 | ✅ `{{start_setting}}` 통글 + UI 표시 | STORY |
| | `prologue` | 프롤로그 | AI 초안 + 사용자 확정 | ✅ `{{start_setting}}` 통글 + 첫 화면 도입 + **첫 턴 History 시드** | STORY |
| | `start_situation` | 시작 상황 | AI 초안 + 사용자 확정 | ✅ `{{start_setting}}` 통글 + 첫 화면 도입 + **첫 턴 History 시드** | STORY |
| 추천 입력 (`story_suggested_inputs`) | `input_text` | 추천 입력(정확히 3) | AI | ❌ 추천 버튼 | — |
| 주요 사건 (`story_main_events`) | `name`·`description`·`key_sentence` | 주요 사건(3~5개) | AI 컴파일 | ✅ 컴파일 시점엔 미유입 — 매 턴 요청 재료로 `{{main_events}}` 등 STORY 슬롯·판정에 유입(2.8) | STORY |
| 엔딩 (`story_endings`) | `name`·`min_turns`·`achievement_condition`·`epilogue` | 엔딩(0 또는 3개) | AI 컴파일 | ✅ 컴파일 시점엔 미유입 — 매 턴 요청 재료로 `{{endings}}` 슬롯·판정에 유입(2.8) | STORY |

> **첫 메시지 / 오프닝 장면 시드**: MVP는 AI가 선제적으로 거는 첫 메시지(`first_ai_message`)를 LLM으로 **생성하지 않는다.** 대신 **백엔드가** 작가가 쓴 `prologue`(+`start_situation`)를 **두 곳에 함께** 둔다 — ⓐ 첫 화면에 표시하고, ⓑ **런타임 History의 첫 항목(오프닝 장면, AI 나레이션 턴)으로 시드**한다. 그래야 사용자의 첫 입력(예: "레이에게 문을 열어준다")이 도착했을 때 채팅 LLM이 **직전 장면(밤·숙소·문 두드림)을 알고** 연결된 첫 응답을 만든다. ⓑ가 없으면 모델은 사용자가 화면에서 읽은 오프닝 장면을 보지 못해 첫 턴이 어긋난다(`{{world_setting}}` 통글의 전제는 거시 배경만 줄 뿐 직전 장면을 주지 않는다).
>
> 이는 **새 텍스트를 LLM으로 만드는 게 아니라 이미 작성된 `prologue`/`start_situation`을 컨텍스트에 배치**하는 것이므로 'first_ai_message 미생성' 원칙과 충돌하지 않는다. 시드는 AI 응답이 아니라 무대 설정이며, **사용자 첫 입력 전에는 AI가 응답하지 않는다.**
>
> **STORY `{{start_setting}}` 슬롯과의 병행 (역할 분리).** 시드(ⓑ)는 History 첫 항목이라 대화가 쌓이면 10턴 윈도우 밖으로 밀려나 사라진다 — 직전 장면 연속성은 첫 턴에만 필요하므로 의도된 소멸이다. 그러나 "이 플레이가 어떤 출발점에서 시작됐는가"라는 **전개 방향 전제**는 세션 내내 유지돼야 하므로, 같은 `prologue`·`start_situation`(+`name`)을 통글로 엮어 STORY `{{start_setting}}` 슬롯에도 **매 턴 고정 삽입**한다(3.3). 둘은 역할이 다르다 — **시드 = 직전 장면(연속성, 첫 턴 한정), 슬롯 = 출발 전제(전개 방향, 상시)**. 초반 턴에는 두 경로의 텍스트가 겹치지만 정적 레이어 prefix라 프롬프트 캐싱으로 비용이 무시할 수준이고, 후반에는 시드가 사라진 자리를 슬롯이 메워 출발점을 잃지 않는다.
>
> **지문 래핑 (결정적).** 표기는 2.5 규약을 따른다 — `prologue`/`start_situation` 원문에는 `*` 장식이 없으므로, **백엔드가 시드 시 각 나레이션 단락을 결정적으로 `*…*`로 감싸** 지문(나레이션)으로 넣는다(LLM 없음). 감싸지 않으면 따옴표 없는 일반 텍스트가 되어 모델이 대사로 오인한다(2.5). 저장 원문은 `*` 없이 두고(첫 화면 표시 ⓐ는 원문 그대로 사용), 모델로 가는 History 경로에서만 래핑한다 — 화자 라벨의 **와이어 포맷 ↔ UI 표시 분리**와 동일한 구조다.

## 4. 런타임 조립 (매 턴) — 시점 B 상세

### 4.1 조립 위치(물리적 좌표)
[2-LAYER-PLACEMENT.md] 2절 다이어그램을 그대로 따른다.

1. **[시스템 앞]** SAFETY → CORE → STORY-core → CHARACTER → USER (정적, 세션 1회 고정)
2. **[History]** 누적 대화 (러닝 트랜스크립트)
3. **[Depth]** MEMORY 현재 상태 — 내역 **끝에서 1~2번째**에 매 턴 갱신 삽입
4. **[PHI]** 정적 가드레일/필터 핵심만, 내부 순서 **CHARACTER → STORY → CORE → SAFETY** (SAFETY가 생성에 가장 근접)

> USER는 PHI·Depth 어디에도 재주입하지 않는다(갓모딩 방지). MEMORY는 PHI가 아니라 Depth가 전담한다.

### 4.2 한 턴의 처리 흐름
백엔드가 매 턴 모든 재료를 보내므로, AI는 받은 것으로 조립·호출만 한다 — **상태 조회·갱신·보관이 없다.**
```text
1. 백엔드 request 도착: 통글 4필드 + 장르 + 시작 설정 + 최근 10턴 History(오프닝 시드 포함)
   + 사용자 입력 + 메모리 요약(summary). session_id 없음.
2. 슬롯 치환: 통글·장르·시작 설정을 STORY/CHARACTER/USER 슬롯에 결정적 치환(LLM 없음)
3. History 정규화: role 대문자(USER/ASSISTANT) → LLM 호출용 소문자(user/assistant) 변환, SYSTEM 제외
   · 사용자 입력(*지문*/대사/선택지)은 별도 필드(`user_input`)로 받아, 조립기가 변환 없이
     History 뒤 마지막 user 턴으로 붙인다 (2.5·2.6)
4. MEMORY-TEMPLATE.md 양식에 받은 summary 렌더 → "[현재 상태]" 블록 (빈 문자열이면 빈 칸 그대로)
5. 조립기: 시스템(앞) + History + 사용자 입력(마지막 user 턴) + Depth(현재 상태) + PHI 구성
6. 본문 호출: ChatProvider.complete(messages, stream=True) → 본문 스트림(상황 묘사 + 대사만, 선택지 없음, 2.5)
7. 본문 완료 후 판정 호출(재료가 있을 때만): JUDGEMENT 프롬프트로 호출 → 판정 메타 3필드.
   재료 없으면 스킵, 실패하면 null 흡수(턴을 깨지 않음, 2.8 ④⑤).
   선택지는 이 흐름에서 만들지 않는다 — 전용 엔드포인트로 분리(KNK-625, 아래 선택지 흐름)
8. SSE로 백엔드에 흘려보낸다 — 본문은 token으로 스트리밍, completed에 {본문, choices 빈 배열(하위호환),
   판정 메타(targetMainEvent·occurredMainEventName·endingName, 재료 없으면 null), meta}를 전달
   (meta = 모델·프롬프트 버전(6레이어+JUDGEMENT)·토큰 수(본문+판정 합산)·retry_count 0 고정).
   completed가 선택지를 기다리지 않으므로 본문 확정이 밀리지 않는다.
   AI는 보관하지 않는다 — History 저장·summary 갱신·판정 상태 저장은 백엔드 몫(2.8 ⑤)
```

> **선택지 흐름 (전용 엔드포인트 `POST /chat/choices`, KNK-625).** 백엔드가 completed 이후
> (턴 저장 뒤) 턴 요청과 같은 재료 + 방금 본문(`ai_output`)으로 호출하는 **동기 REST**다.
> CHOICES 프롬프트로 별도 LLM 호출(비스트리밍 JSON) → 다음 행동 3개. 코드가 개수를 검증해
> 보충(최대 2회)·패딩으로 항상 정확히 3개를 보장하고(2.5) 호출 실패도 흡수하므로 **유효한
> 요청이면 LLM 생성 실패도 항상 200**이다(스키마 위반 요청은 422 검증 오류 — "항상 200"은
> 생성 실패 흡수에 한정). 응답 meta(snake_case — camelCase는 SSE completed만의 공식 예외)에 선택지
> 몫 토큰·재호출 횟수(`retry_count`)·`NEXT_ACTIONS` 버전을 싣는다(백엔드 `ai_call_logs`의
> `choice_generation` 행 재료). ⚠️ 요청 history는 **메인 턴과 동일한 스냅샷(이번 턴 제외)**
> 이어야 한다 — 선택지 호출 시점엔 이번 턴이 이미 DB에 있어 그대로 재조립하면 방금 장면이
> history와 `ai_output`에 중복 삽입된다(제외는 백엔드 책임). 재생성도 같은 흐름을 쓴다
> (본문 재생성 completed 후 프론트 트리거 — 백엔드 결정, 2026-07-20).

> **요약 생성은 이 흐름에 없다(Phase 4).** 직전 AI 응답을 요약해 summary를 만드는 루프는 **별개 기능**이며 백엔드가 수행해 다음 턴 request의 summary로 전달한다(5절). AI는 받은 summary를 **참조만** 하고, 비어 있으면 빈 칸으로 조립한다.

> **첫 턴 주의**: 첫 입력이 와도 History는 비어 있지 않다 — 백엔드가 시드한 **오프닝 장면(`prologue`+`start_situation`)이 History 첫 항목**으로 들어 있어, 사용자 첫 입력이 그 뒤에 붙고 조립 시 모델이 오프닝 장면을 본다. **AI는 첫 턴을 따로 구분하지 않는다**(매 턴 받은 history 그대로 조립).

### 4.3 명세 재검증 메모
[2-LAYER-PLACEMENT.md]는 "임의 깊이 삽입"을 전제하나, 실제 OpenAI 호환 API에서 **mid-array system 메시지의 동작**은 모델마다 다르다. 따라서 Depth 블록을 `system` 역할로 끝 근처에 둘지, `user` 역할 메타 메시지로 둘지는 **Phase 5에서 검증 후 확정**한다(7절).

## 5. MEMORY의 3분리 — 가장 흔한 혼동 지점

"채팅 맥락을 기억하는 MEMORY.md"라는 표현은 **세 가지를 뭉뚱그린 것**이다. 반드시 분리한다.

| 구분 | 정체 | 어디에 사는가 | 정적/동적 |
|---|---|---|---|
| **① MEMORY-TEMPLATE.md** | 상태를 **어떤 포맷으로 적고**, **무엇만 기록하며**(Actuality+State), LLM이 주입된 상태를 **어떻게 읽을지**의 규칙·스키마·렌더 양식 | 리포 `prompt/chat/` | **정적** (커밋됨) |
| **② 런타임 상태 데이터(summary)** | 대화 맥락 요약·배경 정보 압축본 | **백엔드**(매 턴 request의 `summary`로 전달; 영속은 백엔드 DB) | **동적** (채팅별) |
| **③ History** | 원본 대화 트랜스크립트 | **백엔드 DB**(매 턴 messages 배열로 전달) | 누적 |

핵심 규칙:
- **① MEMORY-TEMPLATE.md는 채팅 맥락을 저장하지 않는다.** "어떻게 저장·관리할지를 정의"하는 **정적 계약서**다.
- **② 실제 상태(summary)는 AI가 보관하지 않는다.** AI는 무상태이므로, 매 턴 백엔드가 보낸 `summary`를 받아 Depth에 삽입할 뿐이다(빈 문자열이면 빈 칸). 채팅별 summary의 영속은 백엔드 DB가 소유한다.
- **MEMORY는 History의 파생 요약**이다. ([1-PROMPT-LAYER.md:204]) **요약 생성은 백엔드가 수행하는 별개 기능(Phase 4)**이며, AI는 그 결과(summary)를 **참조만** 한다 — 참조(매 턴, 지금)와 생성(Phase 4, 백엔드)을 섞지 않는다.
- **③ History 원본의 영속 저장도 백엔드 DB가 소유**한다. AI 서버는 History도 summary도 보관하지 않으며 매 턴 둘 다 request로 받는다(채팅 이어가기는 백엔드 DB의 History·summary 복원으로 이뤄진다).
- 이름 충돌 주의: 메모리 요약을 `MEMORY.md`로 부르지 않고 **"요약(summary)"**으로 부른다("세션 상태"는 session 예약어와 충돌 — 용어집 §0-3-3·§0-5).

### 5.1 MEMORY 상태 스키마

> 현 단계는 **스탯(호감도·관계 수치 등)이 없으며, "대화 맥락"만 기억**한다. 따라서 상태 스키마는 요약 한 칸으로 시작한다. (향후 스탯이 생기면 필드를 추가한다.)

**상태 데이터 (백엔드가 매 턴 request로 전달하는 `summary`):**
```json
{ "summary": "지금까지의 대화 맥락 요약 텍스트" }
```
> 채팅 턴 API에서 `summary`는 **문자열 한 칸**이다(`ChatTurnRequest.summary: str`). 위 JSON은 향후 스탯이 생길 때를 대비한 상태 스키마 표현이며, 현 MVP는 요약 텍스트 한 줄만 받는다.

**Depth 주입 렌더 양식 (`MEMORY-TEMPLATE.md`가 정의):**
```text
[현재 상태]
{{summary}}
```

**기록 규칙:**
- `summary`에는 **확정된 사실·진행 상황(Actuality)**만 압축해 적는다. 아직 일어나지 않은 가능성(STORY 소관)이나 인물의 고정 성격(CHARACTER 소관)은 적지 않는다.
- **요약 갱신은 백엔드가 수행한다(Phase 4, 별개 기능).** 직전 턴이 확정된 시점(= 다음 사용자 입력이 도착한 때)에 백엔드가 최근 History를 읽어 `summary`를 갱신하고, 다음 턴 request에 실어 보낸다. 재생성으로 폐기된 응답은 다음 입력 전이라 요약에 반영되지 않는다(재생성 기억 오염 차단). **AI는 이 갱신에 관여하지 않고 결과만 받아 참조한다.**
- 이 블록은 **Depth로 내역 끝 가까이** 매 턴 주입된다. (system 역할 기준; Claude 어댑터 추가 시 조립기가 user 역할로 분기.)

## 6. 추상 경계 요약 (구현 계약)

| 추상 경계 | 역할 | 1차 구현 | 교체 대상 |
|---|---|---|---|
| **ChatProvider** | LLM 호출 단일 통로 | OpenAI 호환 클라이언트 1개 — 본문은 `stream=True`, 선택지는 JSON(비스트림) | DeepSeek·Anthropic 어댑터 |
| **PromptCompiler** | 시점 A-1: 희소 입력 → 스토리 명세 JSON | 하이브리드(LLM+치환) | — |
| **PromptAssembler** | 시점 B: 매 턴 슬롯 치환 + 6레이어 조립 | 받은 재료 → 슬롯 치환 → 시스템+History+Depth(받은 summary)+PHI | — |
| **Choices 생성기** | 전용 엔드포인트(`/chat/choices`)의 선택지 생성 + 정확히 3개 보장(KNK-625) | `CHOICES-TEMPLATE.md` 렌더 → ChatProvider(JSON) 호출 → 코드 검증·보충(최대 2회)·기본값 패딩 | — |
| **판정기(Judgement)** | 사건·엔딩 진행 사후 판정(재료 있을 때만) | `JUDGEMENT-TEMPLATE.md` 렌더 → ChatProvider(JSON) 호출 → 코드 보정(목록 밖·이미 완결 무효화)·실패 시 null 흡수 (2.8) | — |

> **SessionStore·SessionInitializer는 두지 않는다.** AI가 완전 stateless이므로 세션 상태 저장소(SessionStore)가 없고(2.4), "세션당 1회 초기화"(SessionInitializer)도 없다 — 슬롯 치환은 `PromptAssembler`가 매 턴 수행하고, 오프닝 시드(지문 `*…*` 래핑 포함)·summary는 백엔드가 매 턴 전달한다(1절·4.2).

## 7. Depth / PHI 검증 (Phase 5 예고)

- **Depth·PHI·World Info는 모델 기능이 아니라 클라이언트 측 messages 조립 기법**이다. DeepSeek·OpenAI·Anthropic 어디서나 동일하게 구현 가능하며, 별도 모델 지원이 필요 없다.
- 검증 대상은 "모델 능력"이 아니라 **"늦게 주입한 지시를 모델이 실제로 더 잘 따르는가"**다.
- **A/B 하네스**: 동일 History에서 ⓐ MEMORY를 맨 앞 시스템에만 / ⓑ 끝에서 1~2번째(Depth)에 주입 → 동일 질문에 대한 상태 준수도 비교. 배포 모델(DeepSeek)로 그대로 실행.
- 부수 검증: mid-array `system` vs `user` 메타 메시지의 효과 차이(4.3).

## 8. 작업 순서 (Phase 1~5)

**Phase 0 — 설계 확정 (완료)**: 2절의 4가지 결정.

**Phase 1 — 정적 레이어 템플릿 작성**
1. `SAFETY-TEMPLATE.md` — 콘텐츠 비의존 가드레일 (슬롯 없음)
2. `CORE-TEMPLATE.md` — 출력 형식·표기·길이 봉투 (슬롯 없음)
3. `MEMORY-TEMPLATE.md` — 상태 스키마 + 기록 규칙 + 렌더 양식 (5절 ①)
4. `STORY` / `CHARACTER` / `USER-TEMPLATE.md` — **통글 슬롯 포함 템플릿**으로
   - STORY는 `{{world_setting}}`·`{{start_setting}}`·`{{rule_setting}}`(+`{{장르}}`), CHARACTER는 `{{character_setting}}`, USER는 `{{user_role_setting}}` 통글 슬롯으로 작성한다(3.3 확정). 전개규칙/문체톤/분량배분, 세계관/전제/갈등은 각 통글 내부 헤더로 구분된다. `{{start_setting}}`은 `story_start_settings`에서 엮은 예외 소스 슬롯이다(장르처럼 `story_settings` 밖).

**Phase 2 — 스토리 컴파일 파이프라인 (시점 A-1)** (3절)
5. 입력 스키마 정의 · 6. `PromptCompiler` 구현

**Phase 3 — 런타임 조립기 + 채팅 API (시점 B)** (4절)
7. `PromptAssembler`(받은 재료 → 슬롯 치환 + 6레이어 조립) · 8. PHI 내부 순서 보장 · 9. `ChatProvider` 연동(본문 `stream=True`) · 10. `CHOICES-TEMPLATE.md` + 선택지 생성기(별도 JSON 호출 → 코드가 정확히 3개 보장, 2.5) · 11. SSE 채팅 턴 엔드포인트(`token`·`completed`·`error`) — 처음엔 completed에 선택지 3개를 합산 발행했고, 이후 KNK-625에서 선택지를 전용 엔드포인트 `/chat/choices`로 분리(completed의 choices는 하위호환 빈 배열)

**Phase 4 — 메모리 요약 생성 (백엔드 주도, 별개 기능)** (5절)
11. 백엔드가 History → `summary`로 요약·갱신해 다음 턴 request로 전달한다. AI는 받은 summary를 참조만 하므로 조립기 구조는 그대로 두고 Depth에 채워 넣기만 한다(참조와 생성 분리).

**Phase 5 — 검증** (7절)
13. Depth/PHI A/B 하네스 · 14. 긴 세션 캐릭터 붕괴(OOC) 회귀 테스트

## 9. 수용 기준 (자기 검증)

- 시점 A-1(스토리 컴파일·스토리당 1회)·시점 B(조립·매 턴)가 분리되고, **AI가 완전 stateless라 세션 초기화 단계가 없으며**(슬롯 치환은 매 턴 B가 수행), 컴파일 LLM은 A-1에서만 도는 것이 명시됨 (1절)
- Phase 0의 4가지 결정이 모두 명시됨 (2절)
- 역할 매핑이 스토리 생성 산출물과 1:1로 귀속됨 (2.1)
- MEMORY가 ①템플릿/②상태/③History로 분리되고, 런타임 상태가 .md 커밋이 아님이 명시됨 (5절)
- 콘텐츠 소유권·배치의 SSOT가 [1·2]임을 재확인하고 본 문서는 구현 결정만 다룸 (0절, 머리말)
- 모델이 추상 경계 뒤에 있고, AI는 완전 stateless라 세션 상태 저장소를 두지 않으며, 과잉 추상화를 피함 (2.3, 2.4, 6절)
- Depth/PHI가 모델 기능이 아니라 조립 기법임과 검증 방식이 명시됨 (7절)
- 입출력 표기 규약(CORE 소유)과, 본문(`/chat/turns`)·선택지(`/chat/choices`)가 분리된 두 엔드포인트의 별개 LLM 호출로 만들어짐이 명시됨(KNK-625) — 정확히 3개 보장은 코드(검증·보충·패딩), 선택지 내용은 `CHOICES` 프롬프트(명세상 STORY 귀속) 소유 (2.5, 4.2)
- 사용자 입력 3종 처리와 갓모딩 굴절(STORY) 규칙이 명시됨 (2.6)
- CHARACTER 카드가 주요 인물 최대 5명으로 제한됨 (3.2~3.3)
- 메모리 요약 생성은 백엔드 주도의 별개 기능(Phase 4)이며, AI는 받은 summary를 참조만 함이 명시됨 (4.2, 5절)
- History·summary 영속은 백엔드 DB가 소유하고, AI는 완전 stateless라 둘 다 매 턴 request로 받음이 명시됨 (5절)
- 작가 오프닝 장면(`prologue`·`start_situation`)을 백엔드가 첫 화면 표시 + 첫 턴 History 시드로 전달해 첫 턴 연속성이 보장됨 (1절, 3.4, 4.2)
